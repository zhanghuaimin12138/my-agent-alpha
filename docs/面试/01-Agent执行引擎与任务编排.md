## 二、60 秒讲述模板(背这个骨架)

> 我的循环是三层嵌套:**外层**不断取用户输入;**中层**处理一条输入,反复"问模型 + 执行工具";**内层 step()** 就是干净的一轮——把对话发给模型,产出模型回复,再产出工具执行结果。
>
> 整个系统最关键的一个判断是中层的停止条件:**看日志里最后一条模型回复,还有没有"写完整的工具调用"**。有就带着工具结果再问一轮,没有就回合结束。不需要任何额外状态变量,翻日志就知道该不该继续——这是我从 gptme 学来的"日志即状态"设计。
>
> step() 用生成器而不是返回列表,调用方每拿到一条消息就立刻落盘,中途断电已产生的内容都不丢。
>
> 稳定性上是真机踩坑踩出来的:模型"光说不做"时(思考里说要调工具但没写出来),有五模式检测器判断"像是想调却没写成",追加一条提醒消息再生成一轮,有次数上限,超限如实报告,绝不静默吞掉。

## 三、高频追问与答法要点

### 1. "循环的停止条件具体怎么实现?"

从后往前找最后一条 assistant 消息,用 `ToolUse.iter_from_content` 解析出工具调用,看是否有 `is_runnable` 的([chat.py:127](../../src/my_agent_alpha/chat.py#L127-L137))。

注意两个细节:
- 只看**最后一条** assistant,不是全部;
- "可运行"指格式写完整,不是执行成功。

另有 `MAX_STEPS=50` 保险丝防死循环,可用环境变量 `ALPHA_MAX_STEPS` 调。

### 2. "流式输出里你解决了什么真问题?"(三个,每个都是加分点)

**断点检测**([llm/__init__.py:144](../../src/my_agent_alpha/llm/__init__.py#L144-L153)):
流式生成中每凑满一行检查一次,一旦出现完整工具调用立刻停止接收剩余生成——反正下一轮会带着工具结果重新生成,留着是浪费钱。

- 为什么"凑满一行"才查?逐字查太慢,行是天然最小单位。
- 为什么代码块闭合后还要等一个空行才算数?防止把没写完的块当成完整调用。

**用量统计**([_StreamWithMetadata](../../src/my_agent_alpha/llm/__init__.py#L55-L83)):
Python 生成器结束时可以 `return` 一个值,但它藏在 `StopIteration` 异常的 `.value` 里,普通 for 循环拿不到。写了个约 30 行的包装类手写 `next()` 捕获它——这样即使提前打断生成,也照样拿到 token 用量。

**标签跨块切断**([_StreamPrinter](../../src/my_agent_alpha/chat.py#L282-L345)):
`<think>` 标签可能被流切成 `"<thi"` + `"nk>"` 两段。收到"可能是半个标签"的尾巴时先扣住不打印,下一段到了能拼齐再判断;标签本身不打印,只用来切换"思考区暗色/正文正常"两种显示。

### 3. "Ctrl-C 按下去之后发生什么?"(考察点:中断发生在两个不同阶段)

- **生成期间**:[reply()](../../src/my_agent_alpha/llm/__init__.py#L154-L155) 捕获,返回"已生成的部分 + `^C 已中断`标记",metadata 记 `interrupted=True`;中层看到标记就写一条中断标记消息、结束本回合、回到提示符([chat.py:387](../../src/my_agent_alpha/chat.py#L387-L390))。
- **工具执行期间**:由工具执行层收尾(见第二个模块)。
- 已产生的内容因为"逐条落盘"都不丢。

### 4. "异常隔离指什么?"(分层兜底)

- **上下文超长**:`ContextLengthError` 捕获后**自愈**——预算砍半、更狠地压缩、重试一次(只重试这一次,[chat.py:100](../../src/my_agent_alpha/chat.py#L100-L106));
- **LLM 请求失败**:交互模式写成 system 消息回到提示符,**脚本模式让它抛**、带错误码退出——不能粉饰;
- **用户输入坏字符**:入口处 `clean_bad_unicode` 清洗(真机实测:输入法坏表情序列曾把写日志搞崩整个程序);
- **外层 try 把 append 和钩子也包住**:任何一条消息的存储问题都不打死整个 REPL([chat.py:566](../../src/my_agent_alpha/chat.py#L566-L579))。

### 5. "稳定性具体提升在哪?举真实例子。"

补发提醒机制([missed_tooluse_reason](../../src/my_agent_alpha/chat.py#L178-L227)),五种真机踩过的坑:

1. **正文为空**:只有 `<think>`,思考里写着"我来调用工具"——模型把"打算调用"当成了"已经调用";
2. **代码块语言标记写岔**:工具叫 `websearch.search`,模型写 ` ```websearch `,解析器静默忽略;
3. **正文以冒号结尾**:话说到一半戛然而止;
4. **行动宣告**:"我来帮你查一下天气"却没代码块——正则用否定预查排除"如果你让我……"这类条件句,是真机误报过一次后加的;
5. **疑似原生调用行没被严格解析认出**:探测前先把围栏内示例盖掉,防止文档示例误报。

设计细节能讲出来很加分:**提醒额度不是整回合一份**——模型只要真的执行过一次调用,额度就重新计数(`MAX_TOOL_NUDGES=1`)。因为真机出现过"提醒恢复→工具超时→模型想换方式重试却被额度掐死"。

### 6. 诚实缺口(主动说比被问出来好)

- 目前**一次 step 只执行一个工具调用**:检测到第一个完整调用就打断,第二个靠下一轮模型自己再提。并行工具调用是明确的未做项(`reply()` 注释里写着留了口子);
- 重试只做了上下文超长这一种,provider 网络错误没有分级重试策略。
