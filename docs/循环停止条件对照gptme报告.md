# 报告:主链路 agent 循环的停止条件分析(对照 gptme)

> 日期:2026-10-30
> 对照对象:gptme 上游 master 版 `gptme/chat.py`(commit `21213ca2`,经 GitHub 拉取核对)
> 本仓库代码:`src/my_agent_alpha/chat.py`(feat/log-storage-layout 分支)

## 一、本仓库的停止条件

循环在 `_process_message_conversation`(中层,处理一条用户输入,`src/my_agent_alpha/chat.py` 约 350-418 行)。
每轮执行一次 `step()`(问模型 + 跑工具),然后按顺序检查 5 个停止条件:

| # | 条件 | 位置 | 动作 |
|---|------|------|------|
| 1 | **用户中断**(生成期间 Ctrl-C,或工具执行期间收到中断消息) | chat.py:388-391 | 写中断标记,回提示符 |
| 2 | **用户拒绝执行工具**(确认链选了 n) | chat.py:392-394 | 直接结束回合 |
| 3 | **步数到上限**(默认 50,环境变量 `ALPHA_MAX_STEPS` 可调) | chat.py:395-397 | 写系统消息说明,结束 |
| 4 | **正常收尾**:最后一条模型回复里没有"写完整、能执行"的工具调用,且不像漏写 | chat.py:398-403 | 回合自然结束 |
| 5 | **漏写提醒超限**:回复像"本想调工具却没写成"(如只有思考、以冒号结尾),提醒过 1 次仍不写 | chat.py:404-413 | 写明原因结束,不留静默失败 |

继续路径只有两条:最后一条回复有可运行调用(chat.py:398-400),或追加一条提醒消息再生成一轮(chat.py:414-418)。
判定函数 `has_runnable_tooluse`(chat.py:128-138)只翻日志找最后一条 assistant 消息,不看任何额外状态变量。

## 二、gptme 的做法(上游 `chat.py` `_process_message_conversation`,行 602-784)

| # | 条件 | 动作 |
|---|------|------|
| 1 | 生成期间 KeyboardInterrupt | 写中断标记,结束回合 |
| 2 | step 产出里有被消费的用户命令 | 结束回合 |
| 3 | 回复里有用户拒绝标记(DECLINED) | 结束回合 |
| 4 | 步数到 `GPTME_MAX_STEPS`(**默认不设上限**,只有设了环境变量才生效) | 写标记,结束 |
| 5 | 最后一条 assistant 无可运行调用(与本仓库完全同构的判定) | 结束回合 |
| 6 | 模型主动调 `complete` 工具(抛异常结束整个会话,外层处理) | 整个会话退出 |

**关键差异**:gptme 在条件 5 上加了三个旁路——因为它做了"回合中途自动压缩",压缩后日志末尾变成摘要、
不再是模型的工具调用,纯看末尾会误判"该结束了",于是被迫引入 `pending_continuation`、`checkpoint_followup`
等额外状态来记住"压缩前到底该不该继续"(上游行 738-771,注释自己承认了这一点)。
另外 gptme **没有**本仓库的"漏写提醒"机制——模型只输出思考、没写工具调用时,回合就静默结束。

## 三、合理性判断:合理,且有两处比 gptme 更稳

**1. 主干判定与 gptme 完全一致,这是验证过的设计。**
"看最后一条 assistant 是否还有可运行调用"是两边共同的骨架。它的好处是**日志即真相**:
不需要记任何循环状态,崩溃恢复、回放、测试都只需读日志就能推断当时为什么继续/停止。

**2. 本仓库的压缩设计恰好保住了这个判定的正确性(结构性优点)。**
本仓库压缩只发生在发送前(`prepare_messages` 返回压缩后的**副本**,磁盘日志一个字不动),
所以日志末尾永远是真的模型消息,判定永远可靠。gptme 的中途压缩会切换整个日志视图,把末尾换成摘要,
被迫加旁路状态补救——**gptme 走过的这个弯路反过来验证了本仓库"只压视图、不改日志"路线的价值**。

**3. 默认步数上限 50 比 gptme 的"默认无上限"更适合本项目。**
本仓库跑真实付费 API,模型陷入"反复调同一个工具"的死循环时,50 步上限是保险丝;
gptme 定位更信任模型加用户手动中断。上限可调,长任务不受限。

**4. 漏写提醒是本仓库独有、针对真实踩坑的补丁,gptme 缺这一课。**
markdown 工具格式下,模型"只在思考里说要调工具、正文没写代码块"时,gptme 的回合会无声结束;
本仓库提醒一次(执行过调用还会重置提醒额度),超限如实报告。代价是误报时多跑一轮生成,
而误报正则已按真机样本调过(chat.py:144-154 的注释记录了调参依据)。

**一点需要坦白的张力**:`steps` 和 `nudges` 两个计数器严格说是"额外状态",与 AGENTS.md
"不引入额外状态"的纪律字面上有出入。但它们是防烧钱、防静默失败的保险丝,且不影响判定规则本身
(每次继续与否仍只由日志末尾决定)——属于理由充分、受控的例外,不是走样。

## 四、一个前瞻提醒(非当前问题)

将来如果做"回合中途压缩",只有两条路:坚持现在的"只压发送视图"路线(判定继续可靠);
或像 gptme 那样换日志视图并引入旁路状态。看到 gptme 的补救代码后,建议**坚持前者**——
这也是 AGENTS.md 里"压缩写视图副本、不改主文件"纪律的又一处印证。

### 一眼对比

主干两边同构:**取输入 → 命令分流 → 中层"生成+工具"循环 → 靠"末条回复有没有可运行调用"决定去留 → 钩子回灌队列**。
差异集中在三处:

1. **回合怎么收尾**:本仓库多一层"漏写提醒"兜底(★),gptme 没有对应物;
   gptme 多一套"中途压缩 + 三条旁路"(★),本仓库因只压发送副本而不需要。
2. **步数保险丝**(△):本仓库默认 50 步,gptme 默认不设限。
3. **会话级出口**:gptme 有 complete 工具(模型主动结束会话)、崩溃恢复、
   外部队列文件(子代理转向)三个出口(★);本仓库只有 Ctrl-D / 非交互跑完队列退出,
   会话切换走 /resume 命令。
