# Claude Code 长期记忆（Auto Memory）架构报告

> 研究对象：本仓库（Claude Code 源码快照镜像）中的持久记忆子系统
> 报告日期：2026-10-06
> 所有结论均标注 `文件路径:行号`，基于对源码的逐行阅读

---

## 0. 一句话总结

Claude Code 的长期记忆**不是数据库，也不是向量库，而是纯 Markdown 文件目录 + 提示词协议 + 若干个后台 LLM 子代理**。核心设计决策是：复用模型已有的文件工具（Write/Edit/Read/Grep）作为记忆的读写接口，用系统提示词约定记忆格式与行为规范，用独立的 Sonnet 子代理做"相关性检索"，再由两个后台代理（extract-memories、auto-dream）在对话轮次结束后异步完成记忆的提取与整理（固化/去重/剪枝）。

## 1. 总体架构

```
                       ┌────────────────────────────────────────────┐
                       │               会话主循环                     │
                       │                                            │
  通道A 系统提示词 ◄────┤ loadMemoryPrompt()   记忆"使用手册"（无内容）│
  通道B 首条用户消息 ◄──┤ MEMORY.md 全文（默认形态，经 claudeMd 通道） │
  通道C system-reminder◄┤ findRelevantMemories() 每轮按需召回≤5条     │
                       │            （C 为 tengu_moth_copse 实验态）  │
                       │                                            │
                       │  模型用普通 Write/Edit 工具直接写记忆文件      │
                       └───────────────┬────────────────────────────┘
                                       │ 每轮结束 (stop hooks)
                        ┌──────────────┴──────────────┐
                        ▼                             ▼
             extractMemories 后台代理          autoDream 后台代理
             （从对话增量提取遗漏记忆）        （定期固化/合并/剪枝）
                        └──────────────┬──────────────┘
                                       ▼
                    ~/.claude/projects/<git-root>/memory/
                    ├── MEMORY.md        ← 索引（默认注入首条用户消息）
                    ├── user_role.md     ← 单条记忆（frontmatter+正文）
                    ├── feedback_*.md
                    ├── project_*.md
                    ├── reference_*.md
                    ├── team/            ← 团队记忆（TEAMMEM，同步）
                    └── .consolidate-lock  ← autoDream 的 mtime 锁
```

### 涉及的四个记忆子系统

| 子系统 | 目录 | 作用 |
|---|---|---|
| **Auto Memory（memdir）** | `src/memdir/` | 个人长期记忆，本报告主体 |
| **Extract Memories** | `src/services/extractMemories/` | 轮次结束后后台提取记忆 |
| **Auto Dream** | `src/services/autoDream/` | 定期记忆固化/剪枝（"做梦"） |
| **Team Memory** | `src/services/teamMemorySync/` + `src/memdir/teamMem*` | 团队共享记忆（feature flag `TEAMMEM`） |
| Session Memory | `src/services/SessionMemory/` | 会话内记忆，与长期记忆互补（见 §7） |

## 2. 存储层：文件即记忆

### 2.1 目录解析规则

核心在 `src/memdir/paths.ts`：

- 记忆目录默认为 `<配置根>/projects/<sanitized-git-root>/memory/`（`paths.ts:223-235`）
  - 配置根默认 `~/.claude`，可被 `CLAUDE_CODE_REMOTE_MEMORY_DIR` 覆盖（`paths.ts:85-90`）
  - 项目键取 **canonical git root**（`findCanonicalGitRoot`），使同一仓库的所有 worktree 共享同一份记忆（`paths.ts:198-205`，修复 anthropics/claude-code#24382）
- 覆盖优先级（`paths.ts:208-235`）：
  1. `CLAUDE_COWORK_MEMORY_PATH_OVERRIDE` 环境变量（Cowork/SDK 用）
  2. settings.json 的 `autoMemoryDirectory`（**只信 policy/local/user 三级设置**）
  3. 默认计算路径

**安全设计**（`paths.ts:95-150`）：路径校验函数 `validateMemoryPath` 拒绝相对路径、根路径、Windows 盘根、UNC 路径、空字节；`~` 展开时拒绝 `~`、`~/..` 等会展开成家目录或祖先的组合。`paths.ts:168-186` 的注释明确说明：**项目级 settings（.claude/settings.json，随仓库提交）被故意排除在覆盖来源之外**——否则恶意仓库可以设 `autoMemoryDirectory: "~/.ssh"`，借 filesystem.ts 的写入豁免静默获得对敏感目录的写权限。

### 2.2 开关链（`paths.ts:30-55`）

`isAutoMemoryEnabled()` 按顺序判定：`CLAUDE_CODE_DISABLE_AUTO_MEMORY` 环境变量 → `--bare`/SIMPLE 模式关闭 → 远程模式无持久存储关闭 → settings.json `autoMemoryEnabled` → 默认开启。

### 2.3 记忆文件格式

单条记忆 = 一个 `.md` 文件，带 frontmatter（`src/memdir/memoryTypes.ts:261-271`）：

```markdown
---
name: <短横线命名的一句主题>
description: <一行描述——未来对话靠它判断相关性，必须具体>
type: user | feedback | project | reference
---

<正文；feedback/project 类型要求结构为：规则/事实 + **Why:** + **How to apply:**>
```

### 2.4 四类记忆的封闭类型学（`memoryTypes.ts:14-19`）

只允许四种类型，且**显式排除一切可从项目现状推导的内容**：

| 类型 | 内容 | 保存时机 |
|---|---|---|
| `user` | 用户角色、目标、知识背景 | 了解到用户身份/偏好/职责的任何细节时 |
| `feedback` | 用户对工作方式的纠正**和确认** | 用户纠正（"不要 X"）**或**验证了非常规做法（"对，就这样"） |
| `project` | 进行中的工作、决策及其动机（不可从代码/git 推导） | 了解到 who/why/when 时；相对日期必须转绝对日期 |
| `reference` | 外部系统指针（Linear、Grafana、Slack） | 了解到外部资源及其用途时 |

两个值得注意的提示词工程细节：

- **"从成功中学习"**（`memoryTypes.ts:134-137`）：`when_to_save` 明确要求同时记录纠正与确认——"只记纠正会让模型避开过去的错误，但也会偏离已被验证的做法，变得过度保守"。
- **显式保存也有门槛**（`memoryTypes.ts:192-194`）：即使用户明确要求保存，排除规则依然生效。用户让存"本周 PR 列表"时，模型应反问"哪部分是*意外的/非显然的*"——该段注释标明这是经过 eval 验证的（0/2 → 3/3）。

### 2.5 排除清单（`memoryTypes.ts:183-195`）

不保存：代码模式/架构/文件路径（可读现状推导）、git 历史（`git log` 权威）、调试解法（修复在代码里）、CLAUDE.md 已有内容、临时任务状态。

### 2.6 MEMORY.md 索引与硬上限

- `MEMORY.md` 是**索引不是记忆**：每条一行 `- [Title](file.md) — one-line hook`，~150 字符，无 frontmatter，**绝不直接写记忆内容**（`memdir.ts:227`）
- **索引的维护是"由 LLM 用 Edit 重写"，没有任何代码层的 append 逻辑**——提示词要求模型在保存的第二步自己增删改索引行；harness 只在读取端做约束（截断+WARNING）
- 双重上限：**200 行** 且 **25KB**（`memdir.ts:34-38`），超限由 `truncateEntrypointContent`（`memdir.ts:57-103`）先按行截断再按字节截断，并在末尾追加指明哪个上限触发的 WARNING，要求把细节移入主题文件
- 字节上限的注释（`memdir.ts:36-38`）说明动机：实测 p100 出现过 200 行内塞 197KB 的长行索引

## 3. 写入路径：没有专门的"记忆工具"

这是整个设计中最反直觉的一点：**模型写记忆用的是普通的 FileWriteTool/FileEditTool**，没有任何 memory-specific 工具。系统提示词（`memdir.ts:199-266` buildMemoryLines）负责教会模型两步流程：先写记忆文件，再在 MEMORY.md 加一行指针。

配套的工程保障：

1. **目录必然存在**：`ensureMemoryDirExists()`（`memdir.ts:129-147`）在每次会话构建提示词时递归 mkdir（吞 EEXIST）。提示词里明确写"目录已存在，直接用 Write 写，不要 mkdir/检查"（`memdir.ts:116-119`）——注释说明这是因为模型曾浪费轮次跑 `ls`/`mkdir -p`。
2. **权限豁免**：默认记忆目录在 `~/.claude/` 下，属于 DANGEROUS_DIRECTORIES，正常写操作会弹权限确认。`src/utils/permissions/filesystem.ts:1572-1581` 为此做了**预安全检查豁免**：路径命中 `isAutoMemPath()` 的写操作直接放行（理由："auto memory files are allowed for writing"）。读豁免在 `filesystem.ts:1716-1723`。注意：Cowork 的 env 覆盖路径**不享受**写豁免（`hasAutoMemPathOverride()` 为 true 时跳过），因为那是调用方任意指定的目录。
3. **零信任边界**：`isAutoMemPath()`（`paths.ts:274-278`）先 normalize 再前缀匹配，防 `..` 穿越。

### 3.1 后台提取代理（extract-memories）

主代理忙于干活时可能忘记存记忆。`src/services/extractMemories/` 实现了一个**每个 query loop 结束时 fire-and-forget 的后台子代理**（触发点是"模型产出不带 tool call 的最终响应"，即 `handleStopHooks`，不是会话结束——`src/query.ts:1267`、`extractMemories.ts:4-6` 头注释）。

**门控与节流**：

- stopHooks 门（`stopHooks.ts:136-152`）：非 bare 模式、`feature('EXTRACT_MEMORIES')`、仅主线程（`!toolUseContext.agentId`）、`isExtractModeActive()`（GrowthBook `tengu_passport_quail`，非交互还需 `tengu_slate_thimble`，`paths.ts:69-77`）
- 节流：`tengu_bramble_lintel` 控制每 N 个合格 turn 跑一次（默认 1，`extractMemories.ts:374-386`）
- **游标机制**：`lastMemoryMessageUuid` 游标保证每段消息只被提取一次；出错时游标不推进，下轮重试同一区间（`extractMemories.ts:429-435`）
- **与主代理互斥**：`hasMemoryWritesSince`（`extractMemories.ts:112-148`）检查游标之后是否有 assistant 的 Edit/Write 指向记忆目录——主代理本轮已写过就跳过 fork、直接推游标；两者按轮互斥，不会重复处理
- **并发合并**：提取进行中又来新轮次 → stash 到 `pendingContext`，当前跑完后做一次 trailing run（`extractMemories.ts:503-564`）
- headless（-p/SDK）：print.ts 在响应 flush 后、gracefulShutdownSync 前 `await drainPendingExtraction()`（软超时 60s），防止 shutdown failsafe 杀掉 fork（`src/cli/print.ts:966-970`、`extractMemories.ts:579-586`）

**fork 机制（"完美 fork"，缓存共享是核心）**：`runForkedAgent` 让子代理看到主对话的**全部消息** + 一条提取指令作为最后的 user message；system prompt、工具、模型、thinking 配置全部与主请求一致以**命中 prompt cache**（`forkedAgent.ts:46-141` 的 CacheSafeParams；`extractMemories.ts:372-427`）。参数：`maxTurns: 5`（正常 2-4 轮：读→写），`skipTranscript: true`（不写 sidechain 转录，避免与主线程竞态），不单独指定 model——继承主对话参数。

**提取 prompt 要点**（`extractMemories/prompts.ts:29-44`）：

- 开场："You are now acting as the memory extraction subagent. Analyze the most recent ~N messages above and use them to update your persistent memory systems."
- **效率纪律**："turn 1 — issue all Read calls in parallel for every file you might update; turn 2 — issue all Write/Edit calls in parallel. Do not interleave reads and writes across multiple turns."（两轮并行就是为 update-before-create 服务）
- **禁止验证**："Do not waste any turns attempting to investigate or verify that content further — no grepping source files, no reading code to confirm a pattern exists, no git commands."
- 提取前预注入现有记忆 manifest（文件名/type/mtime/description 清单，复用 `scanMemoryFiles`），省掉 ls 的一轮，并附 "Check this list before writing — update an existing file rather than creating a duplicate."（`extractMemories.ts:396-400`、`prompts.ts:30-33`）

**权限闸**（`createAutoMemCanUseTool`，`extractMemories.ts:171-222`）：Read/Grep/Glob 无限制；Bash 仅 `tool.isReadOnly` 通过的命令；Edit/Write 仅 `isAutoMemPath()` 内；其余 deny + 打点。**落地无专门管道**：子代理自己调 FileWriteTool/FileEditTool 写盘；主线程事后从其 assistant 消息的 tool_use 块收集 `file_path`（`extractWrittenPaths`，`extractMemories.ts:251-269`），排除 MEMORY.md 后有主题文件就向用户展示 memory_saved 系统消息（`extractMemories.ts:490-496`）。

**去重的真相**：没有程序化的相似度判断——去重 = prompt 软约束（manifest 注入 + update-before-create 指令）+ 游标/互斥硬机制（防重复处理，而非重复内容）。跨层的去重（auto-memory vs CLAUDE.md）由 remember skill 的人工审批处理（见 §3.4）。

（提取 prompt 与落地细节见 §3.1 补充，来自子研究报告 A）

### 3.2 记忆固化代理（auto-dream/"做梦"）

`src/services/autoDream/` 实现了**定期记忆整理**——合并重复、修正漂移、剪枝索引。名字取"睡眠巩固"（memory consolidation）之意。

**三重门控，最廉价的先检查**（`autoDream.ts:4-8`）：

1. **时间门**：距上次整理 ≥ `minHours`（默认 24h，GrowthBook `tengu_onyx_plover` 可调，`autoDream.ts:63-93`）。上次整理时间 = 锁文件的 **mtime**（一个文件当两个状态用，`consolidationLock.ts:26-36`）
2. **会话门**：自上次整理以来有 ≥ `minSessions`（默认 5）个会话转录被动过（`autoDream.ts:153-171`）；会话扫描有 10 分钟节流（`autoDream.ts:56`），防止时间门通过但会话门不过时每轮空转
3. **锁门**：`tryAcquireConsolidationLock()`（`consolidationLock.ts:46-84`）——写 PID 抢锁，回读验证防止两个抢锁者竞争（"last wins, loser bails"）；锁超过 1 小时且 PID 已死则视为崩溃残留可回收；失败时 `rollbackConsolidationLock` 把 mtime 回滚让下次重试

**执行**（`autoDream.ts:210-233`）：通过 `runForkedAgent` fork 一个子代理跑 `buildConsolidationPrompt` 生成的四阶段提示词（`consolidationPrompt.ts:15-64`）：

- **Phase 1 Orient**：ls 记忆目录、读 MEMORY.md、浏览既有主题文件避免重复创建
- **Phase 2 Gather**：按优先级收集信号——① 日志流（KAIROS 模式的 `logs/YYYY/MM/DD.md`）② 与代码库现状矛盾的漂移记忆 ③ 必要时窄 grep 会话转录 JSONL（明确禁止通读）
- **Phase 3 Consolidate**：合并进既有主题文件而非新建近似重复；相对日期转绝对日期；**删除被证伪的记忆**（"今天的调查推翻了旧记忆时，在源头修正"）
- **Phase 4 Prune and index**：MEMORY.md 保持 ≤200 行且 ≤25KB，删失效指针、超长行降级、解决文件间矛盾

**安全约束**：dream 代理的 Bash 被限制为只读命令（ls/find/grep/cat/stat/wc/head/tail），写操作只能走 Edit/Write 工具（`autoDream.ts:216-218` 的 extra 注入 + `createAutoMemCanUseTool`，复用自 extractMemories）。

**UI 可见性**：`src/tasks/DreamTask/DreamTask.ts` 把这个后台 fork 注册为任务，显示在底部状态条和 Shift+Down 对话框；kill 时回滚锁 mtime（`DreamTask.ts:136-157`）。

### 3.3 整体编排

`src/utils/backgroundHousekeeping.ts:31-37` 在启动时注册全部后台机制：`initMagicDocs`、`initSkillImprovement`、`initExtractMemories`（feature 门控）、`initAutoDream`。autoDream 的每轮成本被优化到"一次 GB 缓存读 + 一次 stat"（`autoDream.ts:315-318`）。

### 3.4 人工干预入口

- **remember skill**（`src/skills/bundled/remember.ts`）：仅 Anthropic 内部用户注册（`USER_TYPE !== 'ant'` 直接 return）。它是**只读的"记忆体检/晋升"顾问，本身不写任何文件**：收集全部记忆层（CLAUDE.md、CLAUDE.local.md、auto-memory），把每条 auto-memory 分类为"应晋升到 CLAUDE.md（项目约定）/ CLAUDE.local.md（个人偏好）/ team memory / 留在 auto-memory"，扫描跨层重复/过时/冲突，输出四组提案（Promotions/Cleanup/Ambiguous/No-action）。硬规则："Present ALL proposals before making any changes. Do NOT modify files without explicit user approval"（`remember.ts:57-61`）
- **/memory 命令**（`src/commands/memory/`）：纯 UI 编辑入口。`MemoryFileSelector` 列出各层记忆文件（不存在的也显示 "(new)"），选中后用 $VISUAL/$EDITOR 打开外部编辑器（`memory.tsx:21-63`）；auto-memory 开启时另有 "Open auto-memory folder" 选项。命令本身不触及 auto-memory 语义
- **memoryFileDetection**（`src/utils/memoryFileDetection.ts`）：路径→记忆类别分类函数集，服务于遥测（`tengu_memdir_accessed/read/edit/write`）、UI 折叠（Read/Grep 组折叠加 memory 标识）、FileReadTool 的新鲜度渲染（读记忆文件时把 mtime 存 WeakMap，`FileReadTool.ts:747-758,1056`）、记忆使用问卷触发。不参与写入决策

**注意两套"类型"体系是不同层级**：`src/utils/memory/types.ts` 的 `User/Project/Local/Managed/AutoMem/TeamMem` 是 **CLAUDE.md 指令文件体系**的文件类型枚举（User → ~/.claude/CLAUDE.md、Project → ./CLAUDE.md 等，`config.ts:1779-1799`；compact 压缩时用它识别并保护记忆文件，`compact.ts:1691-1702`）；而 memdir 的 `user/feedback/project/reference` 是**记忆内容**的四分类。

## 4. 读取路径（召回）：三条注入通道

记忆进上下文有**三条独立通道**，理解这一点是理解整个系统的关键：

### 4.1 通道 A：系统提示词的"使用手册"段（只有协议，无内容）

`getSystemPrompt()` 把 memory 段注册为缓存型动态 section（`systemPromptSection('memory', () => loadMemoryPrompt())`，`src/constants/prompts.ts:495`），位于动态区第二段（静态段 → session_guidance → **memory** → …，`prompts.ts:560-576`）。该 section 计算一次后缓存，直到 /clear 或 /compact 才重建（`src/constants/systemPromptSections.ts:14-20`）。

`loadMemoryPrompt()`（`memdir.ts:419-507`）按 feature 分派：

- KAIROS 助理模式（常驻会话）→ 每日追加日志模式（`buildAssistantDailyLogPrompt`，`memdir.ts:327-370`）：记忆改为 append-only 到 `logs/YYYY/MM/YYYY-MM-DD.md`，MEMORY.md 变成夜间 dream 蒸馏出的只读索引。这个模式下提示词描述的是**路径模式**而非当日字面路径，以保持提示词缓存前缀跨午夜有效（`memdir.ts:330-335` 注释专门解释了这个缓存考量）
- TEAMMEM + 团队记忆启用 → 组合提示词（个人+团队双目录）
- 默认 → 个人记忆提示词（`buildMemoryLines`）

**关键**：主线程的这个段落**不含 MEMORY.md 内容**——`buildMemoryLines` 只输出行为指令（`memdir.ts:196-197` 注释明说内容走用户上下文通道）。

### 4.2 通道 B：MEMORY.md 全文进首条用户消息（默认形态）

`getUserContext()`（`src/context.ts:155-189`）调 `getMemoryFiles()`（`src/utils/claudemd.ts:790`）——按 CLAUDE.md 层级扫描（Managed/User/Project/Local）之后，**额外读 auto-memory 的 MEMORY.md**（`safelyReadMemoryFileAsync(getAutoMemEntrypoint(), 'AutoMem')`，`claudemd.ts:979-992`；TEAMMEM 再读 team 入口，`claudemd.ts:994-1007`）。剥 frontmatter/HTML 注释、按 200 行/25KB 截断后，整份作为 `claudeMd` 字段注入。

**确切插入位置**：消息数组**首条 isMeta user 消息**（`prependUserContext`，`src/utils/api.ts:449-474`），格式：

```
<system-reminder>
As you answer the user's questions, you can use the following context:
# claudeMd
Codebase and user instructions are shown below. ...
Contents of ~/.claude/projects/<slug>/memory/MEMORY.md (user's auto-memory, persists across conversations):
{截断后的 MEMORY.md 全文}
# currentDate
Today's date is {date}.
...
</system-reminder>
```

（TeamMem 类型则包 `<team-memory-content source="shared">` 标签，`claudemd.ts:1180-1183`。）注意 **MEMORY.md 是进首条用户消息，不是 system prompt 本体**——这样它天然位于提示词缓存前缀内且可随会话刷新。REPL 启动时还会把所有记忆文件预写入 `readFileState`，磁盘内容与注入内容（截断过）不一致时缓存原始字节并标 `isPartialView`（`src/screens/REPL.tsx:3798-3818`）。

### 4.3 通道 C：按需召回（`tengu_moth_copse` 实验形态）

GrowthBook `tengu_moth_copse` 开启时切换到**完全不同的召回形态**：`filterInjectedMemoryFiles` 把 `AutoMem`/`TeamMem` 从注入列表剔除（`claudemd.ts:1142-1151`）——**MEMORY.md 索引不再进上下文**，改为每用户轮一次的按需 prefetch：

1. `query()` 每轮入口 `startRelevantMemoryPrefetch(...)`（`src/query.ts:301`）——**旁路 Sonnet 调用，绝不阻塞主轮**；消费点在工具结果之后（`query.ts:1599-1614`），未 settle 则零等待下轮重试
2. 前置门槛：auto memory 开启 且 `tengu_moth_copse` 开启（`attachments.ts:2365-2370`）；**单词 prompt（无空白）直接跳过**（`attachments.ts:2372-2381`）；会话累计注入字节 ≥ 60KB 也跳过（`RELEVANT_MEMORIES_CONFIG.MAX_SESSION_BYTES`，`attachments.ts:279-289`）
3. 单文件注入上限 200 行 / 4096 字节，截断时提示模型用 Read 工具看全文（`attachments.ts:269-277, 2302-2307`）
4. 每条记忆渲染为一条 isMeta user 消息，包 `<system-reminder>`，header 格式：新鲜（≤1 天）`Memory (saved today): {path}:`，否则前置过期警示（`src/utils/messages.ts:3708-3721`、`attachments.ts:2327-2332`）。**header 在创建时一次性算好**——避免跨轮 "3 days ago"→"4 days ago" 的字节变化打爆 prompt cache（`attachments.ts:505-513`）
5. 提取 prompt 同步去掉"第二步维护索引"（skipIndex，`extractMemories.ts:366-369`）——这是"索引常驻"vs"全按需召回"两种上下文策略的 A/B 实验

### 4.4 相关性检索算法：两段式，无向量库

`findRelevantMemories.ts:39-75` 是通道 C 的检索核心。**没有 embedding、没有向量库、没有打分公式**：

1. **扫描**（`memoryScan.ts:35-77`）：递归 readdir，过滤 `.md` 且**排除 MEMORY.md**，每个文件只读**前 30 行**（frontmatter 上限）提取 `description`/`type`，按 mtime 新→旧排序截断 200 个。单遍设计（读时顺手拿 mtime）省一半 syscall
2. **LLM 选择**（`findRelevantMemories.ts:77-141`）：manifest（`- [type] filename (ISO时间): description`）连同用户 query 发给 **Sonnet 旁路调用**（`sideQuery`，不带 CC 系统提示前缀，max_tokens=256，JSON schema 强约束输出，**最多选 5 个**）。系统提示词要求"不确定就不选"、"没有合适的就返回空"；并处理了一个精妙负例：**最近成功用过的工具的参考文档不要召回**（对话里已有活用法），但那些工具的坑/警告**要**召回（`findRelevantMemories.ts:23` + `attachments.ts:2465+` 的 `collectRecentSuccessfulTools`，防"query 含 spawn + 描述含 spawn"的关键词假阳性）
3. **时间因素**：无时间衰减打分；时间只体现在 mtime 排序截断、manifest 时间戳、注入时的"X days old"警示三处
4. **防重复**：`alreadySurfaced` 集合在选择前就过滤已展示文件，"让选择器把 5 个名额花在新候选上"（`findRelevantMemories.ts:35-38`）

**没有 embedding 这件事解释了 frontmatter `description` 为何被提示词强调"用于未来对话判断相关性，必须具体"（`memoryTypes.ts:265`）——它就是这个"向量"的替代品。**

### 4.5 新鲜度标注（防陈旧记忆污染）

`src/memdir/memoryAge.ts` 实现 mtime 驱动的陈旧度提示：

- `memoryAge()`（`memoryAge.ts:15-20`）：把时间戳转成 "today / yesterday / N days ago"——注释直言"模型不擅长日期算术，裸 ISO 时间戳引不起陈旧感推理"
- `memoryFreshnessText()`（`memoryAge.ts:33-42`）：>1 天的记忆附加警告"这是时点观察不是实时状态，file:line 引用可能过时，断言前先对照当前代码验证"。动机注释（`memoryAge.ts:27-32`）：用户报告过陈旧的代码状态记忆被当作事实断言——引用反而让错误主张显得更权威
- 提示词侧还有配套的行为协议：`MEMORY_DRIFT_CAVEAT`（`memoryTypes.ts:201-202`）和整个 "## Before recommending from memory" 章节（`memoryTypes.ts:240-256`）——"记忆说 X 存在"≠"X 现在存在"，推荐前：文件路径查存在性、函数/flag 去 grep、用户要动手前先验证。该章节注释记录了 eval 迭代过程（0/2 → 3/3，且标题措辞"Before recommending"比"Trusting what you recall"有效——位置和行动线索都重要）

### 4.6 兜底层：grep 过往上下文

GrowthBook `tengu_coral_fern` 启用时（`memdir.ts:375-407`），提示词追加"Searching past context"章节，教模型两步兜底：先 grep 记忆目录，最后手段才 grep 会话转录 JSONL（"大文件、慢"），并用窄搜索词。同一节还针对 Ant 内部构建（grep 被 alias 成内嵌 ugrep、无独立 Grep 工具）和 REPL 模式给出对应的 shell 形式。

### 4.7 上下文压缩时的记忆处理

**压缩不"固化"记忆，也没有记忆专属的摘要指令——记忆靠压缩后重注入存活**：

- 压缩摘要 prompt 的 9 个必需小节里没有任何记忆条目；`relevant_memories` 附件会作为普通消息参与摘要，之后随旧消息一起丢弃
- 真正的恢复机制在 `postCompactCleanup.ts:46-70`：主线程压缩时清 `getUserContext` 缓存 + `resetGetMemoryFilesCache('compact')` → MEMORY.md 重新读盘注入；`clearSystemPromptSections()` → memory 系统提示段重建。子代理压缩（querySource `agent:*`）刻意**不**清这些缓存，防止污染同进程主线程状态（`postCompactCleanup.ts:33-44`）
- 通道 C 的会话级 60KB 配额天然随压缩重置——旧附件从转录中消失，"re-surfacing is valid again"（`attachments.ts:2244-2266`）；即压缩后同一条记忆允许再次召回

### 4.8 子代理的记忆：继承与专属

**继承（主 auto-memory）**：

- 子代理 query 用与主线程相同的 `getUserContext()`（含 MEMORY.md 所在 claudeMd，`src/tools/AgentTool/runAgent.ts:380-398`）；但 **Explore/Plan 等标 `omitClaudeMd` 的只读代理会剥掉 claudeMd**（flag `tengu_slim_subagent_claudemd` 默认 true，注释：省 5-15 Gtok/周，`runAgent.ts:385-398`）
- 子代理跑同一个 `query()` 循环，因此同样能触发通道 C 的 memory prefetch（`query.ts:301` 无 agentId 门控）
- extract/autoDream 后台代理是完美 fork，完整继承主上下文（§3.1/§3.2）

**专属记忆（agent memory，按 agentType 隔离）**——自定义代理可声明自己的记忆目录（`src/tools/AgentTool/agentMemory.ts`）：

- 三档 scope（`agentMemory.ts:13, 52-65`）：user `<memoryBase>/agent-memory/<agentType>/`、project `<cwd>/.claude/agent-memory/<agentType>/`、local `<cwd>/.claude/agent-memory-local/<agentType>/`；每个目录有自己的 MEMORY.md
- 代理定义的 frontmatter 写 `memory: user|project|local`，加载时把代理系统提示包成 `systemPrompt + loadAgentMemoryPrompt(agentType, memory)`（`loadAgentsDir.ts:726-732`；插件代理同 `loadPluginAgents.ts:207`）
- 这是**唯一把 MEMORY.md 内容放进 system prompt 的形态**（`buildMemoryPrompt`，`memdir.ts:272-316`，含全文 + scope 提示）
- **快照播种**（`agentMemorySnapshot.ts`）：项目可带 `.claude/agent-memory-snapshots/<agentType>/`（随 VCS 提交）；成员本地无记忆 → 全量拷贝初始化（:149-159）；快照比本地 `.snapshot-synced.json` 新 → 提示更新（:164-186）——团队通过仓库给新成员的代理记忆做种子，类似 npm 包的 seed 数据
- 主线程 `@agent-xxx` 提及时，通道 C 的 recall 只搜该代理的记忆目录（`attachments.ts:2204-2213`）

### 4.9 token 用量统计与展示

一个容易踩的坑：`useMemoryUsage` / `MemoryUsageIndicator` **与记忆系统无关**——它们监控的是 Node 进程堆内存（`process.memoryUsage().heapUsed`，10 秒轮询，≥1.5GB 告警，仅 ant 内部构建显示）。长期记忆的 token 统计在：

- 超限告警：单文件 > 40000 字符进 `getLargeMemoryFiles`（`claudemd.ts:1132-1134`），status/doctor 提醒（`status.tsx:117`、`doctorContextWarnings.ts:44`）
- 遥测：`tengu_memdir_loaded`（文件数/内容长度/是否截断）、`tengu_memdir_prefetch_collected`、`tengu_agent_memory_loaded`、`tengu_extract_memories_*` 等

## 6. 团队记忆（TEAMMEM，feature-gated）

团队记忆是按 **GitHub 仓库**划分、经服务端 API 在组织成员间共享的记忆文件系统。本地落在个人记忆目录的 `team/` 子目录（`join(getAutoMemPath(), 'team')`，`memdir.ts:452-458` 注释），入口同样是 `MEMORY.md`（`teamMemPaths.ts:84-94`）。

**启用条件**：auto memory 开启 + GrowthBook `tengu_herring_clock`（`teamMemPaths.ts:73-78`）+ build flag `feature('TEAMMEM')`（`watcher.ts:253`）+ 第一方 OAuth（含 inference+profile scope，`teamMemorySync/index.ts:151-161`）+ 存在 github.com remote（`watcher.ts:259-266`）。

**关键设计：本地目录按 sanitized 项目根划定，但远端同步按 GitHub repo slug（owner/name）划定**（`src/utils/git.ts:504-521` 的 `getGithubRepo()`）。

### 6.1 提示词层的双目录协议

系统提示词切到 COMBINED 模式（`memoryTypes.ts:37-106` + `teamMemPrompts.ts:63-86`），四类记忆各带 scope 规则：

| 类型 | scope |
|---|---|
| `user` | always private |
| `feedback` | 默认 private，仅当是明确的项目级约定（如测试策略）才入 team |
| `project` | private 或 team 皆可，**强烈偏向 team** |
| `reference` | usually team |

并有敏感数据红线："You MUST avoid saving sensitive data within shared team memories. For example, never save API keys or user credentials."（`teamMemPrompts.ts:78`）。

### 6.2 同步机制（`src/services/teamMemorySync/index.ts`）

API 契约：`{BASE_API_URL}/api/claude_code/team_memory?repo={owner/name}`（`index.ts:8-12,163-167`）；GET 全量 / GET `?view=hashes`（仅校验和）/ PUT（upsert 语义，不带 key 不删）。常量：超时 30s、单文件 250KB、PUT body 200KB、网络重试 3 次、冲突重试 2 次；内容哈希 `sha256:<hex>`（`index.ts:71-136`）。

- **Pull（会话开始）：server 赢（per-key）**——带 `If-None-Match` 条件请求，304 短路；写盘前每条 entry 过 `validateTeamMemKey` 防路径注入、超 250KB 跳过、内容一致跳写保 mtime（避免触发 watcher，`index.ts:689-867`）
- **Push（本地变更后）：local 赢**——读本地全部文件（含密钥扫描）→ 只上传本地哈希 ≠ serverChecksums 的 key（delta）→ 按字母序贪心装箱成 ≤200KB 的多个 PUT（排序保证 ETag 链重试的确定性）→ PUT 带 `If-Match: <ETag>`，412 冲突时 `GET ?view=hashes` 轻量探测刷新校验和再重算 delta，最多 2 次；**不做内容级 merge**——注释明说取舍：本地用户正在编辑、可重新吸收队友改动，静默丢弃本地编辑无救济（`index.ts:874-1146`）
- **删除不传播**：删本地文件不会从服务端删除，下次 pull 会还原（`index.ts:17-19`）
- **结构化 413**：服务端返回 `team_memory_too_many_entries` 时客户端缓存 `serverMaxEntries`，下次 push 前按字母序确定性截断（`index.ts:529-671,1046-1059`）

**Watcher**（`watcher.ts`）：启动时先做 initial pull 再开监听（避免自己的写盘触发 push）；`fs.watch(recursive)` 而非 chokidar（Bun 下 kqueue 每文件一个 fd 的老问题）；任何事件 2 秒 debounce 后 push（`watcher.ts:35,132-145`）；另有 PostToolUse 钩子在 Write/Edit 命中团队文件时显式通知，防 fs.watch 丢事件（`sessionFileAccessHooks.ts:199-206`）。**失败抑制**：永久性失败（无 OAuth/无 repo/4xx）设 `pushSuppressedReason` 停止重试——注释记录了真实事故：一台无 OAuth 的机器因共享目录里其他会话的写事件，2.5 天打出 16.7 万次 push（`watcher.ts:45-117`）。

### 6.3 密钥防泄漏（secretScanner，PSR M22174）

目标："secrets never leave the user's machine"——只选 gitleaks 中带独特前缀、近零误报的 30 条规则（AWS/GCP/Azure/Anthropic/OpenAI/GitHub/GitLab/Slack/Stripe/PEM 私钥等，`secretScanner.ts:48-224`）。Anthropic 自家 key 的前缀是**运行时拼装**的（`['sk','ant','api'].join('-')`），避免字节序列出现在外发 bundle 里（`secretScanner.ts:44-46`）。`scanForSecrets` 只返回规则 ID 不返回匹配文本（永不记录密钥值）；analytics 打点只记 gitleaks rule ID——"not values, not paths — paths could leak repo structure"（`index.ts:924-945`）。

**两处拦截**：
1. 上传前：命中规则的文件整个跳过不上传，警告列出文件名+类型标签（`index.ts:596-615`）
2. 写入前：FileWriteTool/FileEditTool 的 validateInput 里，路径在 team 目录且扫出密钥时**直接拒绝写入**（`FileWriteTool.ts:157`、`FileEditTool.ts:144`、`teamMemSecretGuard.ts:15-44`）

### 6.4 路径安全（防恶意服务端与本地穿越）

`sanitizePathKey` 拒绝 null 字节、URL 编码穿越（`%2e%2e%2f`）、NFKC Unicode 归一化穿越（全width `．．／`）、反斜杠、绝对路径（`teamMemPaths.ts:22-64`）；写盘前 resolve + 前缀包含检查 + 对最深存在祖先做 `realpath` 比对——防 symlink 逃逸（PSR M22186），悬空 symlink/ELOOP/EACCES 一律 fail-closed（`teamMemPaths.ts:97-206`）。

## 7. 会话记忆（SessionMemory）：第三种记忆

除长期记忆外，还有一个常被混淆的子系统：**SessionMemory**（`src/services/SessionMemory/`）。它是"每个会话一份的单文件笔记"，服务于**上下文压缩**：

- **存储**：`~/.claude/projects/{sanitized-cwd}/{sessionId}/session-memory/summary.md`，目录 0o700、文件 0o600（`sessionMemory.ts:189-212`）——按会话 ID 隔离，与会话转录同级
- **维护者**：专用 fork 子代理，`canUseTool` 白名单**只允许对 summary.md 用 Edit**，其余一律 deny（`sessionMemory.ts:460-482`）
- **模板**：固定 10 个 section（Session Title / Current State / Task specification / Files and Functions / Workflow / Errors & Corrections / Codebase Documentation / Learnings / Key results / Worklog，`prompts.ts:11-41`），可被 `~/.claude/session-memory/config/` 覆盖
- **触发**：post-sampling hook，仅主 REPL 线程；初始门≥10000 token，更新门 = token 增长≥5000 且 tool call≥3（或自然对话间隙），**token 阈值永远必要**（`sessionMemory.ts:134-181`；`sessionMemoryUtils.ts:32-36`）
- **自压缩**：不删文件，靠 prompt 强制整理——全文超 12000 tokens 时追加 "You MUST condense the file… Prioritize keeping 'Current State' and 'Errors & Corrections'"，每 section 上限 ~2000 tokens（`prompts.ts:168-196`）
- **压缩集成（SM-compact）**：autoCompact 可走 session memory 路线替代传统 compact API——从 lastSummarizedMessageId 起向前保留近期消息（保住 tool_use/tool_result 配对与 thinking 块的 API 不变量），其余上下文用 summary.md 截断后的内容替代；三个回退点（文件不存在/内容仍为模板/定位失败）都退回传统 compact（`sessionMemoryCompact.ts:514-630`）

### 三种记忆的对照

| 维度 | Auto Memory（memdir） | Team Memory | Session Memory |
|---|---|---|---|
| 生命周期 | 跨会话永久 | 跨会话+跨成员 | 单会话 |
| 存储 | `memory/` 多文件+索引 | `memory/team/` | `{sessionId}/summary.md` 单文件 |
| 注入 | MEMORY.md 常驻系统提示 | 同左 | 仅压缩时作为摘要 |
| 写者 | 主代理+extract 后台代理 | 同左+同步服务 | 专用 fork 子代理（Edit-only） |
| 同步 | 无 | 服务端 per-repo | 无 |

## 8. 与其他持久化机制的边界

系统提示词明确划界（`memdir.ts:254-257`）：

- **记忆 vs Plan**：非平凡实现前对齐方案 → 用 Plan；方案在会话内变更 → 更新 Plan 而非存记忆
- **记忆 vs Tasks**：当前会话内的步骤分解/进度 → Tasks；记忆只留给跨会话有用的信息
- **记忆 vs CLAUDE.md**：已在 CLAUDE.md 里的内容不重复保存（`memoryTypes.ts:189`）
- **记忆 vs Session Memory**：长期记忆留给跨会话有用的信息；会话内的进展快照归 SessionMemory（它本质是压缩摘要的持久化形态，见 §7）

## 9. 设计洞察与评价

### 9.1 值得借鉴的决策

1. **文件即记忆（Files-as-memory）**：零新增工具、零新存储引擎，用户可以直接用编辑器查看/修改/删除自己的记忆，可调试性极强；代价是结构化程度低，靠提示词协议维持格式
2. **上下文经济**：默认形态常驻的只有首条用户消息里的 ≤200 行索引；实验形态（moth_copse）连索引都不注入，正文每轮由廉价 Sonnet 从"文件名+描述"清单筛选 ≤5 条、会话级 60KB 配额。把"上下文预算"当作一等约束，且在两种策略间做受控 A/B
3. **写路径三通道冗余**：主代理即时写（提示词驱动）→ 轮末后台补漏（extractMemories）→ 定期固化整理（autoDream）。职责在注释里写得很清楚：主代理写了，后台就跳过
4. **防陈旧是读侧一等公民**：不只是存时小心，读时强制标注新鲜度 + "推荐前验证"行为协议，且都经过 eval 迭代验证（注释里保留了 0/2→3/3 的实验记录）
5. **用 mtime 当持久化时钟**：锁文件 mtime=上次整理时间，会话 mtime=活跃度信号，避免额外的状态文件
6. **提示词缓存意识**：KAIROS 模式宁可让模型自己从上下文推日期也不在提示词里内联当日路径，只为保住跨午夜的缓存前缀；extract 的"完美 fork"同参继承更是把缓存共享当作设计前提（fork 的经济学：全量对话前缀几乎全部缓存命中，只有提取指令是新 token）
7. **防重复处理靠硬机制，防重复内容靠软约束**：游标（lastMemoryMessageUuid）+ 主代理互斥（hasMemoryWritesSince）+ 进程锁（consolidate-lock）都是代码保证；而"别写重复记忆"只能靠 manifest 注入 + prompt 指令——诚实地承认了内容级去重没有可靠程序化方案

### 9.2 已知的局限（源码注释自证）

- 相关性检索是"LLM 看文件名+描述"，描述写得差就召不回（`memoryTypes.ts:265` 只能用提示词求"be specific"）；且通道 C 的按需召回整个还压在 `tengu_moth_copse` 实验开关后面，默认形态下模型主要靠常驻索引自己决定何时 Read
- 单目录 200 文件 / 索引 200 行的硬上限在记忆规模大时成为瓶颈，依赖 dream 的剪枝维持
- `TRUSTING_RECALL_SECTION` 注释承认已知缺口：H1 规则不覆盖斜杠命令类主张（0/3）
- dream 的 filesTouched 只统计 Edit/Write 工具调用，bash 介导的写入不可见（`DreamTask.ts:28-35`）
- 压缩对记忆内容零特殊处理：`relevant_memories` 附件是否进摘要全凭摘要模型自由发挥，可能丢失当轮已召回的记忆细节（靠压缩后重注入弥补索引，但不弥补正文）
