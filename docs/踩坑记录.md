## 1. kimi 把围栏粘在 `</think>` 后面,工具调用静默消失(2026-10-04,已修复)

**环境**:真实会话,模型 `dashscope/kimi-k3`,markdown 工具通道,websearch MCP 工具。

**现象**:连续三次工具调用(`fetchWebContent` ×2、`search` ×1)全部没有任何结果——
日志里 assistant 消息后面直接是下一条用户输入;不报错、不中断、终端无任何提示。
模型下一轮的思考里自己都说 "no system tool output shown"。

**排查**:
1. 日志里无结果、无报错、无中断标记 → 排除执行出错;
2. 唯一"什么都不写就结束回合"的路径是 `chat.py` 的
   `has_runnable_tooluse() → False` 静默返回 → 说明解析出的 ToolUse 是 **0 个**;
3. 看 assistant 原文:kimi 的输出把围栏开栏紧跟在 `</think>` 后面**写在同一行**;
4. 复现确认:粘连写法 `iter_from_markdown` 返回 `[]`,换行隔开则正常。

**根因**:两层叠加。
- 开栏识别规则是"反引号必须在**行首**"(`_FENCE_RE.match(line)`),
  `</think>```websearch.search` 这一行以 `<` 开头 → 开栏不可见;
- 后面单独成行的 ` ``` ` 反被当成新开栏且永不闭合 → 整块丢弃。
解析出 0 个调用 → 不执行、不落日志、循环判定也 False → 全程无痕。

**修复**:仿 gptme(`gptme/codeblock.py` 的 `_extract_codeblocks` 开头就剥思考区):
解析前先把 `<think>...</think>` 整段剥掉(兼容 `<thinking>`,允许开闭混搭;
未闭合的思考区整体不解析)。围栏"落到行首",规则本身没动。
改动:`codeblock.strip_think()` + `iter_from_markdown`/`ToolUse.iter_from_content`
入口调用。详见 devlog 013。

**教训**:
- **对模型输出的解析,约定要防御格式变体**:我们约定"围栏独占一行",
  但不同模型的排版习惯不同(kimi 粘连)。协议文档对模型没有强制力;
- **静默失败最危险**:解析结果是 0 时,后面每一步都"正常"走完,不留任何痕迹。
  解析类代码遇到"该有却没有"的情况,值得留一条可见的日志或提示;
- 拿不准就**对照原项目**:gptme 早已在解析前剥 think,还写了注释说明原因
  (claude 会在思考里忘闭合围栏、gemini 用 `</thinking>`)。

## 2. MCP 工具超时后错误信息是空的(2026-10-04,已修复)

**环境**:websearch MCP 服务器(stdio,npx 启动),无代理网络。

**现象**:工具真的执行了(确认链正常),但结果一直是
`工具 websearch.search 执行失败: `(冒号后面**什么都没有**),连模型都不知道死因。

**排查**:对比日志时间戳——两次失败距调用发起都恰好 ~60 秒(减去确认提示符前的
等待),精确撞上 `mcp_client._CALL_TIMEOUT = 60.0`。

**根因**:三层。
1. `fut.result(timeout=60)` 抛的 `concurrent.futures.TimeoutError`,
   其 `str()` 是**空字符串** → 错误信息在 `f"执行失败: {e}"` 里被拼成空白;
2. 调用真的超时:服务器直连 duckduckgo 无代理,请求挂到服务自己的超时;
3. 架构弱点:常驻会话协程串行处理队列,一次 `call_tool` 挂起会堵住该服务器
   后续所有调用(超时只救主线程,协程还在原地 await)。

**修复**(2026-10-04,devlog 014):
1. 超时挪进协程内:`asyncio.wait_for(session.call_tool(...), timeout)` 包住,
   到点**取消**单次调用,协程立刻回队列服务后续工单;主线程 `fut.result` 只留
   +10 秒兜底。回归测试确认:超时后同一连接还能正常调用(不被堵死);
2. 超时异常翻译成人话:`MCP 服务器 'websearch' 调用工具 'search' 超时
   (120 秒无响应;可能网络不通或服务器卡住,可在 alpha.toml 里调大该服务器的
   timeout)`;`ToolUse.execute` 的错误格式统一带上 `{type(e).__name__}`,
   任何空消息异常不再隐身;
3. 超时可配置:`McpServer.timeout` 字段(alpha.toml 里 `[[mcp.servers]]` 下
   `timeout = 180`),默认 60 → 120 秒——搜索/渲染类工具天然偏慢。
   环境侧对策(不改代码):给 websearch 服务器配 `env = {USE_PROXY = "true"}`
   启用代理,或把默认引擎换成国内可达的。

**教训**:
- **异常消息可能为空**:`TimeoutError` 这类异常 `str()` 是空串,
  给用户/模型看错误时格式要带 `type(e).__name__`;
- 跨线程/协程桥接的设计里,**超时要在执行侧生效**(能取消),只靠等待侧超时,
  执行侧还挂着,资源会被慢慢占死;
- 时间戳是对账利器:日志里的时间差直接暴露了"精确 60 秒"这个特征。

## 3. 模型瞎猜 MCP 工具的调用格式,连错两轮(2026-10-04,已修复)

**环境**:websearch MCP 工具,markdown 通道,模型 dashscope/kimi-k3。

**现象**:让模型搜天气,它连续猜错调用格式:第一次围栏里写裸文本
(`上海市宝山区天气预报`)→ 报错;第二次写 `{"q": ...}`(键名错,正确是
`query`)→ 服务端校验报错。每错一次浪费一整轮交互 + 一次用户确认。
另外前两轮模型只输出思考块、连围栏都没写(日志确认 think 里也没有)——
那是模型自己抽风,与解析无关。

**排查**:对比内置工具和 MCP 工具的系统提示词:内置工具每个都有手写的
说明+示例;`_make_spec` 生成的 MCP ToolSpec **只有一句远端 description**。
关键缺口:markdown 通道下**参数名对模型完全不可见**——参数表
(`parameters`)只在原生通道转 JSON Schema 时才用上,`instructions` 和
`examples` 都是空的。模型无从得知"围栏内容要写 JSON 参数体"和"键名叫
query",只能按语义猜。

**根因**:工具协议的约定没有传达给模型。我们的 JSON 参数体约定写在
`_make_spec.execute` 的报错里(事后教育),没写在工具说明书里(事前教育)。

**修复**(2026-10-04,devlog 015):`_make_spec` 按参数表自动生成——
- `instructions`:说明"围栏内容写 JSON 参数体,键名必须用下面的参数名",
  并列出每个参数的名字/类型/必填性/描述;
- `examples`:用必填参数生成一个可直接照抄的示例围栏,如
  ` ```websearch.search\n{"query": "<query>"}\n``` `(占位值按参数类型挑)。
渲染效果(get_tool_prompt):说明紧跟远端描述之后,示例在"### 示例"下。

**教训**:
- **约定必须写在模型看得到的地方**:执行端报错只是兜底,说明书才是主渠道;
  事后纠错一轮的成本 = 一次完整交互 + 可能一次用户确认;
- 生成式接入(MCP 转本地 ToolSpec)要检查**每条通道的完整链路**:参数表
  这份数据在原生通道有用武之地,不代表 markdown 通道也用上了——
  两种通道对"模型需要看到什么"的要求不同,得分别核对;
- 真实会话是最好的测试:这个问题所有单元测试都没抓到(功能都对,
  缺的是"教模型怎么用"),第一次真跑就现形了。

## 4. 模型只输出思考、正文不写代码块,回合静默结束(2026-10-05,已修复)

**环境**:真实会话,模型 `dashscope/kimi-k3`,markdown 工具通道,websearch MCP 工具。
实录样本存档:`docs/tmp.jsonl`。(条目 3 里记的"前两轮只输出思考块、连围栏
都没写 —— 模型自己抽风,与解析无关"就是它,当时搁置,这次正式解决。)

**现象**:用户要搜天气,模型连续几轮"明确想调工具"却一个围栏都不写:
- 第 3 行:整条回复只有 `<think>…Let me use the websearch tool.</think>`;
- 第 6 行:思考之后正文写了"抱歉,刚才没有实际发起搜索。现在为您查询:"
  就戛然而止(全角冒号结尾);
- 第 18 行:回复干脆是空字符串。
每轮都无报错、无提示,回合直接结束,用户只能自己再敲"结果呢"。

**排查**:`has_runnable_tooluse() → False` 时中层循环无条件 return,
而这三种回复解析出的 ToolUse 都是 0 个 —— 和条目 1 同一个"静默失败"
病灶,只是这次连围栏都不存在,解析器没有任何可下手的东西。
结论:光修解析救不了"根本没写",得让模型在没写时被**点名提醒**。

**根因**:两层。
1. 模型把"打算调用"当成了"已经调用":思考里说了要用工具,正文却没落实
   成围栏(推理模型的已知通病,kimi 尤其明显);
2. 我们的协议没有兜底:提示词只说"需要执行操作时输出代码块",没说
   "只在思考里打算 = 没有调用";运行时发现 0 个调用也只是安静收场。

**修复**(2026-10-05,devlog 016):
1. 提示词(markdown/原生两条身份说明)各加一条:打算调用必须落实为
   正文里真的写出代码块/真的发起函数调用,禁止空回复和冒号结尾的半句话;
2. 新增检测器 `chat.missed_tooluse_reason()`:回合即将因"无可执行调用"
   结束时,认三种形态 —— 正文为空(只有思考或全空)、围栏标记写岔
   (如 ```websearch 而工具叫 websearch.search,按点号拆段比对)、
   正文以冒号结尾(ASCII/全角都认);
3. 命中就注入一条可见的 `[工具调用提醒]` system 消息并再生成一轮
   (上限 `MAX_TOOL_NUDGES`,默认 1),超限如实报告"本回合结束"。
   循环继续判定规则未动。

**教训**:
- **"协议对模型没有强制力"是双向的**:条目 1 教过排版会走样(粘连),
  这次是执行会走样(只想不做)——凡是靠模型自觉的约定,都得备一条
  "没做到时怎么办"的兜底路径;
- **启发式字符细节要拿真实样本对账**:冒号判断最初只写了 ASCII `":"`,
  中文模型用的是全角 `"："`(U+FF1A),拿实录一回放就露馅 ——
  判定规则里出现具体字符时,必须用真实语料验证码点;
- **回合结束前是最后的可观测点**:与其让用户发现"结果呢?",不如在
  return 之前问一句"这真的是正常收尾吗"。

**复测补充(2026-10-05 下午)**:修复后真机复测,提醒机制生效(冒号
结尾被提醒、模型补发格式正确的调用),但暴露三个残留,同日修复
(devlog 016"复测迭代"一节):①"我来帮你查一下上海今天的天气。"这种
**不带冒号的行动宣告**漏检 → 检测器加"行动宣告"标记表(只收"我+动作"
的词;初版收了"帮你",立刻误伤"我可以帮你做这些事:"这类能力介绍,
已移除);②提醒额度按整回合计,工具报错后模型想重试却被"额度用完"
掐死 → 改为**执行过调用就重置额度**;③原生通道另有独立 bug,见条目 5。

**预防层补充(2026-10-05 晚,devlog 018)**:会话 3b400c 里 hook 一场
兜了 5 次 —— 兜底有效但每漏一次浪费一整轮生成。查 gptme 源码发现它的
解法全在提示词层(prompts/templates.py):"工具使用强制令"(立刻调用,
不要描述;"每次要用工具的决定都必须在同一条消息里产生真实调用",按
服务商名单选择性注入)+ "下一步具体化"(回复以具体动作收尾,不要以
"需要的话我可以……"提议收尾;注释注明实测这是跨模型的共同弱点)。
照抄进 prompts/__init__.py 的独立"行动纪律"段(markdown/原生两版,
统一注入 —— glm-5.3 不在 gptme 名单里但实测就是患者)。最终形态:
**提示词预防 + hook 纠偏**双层,gptme 只有前一层。

## 5. 原生调用编号带点号,解析整行失配,调用静默丢失(2026-10-05,已修复)

**环境**:dashscope/kimi-k3,原生工具调用通道(`--tool-format tool`),
websearch MCP 工具。实录:`~/.local/share/my_agent_alpha/logs/2026-1005-332a08`。

**现象**:模型正确发起了函数调用(日志里有完整的调用行),但**没有任何
工具结果**;下一轮模型自认为"调用格式写错了",换个编号重试,依然没有
结果。两次调用全部无声消失。

**排查**:
1. 看日志原文,调用行长这样:
   `@websearch.search(websearch.search_0_a475cfc6): {"query": ..., "limit": 5}`
   —— 生成端没问题(是我们自己从 API 的 tool_calls 拼出来的);
2. 用这行原文喂 `_NATIVE_CALL_RE` → **零匹配**;对照无点号编号
   (`call_abc123`)正常;
3. 原因:dashscope 给的调用编号格式是 `工具名_序号_哈希`,**编号内部
   含点号**,而正则里编号的字符集 `[A-Za-z0-9_\-]*` 没有点。

**根因**:**生成端和解析端的"合法编号"字符集不同源**。我们自己拼行时
照抄 API 给的任意编号,解析回读时却假设了 OpenAI 风格(`call_xxx`)。
编号里的 `.` 让回溯也救不回来:工具名组贪到 `websearch.search` 后,
编号组匹配 `websearch` 碰 `.` 停,`)` 对不上;缩短工具名组又要求 `(` 对
上 `.` —— 整行失配 → 解析 0 个调用 → 不执行、不报错。且条目 4 的检测
器也放行(正文非空、无围栏、结尾是 `}`)→ **双重静默**。下一轮
`msgs2dicts` 同样解析不出 tool_calls,把调用行当纯文本发回,模型看到
自己的调用没有 tool 角色结果,错误地归因为"我格式写错了"。

**修复**(2026-10-05,devlog 016"复测迭代"):
1. `_NATIVE_CALL_RE` 编号字符集放宽为 `[A-Za-z0-9_.\-]*`(两侧有字面
   `(` `)` 包夹,放宽无歧义);`_strip_native_lines`、`msgs2dicts`
   复用同一正则自动受益;
2. 检测器加兜底:宽松探测器 `_LOOSE_NATIVE_CALL_RE`(不限编号字符集)
   命中调用行、严格解析却 0 个 → `[工具调用提醒]` 点名,防未来服务商
   再出怪编号;
3. 回归测试:真机原文(带点编号)必须解析出调用且 call_id 原样保留。

**教训**:
- **生成端能写什么,解析端就必须能认什么**:同一份数据的两端契约
  (这里是"编号的合法字符")必须同源,差异就是静默丢失;
- **别按一家服务商的格式假设字段长相**:OpenAI 的 `call_xxx` 只是
  事实,不是规范;dashscope 的编号就带点;把字符集写窄等于把别家
  服务商挡在门外;
- 模型的自我归因不可信:"我上次格式写错了"多半是"上次的结果没送到"
  —— 排查时先核对日志原文,别信模型的自我诊断。

## 6. 用户输入混入坏字符,写日志时整个程序崩溃(2026-10-05,已修复)

**环境**:WSL2 终端,用户输入法/粘贴传入坏的 UTF-8 序列(疑似表情符号截断)。

**现象**:搜索链路刚打通(5 条真实结果),用户下一条输入"🌧️有下雨吗"后,
程序直接 Traceback 崩到系统提示符:

```text
UnicodeEncodeError: 'utf-8' codec can't encode characters in position 29-30:
surrogates not allowed
```

崩溃点在 `logmanager._jsonl_line` 的 `encode("utf-8")`;position 29-30
恰好是 `{"role": "user", "content": "` 之后的第 1-2 个字符 —— 坏字符就在
用户输入的开头(表情序列解码成了"落单代理字符"surrogate)。

**根因**:两层。
1. 终端坏字节解码后留下**落单代理字符**(U+D800–U+DFFF 区间的孤儿,
   utf-8 编码不了),input() 原样放行;
2. `manager.append(user)` 这一行在 `_run_chat_loop` 的 try 块**外面**,
   存储层一炸就穿透到 main(),REPL 直接死亡 —— 违背"REPL 不被打死"的
   阶段 1 老教训,只是当时只防了 provider 异常。

**修复**(2026-10-05,devlog 017),三层防御:
1. 入口清洗:`_get_user_input()` 返回前用 `clean_bad_unicode()` 把
   落单代理字符换成 ?(message.py 新增该函数);
2. 日志层兜底:`_jsonl_line` 编码前同样清洗 —— 就算坏字符来自别的路
   (LLM 回复、MCP 工具结果),写盘也永不崩;宁可一个字符变 ?,
   不丢整个会话(日志是唯一状态);
3. REPL 存活:把 append(user)/TURN_PRE 钩子挪进 try 块,任何一条消息
   的存储问题都只终结当前回合,不终结程序。

**教训**:
- **外部输入的字节边界就是攻击面**:终端、LLM 接口、MCP 服务器都是
  "外面的世界",进来的字符串不能假设一定能 utf-8 编码;
- **"日志是唯一状态"意味着写入路径必须永不失败**:持久化函数的容错
  要按"任何输入都不许抛"的标准做;
- 崩溃信息里的 position 是线索:`{"role": "user", "content": "` 恰好
  28 个字符,position 29 直接指认了坏字符在用户输入开头。

## 7. Clash fake-ip 假 IP 撞上服务器 SSRF 防护,网页抓取全被拦(2026-10-05,已修复)

**环境**:websearch MCP 服务器 + Clash 代理(fake-ip 模式,127.0.0.1:7897)。

**现象**:搜索正常,但 `fetchCsdnArticle` / `fetchWebContent` 一律失败:

```text
Request URL (blog.csdn.net) resolves to private IP(s) (198.18.0.6),
which is not allowed
```

而同一台机器上 shell 的 curl 抓同一 URL 却能通(拿到反爬页也算通了)。

**排查**:198.18.0.6 属于 198.18.0.0/15 —— 这是 **Clash fake-ip 模式**的
标志性网段:DNS 把所有域名解析成假 IP,只有流量经过代理、由代理端重新
解析才有意义。websearch 服务器的 SSRF 防护(utils/urlSafety.js)抓取前
自己解析一次 DNS,看到"保留网段 IP"就按"疑似内网攻击"拒绝。curl 走
https_proxy 环境变量、由代理解析,所以不踩这个坑。

**根因**:代理客户端的 DNS 方案(fake-ip)和工具服务器的安全检查
(私网 IP 拦截)互不知情 —— 环境组合出来的坑,单看任何一边都是"对的"。

**修复**:服务器作者预见到了这个场景(报错信息里直接写了答案):
alpha.toml 的 `[mcp.servers.env]` 加

```toml
FAKE_IP_CIDRS = "198.18.0.0/15"
```

语义(urlSafety.isAllowedFakeIp):落在声明网段里的解析结果视为代理假 IP
放行(真实解析在代理侧完成);字面私网地址(如 127.0.0.1)仍然无条件拦。
实测:private-IP 拦截消失,请求经代理真正到达目标站;普通站点
(weather.com.cn)fetch 返回真实页面内容。

**教训**:
- **报错信息要认真读**:这个服务器把解法直接写在错误消息里了;
- 加一层基础设施(代理)会把它的实现细节(DNS 假 IP)泄漏给所有
  在它旁边跑的程序;排环境问题时,先问"新组件改变了什么共享假设"
  ——这里被改变的假设是"DNS 解析结果是真实地址";
- 198.18.0.0/15 网段是 fake-ip 的指纹,见到它就该想到代理 DNS。
