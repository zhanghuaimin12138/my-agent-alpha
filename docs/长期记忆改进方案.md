## 一、现状盘点

先说清楚我们现在有什么。整条链路四个环节:

| 环节 | 现状 | 位置 |
|---|---|---|
| 存储 | 一条记忆 = 一个 md 文件:`# 标题` + 正文 + `*记录于 日期*` 尾注;**无 frontmatter、无类型、无描述** | [memory_store.py:64-79](../src/my_agent_alpha/memory_store.py#L64-L79) |
| 目录 | 两层:工作区 `memory/`(项目层)+ 数据目录 `memory/`(用户层),同名近层盖远层 | [memory_store.py:39-41](../src/my_agent_alpha/memory_store.py#L39-L41) |
| 索引 | 每层一个 `MEMORY.md`,**每次保存后代码全量重建**,一行 = 链接 + 标题 | [memory_store.py:82-92](../src/my_agent_alpha/memory_store.py#L82-L92) |
| 注入 | 仅会话开始且日志为空时,渲染索引进 pinned 隐藏 system 消息,预算 64KB | [chat.py:631-636](../src/my_agent_alpha/chat.py#L631-L636)、[memory_store.py:113-143](../src/my_agent_alpha/memory_store.py#L113-L143) |
| 写入 | memory 工具(fence / 原生参数),**硬编码写项目层**,同名静默覆盖,**无删除**;经确认链 | [tools/memory.py:34](../src/my_agent_alpha/tools/memory.py#L34) |
| 读取 | 模型看索引后自己用 read 看细节;`/memory`、`/memory show <名>` 给人用 | [commands/builtin.py:90-106](../src/my_agent_alpha/commands/builtin.py#L90-L106) |
| 测试 | test_phase8.py 覆盖存取、两层覆盖、索引注入 | tests/test_phase8.py |

**没有的东西**:类型纪律、"该存什么/不该存什么"的提示词约束、新鲜度标注、更新/删除路径、去重整理、写入兜底(模型忘了存就没了)。

## 二、设计标尺(从报告提炼的取舍原则)

后面每一项改进都拿这五条量过,读者也可以拿它们检验:

1. **文件即记忆**:人能直接用编辑器看/改/删,可调试性极强。我们已经是,继续是——所有改进不得引入数据库或二进制格式。
2. **上下文经济**:常驻上下文的只有索引,细节按需 read。索引是"目录",不是"记忆本身"。
3. **description 是"向量"的替代品**(报告 §4.4):CC 没有向量库,相关性判断全靠 frontmatter 里那行 description。**这是整个检索质量的地基**——description 写得差,后面一切召回机制都白搭。所以我们第一优先级是把 description 建起来,而不是先做花哨的召回。
4. **防陈旧是读侧一等公民**(报告 §4.5):不只存的时候小心,每次注入都要标年龄 + 提醒"记忆说的不等于现在成立的"。
5. **防重复处理靠硬机制,防重复内容靠软约束**(报告 §9.1-7):同名覆盖、索引重建这类是代码保证;"别写重复记忆"只能靠把现有记忆清单喂给模型 + 提示词指令。诚实接受这一点,不发明假的程序化去重。

**我们与 CC 的一处方向差异,保留不改**:CC 写记忆免确认(权限豁免 + 提示词纪律);我们走确认链(模型提议、用户点头,见 [tools/memory.py](../src/my_agent_alpha/tools/memory.py) 模块注释)。学习项目里用户审批就是最好的"排除清单",这套保留。

## 三、改进项(分四期,按优先级)

每项四要素:**报告依据 → 我们现状 → 改法 → 验收**。

### M1 格式与提示词地基(优先级最高:小改动,大收益)

#### M1.1 记忆文件加 frontmatter

- **报告依据**:§2.3——`name / description / type` 三字段;§4.4 结尾点题:"没有 embedding 这件事解释了 description 为何被强调必须具体——它就是这个向量的替代品"。
- **现状**:只有首行标题 + 正文,索引行也只有标题。模型判断"要不要读这条"时信息量太少。
- **改法**:`save_memory` 写出新格式:

  ```markdown
  ---
  name: 部署流程
  description: 服务器登录与发布步骤,含 systemd 重启命令
  type: project        # user | feedback | project | reference
  created: 2026-10-07
  ---

  # 部署流程

  (正文)
  ```

  **兼容策略:读时兼容,写时升级**——旧的无头文件不主动重写(尊重"用户手写的文件别乱动"),解析时无 frontmatter 就按 `type: project`、`description = 首行标题` 处理;只有再次经过 `save_memory` 写入时才升级成新格式。不搞一次性迁移脚本。
- **验收**:test_phase8 加用例——新格式解析出 description/type;旧格式回填默认值不报错;`list_memories`、`rebuild_index` 对两种格式都能取到标题。

#### M1.2 索引行升级:标题 → description 钩子行

- **报告依据**:§2.6——索引"每条一行、约 150 字符、绝不含记忆正文";§2.3——description "必须具体,未来对话靠它判断相关性"。
- **现状**:[memory_store.py:91](../src/my_agent_alpha/memory_store.py#L91) 索引行是 `- [名](文件.md) — 标题`,标题往往就是名字的重复,信息量为零。
- **改法**:索引行改为 `- [标题](文件.md) — description(类型)`,例如:

  ```
  - [部署流程](部署流程.md) — 服务器登录与发布步骤,含 systemd 重启命令(project)
  ```

  同时给单行长度设软上限(比如截到 120 字符),防报告 §2.6 提到的"200 行内塞 197KB 长行"式事故。注意保持 `](xxx.md)` 的链接形态不变,否则 [`_with_real_paths`](../src/my_agent_alpha/memory_store.py#L95-L110) 的正则匹配不到。
- **验收**:构造一条带 description 的记忆,检查 MEMORY.md 行格式;超长 description 被截断。

#### M1.3 memory 工具加 type 参数

- **报告依据**:§2.4 四类封闭类型学。
- **现状**:工具只有 name/content 两个参数([tools/memory.py:44-47](../src/my_agent_alpha/tools/memory.py#L44-L47)),模型表达不了"这是用户偏好还是项目事实"。
- **改法**:加 `type` 参数,四选一,默认 `project`。
- **验收**:markdown 通道 fence 头支持 ` ```memory 部署流程 project ` 或 kwargs;原生通道 schema 多一个 enum 参数。

#### M1.4 提示词协议:教模型"什么值得记"

- **报告依据**:§2.4(类型学+保存时机)、§2.5(排除清单)、§2.4 尾注(从成功中学习)、§9.1-4(eval 迭代记录)。
- **现状**:工具 instructions 只有一句"名字要短且能认出内容"。模型没有任何"不该记什么"的概念,迟早把代码结构、git 历史这类可推导的东西塞进记忆。
- **改法**:扩写 memory 工具的 `instructions`(它进系统提示词),包含四张表:

  1. **四类何时保存**(照抄报告 §2.4 表,翻译成中文);
  2. **排除清单**:代码结构/文件路径(读代码就知道)、git 历史(`git log` 是权威)、调试解法(修复在代码里)、AGENTS.md 已有内容、临时任务状态;
  3. **从成功中学习**:用户纠正("不要 X")和确认("对,就这样")都记——只记纠正会让模型过度保守;
  4. **相对日期转绝对**:"上周"要写成具体日期;
  5. **update-before-create**:存之前先看注入的索引,有近似条目就覆盖更新,别新建重复。

  同时注入索引的头部说明(现在是"需要细节时用 read 工具查看对应文件")追加一句:"记忆说某东西存在 ≠ 它现在还存在,引用前先验证"——报告 §4.5 的行为协议,一行就够。
- **验收**:test_prompts 断言系统提示词含关键词(如"排除清单"或"从成功中学习");人工跑一轮让模型试着记一条"项目用 pytest"——预期它应拒绝(可从 pyproject.toml 推导)。

### M2 读路径:预算收紧 + 新鲜度标注

#### M2.1 索引双上限,64KB → 行数 + 字节双卡

- **报告依据**:§2.6——CC 用 200 行**且** 25KB 双上限,截断时追加指明触发原因的 WARNING,要求把细节移入主题文件;64KB 是 gptme 的老数字,CC 实测后收紧了一半多。
- **现状**:[memory_store.py:27](../src/my_agent_alpha/memory_store.py#L27) 单一 64KB 预算。字节上限挡不住"行行超长",行数上限挡不住"行行塞满"——必须双卡。
- **改法**:常量改为两个:`_INDEX_MAX_LINES = 100` / `_INDEX_MAX_BYTES = 16 * 1024`(我们两层各一份索引,单层配额取 CC 的一半,总量相当;数值写在常量上,实测后好调)。截断逻辑:先按行截、再按字节截,末尾注明触发了哪个上限。
- **验收**:测试构造 101 条记忆 → 截到 100 行且尾注正确;构造超长行 → 字节上限兜底。

#### M2.2 新鲜度标注:mtime 年龄 + 过时警示

- **报告依据**:§4.5——三个洞察:① 模型不擅长日期算术,裸 ISO 时间戳引不起"这事儿可能变了"的推理,要转成"今天/N 天前";② 陈旧记忆加警告"引用前先对照现状验证";③ 让错误主张显得更权威的恰恰是那些 file:line 引用。
- **现状**:文件尾注有记录日期,但它在正文里——模型不 read 就看不到;索引里完全没有时间信息。
- **改法**:`render_memory_index` 渲染每行时按文件 mtime 算年龄,行尾追加 `(今天)` / `(3 天前)` / `(42 天前⚠旧)`,阈值暂定 30 天。注入只在会话开始做一次,零边际成本。注意:索引文件本身不存年龄(年龄是渲染时算的),`rebuild_index` 不受影响。
- **验收**:测试用 `os.utime` 伪造新旧文件,断言渲染文本含"天前"与 ⚠ 标记。

### M3 写路径补全:scope + 更新/删除

#### M3.1 scope 参数:解除"永远写项目层"的硬编码

- **报告依据**:§2.4/§6.1——CC 按类型分 scope(user 永远私有,project 可共享)。我们没有团队层,但两层目录(项目/用户)已经存在,只是工具够不着。
- **现状**:[tools/memory.py:34](../src/my_agent_alpha/tools/memory.py#L34) `project_level=True` 写死。"用户偏好简短回答"这类记忆跟着项目走显然不对——换个项目就看不见了。
- **改法**:memory 工具加 `scope` 参数(`project|user`),不传时按类型推断默认:`user`/`feedback` → 用户层,`project`/`reference` → 项目层。`/memory` 列表本来就把两层都列出([memory_store.py:50-61](../src/my_agent_alpha/memory_store.py#L50-L61)),读取侧无需改。
- **验收**:同一条记忆分别写两层,索引两段各出现一次;`/memory show` 都能取到。

#### M3.2 显式更新提示 + 删除动作

- **报告依据**:§3.2 Phase 3——"删除被证伪的记忆:今天的调查推翻了旧记忆时,在源头修正";§9.2 承认错误记忆的最大风险是被当事实断言。
- **现状**:同名覆盖是**静默**的(调用方都不知道覆盖了什么);删除只能用户手动 rm。
- **改法**(两个小动作,不引入新工具):
  1. `save_memory` 覆盖已存在文件时,返回信息里注明"已覆盖旧记忆(旧首行标题:…)",工具输出把这个透传给模型——它就会发现"哦原来有一条近似的,我是合并还是替换";
  2. memory 工具加 `action: delete` 支持(按名删文件 + 重建索引),照走确认链——删除是不可逆操作,必须过用户。
- **验收**:覆盖测试断言提示文本;删除后索引行消失、文件不存在;非交互 -y 下 delete 也过安全护栏(它不是只读工具,天然在确认链里)。

### M4 记忆整理("做梦"):/memory consolidate 手动命令

- **报告依据**:§3.2 全节——四阶段提示词(定向→收集→固化→剪枝)、合并重复、相对日期转绝对、删证伪、索引双上限内。
- **现状**:完全没有整理机制。记忆只会单调增长,重复和过时靠用户眼睛。
- **改法**:新命令 `/memory consolidate`,内部用现成的 [subagent 工具](../src/my_agent_alpha/tools/subagent.py) 起一个整理代理,prompt 按四阶段写:

  ```
  1. 定向:列出两层记忆目录,读 MEMORY.md,浏览既有文件——先知道有什么再动手;
  2. 收集:通读记忆正文,标记三类问题——近似重复、相互矛盾、与当前代码/文档不符的过时条目;
  3. 固化:重复的合并进既有文件(别新建)、相对日期转绝对、被证伪的删除;
  4. 剪枝:重建索引,确认在双上限内。
  ```

  **约束**:给这个 subagent 的工具白名单只给 read/grep/edit/memory(不许 shell),写操作仅限两个记忆目录——对应报告 §3.2 的安全约束(dream 代理 Bash 只读、写只走 Edit/Write)。
  **诚实声明**(标尺 5):内容级去重没有程序化方案,靠的就是把"现有记忆清单 + 各自 description"完整喂给整理代理 + prompt 里的合并指令。
  **不做自动定时**:CC 的时间门+会话门+锁(§3.2 三重门控)是为了无人值守设计的;我们手动敲命令就是用户审批,天然安全。将来若真要自动,用 mtime 当时钟(报告 §9.1-5 的省状态文件技巧)+ SESSION_START hook。
- **验收**:集成测试——预置一对近似重复记忆 + 一条过时记忆,跑 consolidate(用 mock 模型扮演整理代理),断言:合并后文件数减少、索引同步、过时条目消失。

### M5 远期可选(默认不做,写明触发条件)

| 机制 | 报告依据 | 不做的理由 | 什么情况下再做 |
|---|---|---|---|
| **轮末后台提取代理**:turn 结束(assistant 无工具调用)后 fire-and-forget 起子代理,扫当轮对话补存遗漏记忆;游标机制保证每段消息只提取一次,本轮模型已写过记忆就跳过(互斥) | §3.1 | 复杂度最高(fork、游标、互斥、非交互退出前的 drain);我们的确认链本来就要求用户在场,补一个"你刚才是不是忘了记"的成本低 | 记忆超过 ~50 条,且用户实际观察到"该记的没记"成为常态 |
| **按需召回**:每用户轮一次,用便宜模型从"文件名+description 清单"里选 ≤5 条注入,索引不再常驻 | §4.3/§4.4 | 需要旁路 LLM 调用(多一次延迟和费用);小规模下常驻索引 + 模型自己 read 已经够用 | 索引常驻成为实际上下文压力(记忆 >100 条,或双上限频繁触顶) |

若做轮末提取,基础设施都在:`TURN_POST` hook(报告 §3.1 的触发点对应物,R4 会话命名已在用,[hooks/naming.py](../src/my_agent_alpha/hooks/naming.py))+ subagent 子进程。

## 四、明确不采纳(及理由)

| 不采纳 | 理由 |
|---|---|
| 团队记忆(TEAMMEM) | 用户明确不需要;且依赖服务端同步、密钥扫描等一整套,超出学习范围 |
| 向量库 / embedding | 报告 §4.4 证明 CC 自己都不用——description + 廉价选择就够了,这是报告最有力的结论之一 |
| 提示词缓存微优化(KAIROS 式路径模式化等) | 我们单 provider、会话短,索引只注入一次,没有跨午夜缓存前缀问题 |
| 自动定时 dream | 见 M4——手动命令先行,自动化的三重门控是无人值守场景的需求 |
| 每类 agent 专属记忆目录(报告 §4.8) | 我们只有一种主 agent,subagent 是无状态工人;等真有带个性的常驻 agent 再说 |
| 记忆注入位置从 system 消息挪到首条用户消息(报告 §4.2) | CC 那样做是为了提示词缓存前缀;我们 pinned system 消息一次注入,功能等价,不值得动 |

## 六、风险与注意

1. **frontmatter 会破坏"首行即标题"的解析**:`list_memories`、`rebuild_index`、`/memory show` 都靠 `split("\n", 1)[0]` 取标题——解析函数要先剥 frontmatter 再找 `#` 行。这是 M1 里最容易漏的改动点,三处调用都要过一遍。
2. **索引行格式与 `_with_real_paths` 正则的耦合**:链接必须保持 `](文件.md)` 形态(路径里没有 `/`),新增的类型/年龄标注只能加在行尾。
3. **旧文件混存**:读时兼容意味着磁盘上长期两种格式并存,所有读路径都要按"可能有头也可能没头"处理;宁可代码里多一个 `parse_frontmatter` 帮助函数,不要在每个调用点写 if。
4. **双上限数值是猜的**:100 行/16KB 起步,等真实记忆量上来后按实测调——报告的教训是 CC 也是从 200 行单上限进化到双上限的(§2.6)。
5. **M4 的 subagent 权限**:整理代理能删文件,工具白名单必须收紧(无 shell、写仅限记忆目录);这块如果 subagent 工具目前不支持按调用定制工具集,需要先给它加一个可选参数——算 M4 的前置小任务。
