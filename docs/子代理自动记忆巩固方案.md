# 子代理自动记忆巩固方案(定稿)

> 目标:回合结束后由子代理在后台自动维护长期记忆(补记遗漏、更新过时、合并重复),替代目前"全靠主 agent 自觉调 memory 工具"的模式。
> 依托:记忆索引已按 devlog 054 改为"每次请求动态注入 + 进程内单份缓存"(不落日志)——本方案删缓存即生效的机制建立在这上面。

**两种巩固任务,后文统一用这两个中文名:**

- **回合巩固**:一个回合结束后的小补记(只看这个回合聊了什么),后台即时做;
- **会话巩固**:整个会话结束时的一次大整理(回顾全程 + 整理全部记忆,即"做梦"),落盘后下次打开会话时收结果。

---

## 1. 背景与目标

### 1.1 现状

```
每次请求:prepare_messages 组装上下文时动态注入记忆索引
          (get_memory_index:进程内单份缓存,记忆改动即失效;不落日志)
会话中:  主 agent 觉得"该记" → memory 工具 → 确认链(用户点头)→ save_memory 落盘
手动整理:/memory consolidate → 派子代理四步整理(定向→收集→固化→剪枝)
```

### 1.2 痛点

1. **漏记**:主 agent 忙着干活,用户的纠正("以后别 X")、偏好表达常常没被记下——记忆协议全靠模型自觉,没有兜底;
2. **质量参差**:顺手记的条目 description 含糊、和旧记忆重复、相对日期没转绝对日期,这些"整理债"只有手动 consolidate 才还;
3. **会话结束即散场**:聊了一整段的 project 状态、决策动机,会话结束没人回顾。

### 1.3 安全底线

自动巩固会绕过 memory 工具的逐条用户确认。底线与兜底:

- 记忆索引不落日志,改错/删错**不污染会话历史**,影响仅限"下一次请求的注入内容",改掉即愈;
- 写入只有 memory 工具一个通道,落盘路径硬编码在两个记忆目录里(硬沙箱);
- 派发前整目录备份,禁删、删了自动恢复,收割出审计报告;
- 默认关闭(`ALPHA_AUTO_MEMORY` / `ALPHA_AUTO_MEMORY_DREAM`),开不开由用户决定。

## 2. 设计总览

### 2.1 总体时序(回合巩固,主路径)

三个角色,各管一段:主线程管"要不要做",job 线程管"流程怎么走",子代理管"动脑子干活"。

```
┌─ 主线程(回合边界,纯规则,毫秒级) ─────────────────────────┐
│ 回合 N 结束,turn.post 触发 automemory 钩子                  │
│  ① 预筛:单飞行闸/冷却/信号(见 §3),不命中就什么都不做        │
│  ② 派发准备:备份记忆目录 → 写 input.md → 写 job.json        │
│     → 起 job 线程 → print 一行提示 → 回到输入提示符          │
└────────────────────────────────────────────────────────────┘
                          │ 并行
┌─ job 线程(后台) ────────┐   ┌─ 子代理(独立进程) ─────────┐
│  ③ 派子进程并喂入 input   │→ │  ④ 读输入 → 判断 →          │
│  ⑤ 等它跑完              │   │     调 memory 工具改记忆     │
│  ⑥ 收割:取结论/审计/     │← │     最后交一份固定格式报告    │
│     恢复/删缓存/写报告    │   │     (跑完即退出)            │
│  ⑦ 清单飞行闸             │   └────────────────────────────┘
└─────────────────────────┘
                          ▼
用户下一条消息 → 模型请求 → 缓存已删 → 重新渲染 → 注入最新记忆索引
(模型感知新记忆不需要任何通知消息;提示只 print 给人看)
```

### 2.2 job 线程在干什么(监工 + 搬运工,自己不思考)

线程**不调模型、不做任何判断**,只按固定流程搬运文件和调用现成函数:

```
memory_job_thread(job_dir, ...):
  1. 派子进程:
       python -m my_agent_alpha -n -y \
         --name subagent-mem-<id> --tools read,grep,memory \
         --workspace <ws> -m <model> -     # "-" = 提示词从 stdin 进
       stdin 喂入 input.md 的全部内容;超时上限 120 秒
  2. 阻塞等待子进程退出(后台线程等得起;超时就杀掉走失败分支)
  3. 取结论:从子代理自己的会话日志里读最后一条模型回复
       ——日志是唯一事实来源,子代理跑完整套过程都记录在里面
  4. 审计:逐个比对 backup/ 快照与记忆目录现状
       文件新增 / 内容有变  → 记入报告
       文件消失(被删了)    → 从备份恢复该文件 + 告警(禁删的硬执行)
  5. 删缓存:invalidate_memory_cache()
       ——与主线程共享同一份进程内存,删完立即生效
  6. 汇报:终端 print 一行变化摘要;完整报告写 report.md;
       job.json 状态改为 harvested
  7. 让位:finally 里清掉单飞行闸(线程退出 = 允许派下一个 job)

  任何一步抛异常(子进程崩溃/超时/日志里没有结论):
       也要先做第 4 步的 diff 审计(子代理崩溃前可能已写了一半记忆,
       不 diff 就不知道它动过什么),再标 failed、记节流指纹、
       print 一行原因 —— 凡线程退出,必有审计报告。
```

### 2.3 子代理在干什么(干活的人,只见到一份输入)

子代理是一个**独立进程里的完整 agent**(有自己的会话日志、白名单工具、自动确认)。它不知道 job、线程、备份的存在,拿到的全部世界就是 stdin 喂进来的 input.md。按提示词干四件事:

```
1. 读【现有记忆清单】
     先知道已经记了什么(一行一条:路径 + 描述 + 类型),
     该合并的合并、该新建的新建,判断都以它为底

2. 逐条看【对话增量】
     对照四类标准判断"值不值得跨会话记住":
     user(用户角色/偏好/背景)、feedback(对工作方式的纠正或确认)、
     project(进行中的工作/决策及动机)、reference(外部资源指针)
     代码结构、文件路径、git 历史、修复过程、临时状态 → 不该记

3. 动手(全部经 memory 工具 —— 它唯一的写通道):
     漏记      → 补记一条(frontmatter 的 description 写具体;
                 "上周"这类相对日期换算成绝对日期)
     与已有近似 → 同名覆盖更新,把新旧内容合并成一份
     发现该删   → 不删,只写进报告的"删除建议"
     没东西可记 → 不硬记,直接报告"无事可记"

4. 交报告:最后一条模型回复按固定格式输出三个小节
     新增: / 更新: / 删除建议:
     ——这就是 job 线程第 3 步要取的"结论"
```

它改的记忆文件直接落在两个记忆目录里(硬沙箱,§4.1),跑完进程即退出,不留任何驻留状态。

### 2.4 主进程退出时,在飞的 job 怎么办

三种退出方式,行为不同:

**① 正常退出(/exit),回合巩固在飞** —— 等它收完尾。job 线程是
daemon=False,Python 解释器退出前会等所有非 daemon 线程结束:收割、
删缓存、写报告一样不少,代价是退出命令后终端最多多等 120 秒(超时上限)。
想让退出干脆:session.end 里主动 terminate 子代理进程(可选项,实施时再定)。

**② 会话结束触发会话巩固("做梦")** —— 本来就设计成不等:
主进程派完就退,不为此起线程(线程要么拖住退出、要么被硬杀,审计会做一半):

```
session.end → 派子进程(同 §2.2 第 1 步,输入换成会话日志尾部,见 §4.4)
            → 主进程直接退出
子进程 start_new_session=True 脱离终端,独立跑完:
  记忆文件已改,结论落在子代理自己的日志里
下次打开会话 → SESSION_START → 扫 memory-jobs/ 补收(见下)
```

**③ 主进程被杀/崩溃,回合巩固在飞** —— 兜底路径:

```
主进程死亡 → job 线程同死,job.json 停在 running
           → 子代理进程变孤儿,继续跑完(或被一起杀,记忆可能改了一半)
下次打开会话 → SESSION_START → 扫 memory-jobs/ 发现 running 的 job:
  按 job.json 里记的子代理 pid 探活:
    还活着(另一终端的同会话在跑,罕见)→ 跳过,下次再看
    已死 → 视为"已结束",走补收:diff 审计 + 恢复 + 删缓存 + 报告
           (有结论报告最好;日志里没有结论,就以纯 diff 结果为准)
```

三种路径汇到同一条规则:**凡 job 结束(无论成功、失败、崩溃),最终
都经过一次 diff 审计**——backup 快照就是为此存在的,半改的记忆要么
确认保留(记入报告)要么整体回滚。

### 2.5 job 数据布局

```
<会话目录>/memory-jobs/<job-id>/
├── job.json    {kind: turn|session, status: running|harvested|failed,
│                 trigger, created_at, subagent_name, subagent_pid,
│                 input_from, input_upto}
│                 # subagent_pid:补收时探活用(§2.4 ③)
│                 # input_from/input_upto:增量覆盖区间(§4.2,harvested 才生效)
├── input.md    拍平的四段输入(子代理的 stdin)
├── backup/     派发时两层记忆目录的完整快照(审计与回滚的依据)
└── report.md   收割时写的审计报告(diff 清单 + 子代理结论)
```

磁盘状态的作用:**崩溃兜底 + 补收的凭证**。正常运行时单飞行判断走内存闸(job 线程句柄判活),不扫目录;主进程崩溃则线程同死,子进程独立跑完落盘,下次会话按 job.json 补收(判定规则见 §2.4 ③)。

### 2.6 线程边界(收割为什么能放后台线程)

收割只碰三样东西:记忆文件(子代理已写完,线程只读与恢复)、模块级索引缓存(删除操作,天然线程安全)、终端 print——全部线程安全。设计约束因此成立:**收割不依赖任何按单线程假设工作的会话状态**(如 LogManager 的游标与写盘),只依赖 job 目录与记忆目录这两个磁盘位置——将来若收割需要改动会话日志/视图,就必须移回主线程做。

## 3. 触发与节制

### 3.1 两种任务

| | 回合巩固 | 会话巩固 |
|---|---|---|
| 触发 | turn.post,规则预筛出信号 | session.end,每会话一次 |
| 输入 | 本回合增量 + 记忆清单 | 会话日志尾部 20 回合拍平 + 记忆清单 |
| 等待 | job 线程在线等,完成即收割 | 不等,落盘,下次会话补收 |

回合巩固漏掉的内容由会话巩固兜底;会话巩固也没跑(进程被杀),下次打开会话补收。

### 3.2 "本 turn"与"增量"怎么界定(两个不同的游标)

信号预筛说的"本 turn"和 input.md 里的"对话增量"不是一回事,分开记:

- **本 turn**(信号判断用):上个回合边界以来的消息。实现是内存计数——
  hook 里记"上个 TURN_POST 时的消息条数",本次 TURN_POST 先取
  `messages[上个条数:]` 做信号判断,再更新计数(和冷却计数同款管理方式);
- **对话增量**(input.md 用):**上次成功巩固覆盖以来**的消息,不是"上次
  派发以来"——失败的 job 没干成活,它覆盖过的内容下次要重算。
  统计规则见 §4.2。

### 3.3 信号词表(纯规则,可按误报率调)

记住 / 别忘 / 以后 / 下次 / 总是 / 每次都 / 我喜欢 / 我讨厌 / 我偏好 / 别再 / 不要再 / 我习惯 / 我用的是(中英都收)。误报的代价小(子代理白看一眼说"无事可记"),漏报有兜底。

### 3.4 节制机制

- **冷却**:距上次派发不足 3 个回合不派;
- **单飞行**:同一时刻最多一个记忆 job 在飞(内存闸判 job 线程是否存活);
- **节流**:job 失败记源指纹,同一指纹不再自动重试;
- **开关**:两通道默认关,环境变量开启。

## 4. 子代理规格

### 4.1 工具白名单:read + grep + memory

- **read**:看记忆原文(清单只有一行描述,合并/去重判断必须看全文);
- **grep**:跨记忆文件查"还有没有别的条目说过这件事",比逐个 read 省轮次;
- **memory**:**唯一写通道**。save_memory/delete_memory 的落盘路径硬编码在两个记忆目录里(memory_store.memory_dirs),子代理想写别处都没有入口——硬沙箱;
- **不给** edit/save/shell(通用写入口,会绕出沙箱,且审计 diff 只盯记忆目录,是盲区)、todo/subagent(用不上;绝不嵌套派生)。

覆盖更新用 memory 同名覆盖(实施时给 save_memory 加"覆盖保留原 created 日期"的小改进)。

### 4.2 输入上下文(input.md 四段,派发时主线程拍平,子代理零探索)

1. **现有记忆清单**:两层目录逐条"路径 + description + 类型"——去重必须先知道有什么;
2. **对话增量**(统计规则见下):消息逐条拍平成证据行(`[003][USER] 内容` / `[005][TOOL_RESULT call_id=a] 内容`);单条超 2000 tokens 先裁头尾(裁的是给记录员看的副本,原文不动);
3. **判断协议与动作规则**(§4.3 提示词正文);
4. **报告模板**:固定小节,线程解析它生成审计摘要。

**增量的统计规则**(核心:增量从"上次成功巩固覆盖点"起算,失败的 job 不推进覆盖点):

```
派发时(主线程):
  end   = len(manager.messages)          ← 当前全部条数
  start = max( 最近一次 harvested job 的 input_upto,   ← 磁盘:扫 memory-jobs/
               本会话打开时的消息条数,       ← 内存:会话装配时记一次
               0 )
  增量  = messages[start:end]
  job.json 记 {input_from: start, input_upto: end}
       —— 只有收割成 harvested,input_upto 才成为下次的起算点;
          failed 的不算,它覆盖过的内容下次自动重算进来
```

取 max 的三个来源各管一件事:

| 来源 | 管什么 |
|---|---|
| harvested job 的 input_upto(磁盘) | 上次巩固看到哪,接着看——含 job 在飞期间用户又聊的回合 |
| 本会话打开时的条数(内存) | resume 进来的旧历史**不当增量**(那些归会话巩固管) |
| 0 | 新会话从零开始 |

两个边界:

- **增量超过 40 条**:只保留最近 40 条,开头注明"更早 N 条未包含"——子代理据此知道上下文可能不完整;漏掉的部分由会话巩固兜底;
- **激活过视图**会让"当前有效历史"的条数跳变减少(如 182 → 95),旧游标可能大于当前条数 → start 用 `min(start, len(messages))` 截住,失准漏掉的部分同样由会话巩固兜底。

### 4.3 提示词骨架(回合巩固)

```
你是记忆巩固代理(自动模式)。下面是【对话增量】和【现有记忆清单】。
任务:判断增量里有没有"值得跨会话记住"的内容,有就落盘,没有就报告"无事可记"。

判断标准(四类):user(用户角色/偏好/背景)、feedback(对工作方式的纠正或确认)、
project(进行中的工作/决策及动机)、reference(外部资源指针)。
不该记:代码结构、文件路径、git 历史、修复过程、临时任务状态(读现状就能知道)。

动作规则:
- 漏记 → 用 memory 工具补记(frontmatter:description 具体;相对日期转绝对日期);
- 与现有记忆近似 → 同名覆盖更新合并,不要新建文件名;
- 禁止删除:该删的在报告里建议,不要执行;
- 宁缺毋滥:没东西可记就直说,不要为了交差硬记。

【现有记忆清单】…【对话增量】…

最后一条回复按固定格式输出报告:
新增: <名字 — 一句话理由>(没有写"无")
更新: <名字 — 改了什么>
删除建议: <名字 — 理由>
```

### 4.4 会话巩固的差异

输入第 2 段换成**会话日志尾部 N 回合拍平**(建议 20,派发时主进程自己读日志拍平,不依赖子代理节制),另加 consolidate 四步指令(定向→收集→固化→剪枝)。清单、协议、报告模板同上。

## 5. 安全与失效

1. **备份**:派发前两层记忆目录整体拷进 backup/(几十 KB),任何问题可回滚;
2. **禁删恢复**:提示词禁删(软约束),收割 diff 发现文件减少即从备份恢复 + 告警(硬执行);
3. **审计报告**:收割时产出"新增 X / 更新 Y / 恢复 Z"清单,print 给用户 + 落盘 report.md;
4. **缓存失效**:收割(含会话巩固补收)固定调 invalidate_memory_cache(),下一次请求自动注入最新索引——模型感知不需要通知消息;
5. **崩溃恢复**:主进程死则线程同死,子进程独立跑完;SESSION_START 扫 memory-jobs/,按子代理 pid 探活判定 running 的 job 是否已结束(§2.4 ③),补收 = diff 审计 + 恢复 + 删缓存;
6. **并发写加固**:save_memory 实施时改"临时文件 + os.replace"原子替换(Log 全量重写同款),消除与主线程 memory 工具并发写、以及缓存重算撞上写入的竞态。

---

## 6. 实施阶段划分

1. **run_subagent 异步化**:拆出 dispatch(Popen 返回)/ await_result(等待+取结论)原语,同步版组合两者(行为不变,现有测试全绿);
2. **job 线程框架**:线程函数骨架(§2.2 的七步)+ 内存单飞行闸 + job.json 读写;
3. **信号触发器 + 派发**:词表、冷却、两级游标(本 turn 计数 / 巩固覆盖点,§3.2+§4.2)、input.md 拍平;
4. **收割与审计**:diff 报告、删除恢复、invalidate_memory_cache、report.md;
5. **save_memory 原子写 + 覆盖保留原 created**;
6. **会话巩固 + SESSION_START 补收**(复用收割代码);
7. **测试**:mock 模型集成(派发→中途聊天→线程收割→记忆变化断言→缓存已删);禁删恢复;线程异常兜底;崩溃恢复(杀主进程→重开补收);单飞行(在飞时不重复派);词表误报路径。

## 7. 风险与开放问题

1. **记忆质量**:子代理判断比用户确认宽松——提示词宁缺毋滥 + 审计报告可见;不放心可加"回合巩固只建议、会话巩固才执行"的中间档;
2. **词表维护**:接受不完美,靠会话巩固兜底,不堆砌到失控;
3. **会话巩固读日志深度**:建议尾部 20 回合,可调;
4. **多终端同会话**:内存飞行闸只管本进程,磁盘 job.json 是第二道闸(派发前扫一眼 running 状态);
5. **默认开关**:两通道默认关,跑一段验证再议默认值。

## 8. 决策速览

| # | 决策 | 一句话理由 |
|---|---|---|
| 1 | 两种任务:回合巩固 + 会话巩固 | 每 turn 无条件派太贵;两级覆盖"即时补记"和"睡前总账" |
| 2 | 触发信号纯规则零调用 | 误报代价小、漏报有兜底 |
| 3 | job 线程等子进程,线程内收割 | 等待免费(收割在子进程退出瞬间)、共享缓存删了即生效;agent 循环留在子进程,隔离白送 |
| 4 | 工具只给 read/grep/memory | 写入只有 memory 一个通道且路径硬编码 = 硬沙箱 |
| 5 | 磁盘状态作崩溃兜底,内存闸管单飞行 | 正常路径不扫目录,崩溃路径有据可收 |
| 6 | 同一时刻最多一个记忆 job | 后台任务重了只会烧钱不会更好;内存闸一行判活 |
| 7 | 收割在线程里删缓存 | 同进程共享,下一次请求自动见新索引,无需通知消息 |
