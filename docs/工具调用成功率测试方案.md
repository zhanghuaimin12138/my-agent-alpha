# 工具调用成功率测试方案

> 结论先行:**在 mock 测试和 agent 任务评估之间补一层"真模型 × 单步调用"的专项测试**。
> 每道题 = 一句用户输入,期望恰好一次指定工具调用 + 指定参数;直接调 `llm.stream()`
> 走真实的流式拼装 + 解析链路,用纯代码判分,产出一张"从模型发起到参数正确"的
> 逐级漏斗表。不改核心代码,无新依赖,单模型一轮 5-15 分钟。

---

## 1. 定位:为什么需要这一层

项目里关于工具调用的测试现在有两层,中间有个洞:

| 层 | 驱动 | 回答的问题 | 现状 |
|---|---|---|---|
| A. 代码正确性 | mock 分片(手写假事件) | 给定模型输出,**我们的拼装/解析代码**行为对不对 | 已有,661 条测试(devlog 034 的 286 条锁解析器) |
| **本方案** | **真模型** | 模型在原生通道下,**实际**把工具调用发对的比例;损失发生在哪一环 | 本方案要新建 |
| B. agent 任务成功率 | 真模型 + 完整 chat 循环 | agent 端到端能不能完成任务 | [agent离线评估方案](agent离线评估方案.md)规划中,evals/ 未建 |

A 层测不出"模型的输出分布":mock 分片是手写的,真模型发的东西(参数转义、选哪个工具、
会不会只说话不调工具)A 层根本见不到。B 层能测到但太贵、判分面太宽,一次失败难以归因。

本方案就是 [agent离线评估方案](agent离线评估方案.md) 第 4 节"工具调用评测"一行的
**先行落地**:先搭最薄的一块,把"出题 → 跑真模型 → 判分 → 报告"的骨架跑通,
E1 的 agent 任务评估直接复用这套骨架。

## 2. 测什么链路(刻意不进 chat 循环)

```
get_prompt(native=True) + 题目   ← 和真机完全一致的系统提示词(全部工具说明)
    → llm.stream()               ← 真实网络请求,真实流式分片
    → 完整回复文本                ← 原样存档(归因的唯一依据)
    → ToolUse.iter_from_content() ← 真实解析
    → 判分(纯代码,无 LLM 裁判)
```

不执行工具(无副作用,不需要沙箱)、不走确认链、不喂结果回去。
这意味着几个盲区,如实列出:

| 盲区 | 为什么测不到 | 怎么补 |
|---|---|---|
| nudge 兜底(漏写调用提醒) | nudge 在 chat 循环里 | 5 题 chat() 完整对照(E1 一起做) |
| 多轮纠错(报错后重试) | 只有单轮 | 归 B 层 `error_recovery` 分类 |
| 执行层成功率(工具真跑起来) | 不执行 | 归 B 层文件状态断言 |

## 3. 判分:五级漏斗,逐级归因

一次调用要过五道门,每道门单独计数,通过数逐级递减形成漏斗——
**两级之间的差值 = 这一环损失了多少**,这是本方案最核心的产出:

| 级 | 门 | 没过的含义 |
|---|---|---|
| S0 | 请求成功(没超时/限流) | 基础设施问题,**不计入成功率**,单独归类 |
| S1 | 回复里有原生调用行(正则或解析出 ≥1 条调用) | 模型没发调用(含"只说话不干活") |
| S2 | 解析出 ToolUse 且工具名 = 期望 | 走错通道(模型写了 markdown 围栏)或格式坏 |
| S3 | kwargs 过参数表校验(必填齐全、类型对、无未知键) | 模型发的参数不合法 |
| S4 | kwargs 与题目期望匹配 | 参数发错值、选错工具的意图问题 |

- **成功率口径 = S4 通过率**;S0 失败(网络/限流)绝不混进来,否则网络抖动会被当成"模型变笨"。
- 走错通道(S2 差值)单独记一栏:模型写了 shell 代码块(markdown 通道)不算失败,算**通道偏移**——
  这是"原生 vs markdown"两条通道真实使用率的直接数据。
- **静默丢失归因**:解析层已知会静默丢弃坏 JSON(缺陷清单 5/6 条)。每题把完整回复
  原文存档,事后数"原文里 `@xxx(` 行数 vs 解析出的调用数":前者多 = 我们丢了,
  相等 = 模型没发。没有原文,这个问题永远扯不清。

## 4. 题目集设计

不引 YAML,Python 直接定义(与离线评估方案同款纪律):

```python
# evals/toolcall_tasks.py(示意)
@dataclass(frozen=True)
class CallCase:
    id: str  # "tc-read-001"
    tool: str  # 期望工具名
    prompt: str  # 发给模型的用户输入
    want: dict[str, str]  # 期望 kwargs(键值等价即过)
    level: str  # D1-D5 难度层
```

9 个可运行工具(append/edit/grep/memory/read/save/shell/subagent/todo)全覆盖,
每工具 ≥3 题,共 30 题。分五个难度层,层的设计直指已知痛点:

| 层 | 考什么 | 例题 |
|---|---|---|
| D1 单参数直给 | 基本盘:会不会发调用 | "看一下 config.toml 的内容" → `read {"path": "config.toml"}` |
| D2 内容参数转义 | 参数里有引号/反斜杠/换行/中文/emoji —— devlog 034 手抄都连错三次的转义,真模型重点雷区 | 保存一段含 `"` 和 `\n` 的文本 → save 的 content 逐字符等价 |
| D3 可选参数与默认 | 不给的参数不该瞎编 | "在当前目录找 TODO" → grep 只给 pattern,glob/path 不出现或为空 |
| D4 工具选择歧义 | 多个工具都能干,选没选对 | "把 a.txt 里的 TODO 换成 DONE" → 选 edit 而不是 save 重写整个文件 |
| D5 并行多调用 | 一条回复发多个调用,拼装的 index 分流 + call_id 配对 | 一次保存两个文件 → 两条 save,参数各自正确 |

出题纪律:期望参数**手写死**,不从模型输出推导(和 devlog 034 的"三件套"教训一致:
自己出题自己答 = 没有独立性)。

## 5. 运行器与产物

先做单文件 `evals/toolcall.py`(题目 + 判分 + 运行一体,约 700 行);
等 E1 的 agent 任务评估落地时再按 tasks/runner/metrics 拆开共用。
放 `evals/` 而不是 `scripts/`:这是"考卷",不是开发辅助工具,和离线评估方案同一家。

```
evals/
├── toolcall.py                    # 出题 + 判分 + 运行(单文件起步)
└── toolcall_results/
    └── 2026-1024-<随机码>/        # 一次运行一个目录
        ├── summary.md             # 人看的报告(漏斗表 + 按工具/难度/模型)
        ├── summary.json           # 机器可读(版本对比用)
        └── cases/
            └── <题id>.<第几次>.md  # 每次调用:题目 + 完整原文 + 解析结果 + 判分明细
```

- 复用现成零件:`get_prompt(tools, native=True)`、`llm.stream()`、
  `ToolUse.iter_from_content()`、`resolve_model()`,一行核心代码不用改;
- `summary.json` 里记**工具提示词的指纹**(`tools_native.json` 内容哈希,
  devlog 033 的导出脚本就是为这个准备的):两次 run 指纹不同,成绩不可直接对比,
  报告里要标出来;
- 命令形态:`uv run python -m evals.toolcall --model glm --repeat 3 --tools read,save`,
  支持按模型、按工具、按难度过滤。

## 6. 指标与报告

- **总成功率(S4)+ 漏斗表(S1→S4 各级通过数)**:损失集中在哪一环,一眼看出;
- 三维切分:按工具 × 按难度 × 按模型(四家:glm / deepseek / moonshot / dashscope);
- **pass@1 与 pass@3**(同一题独立跑 3 次:三次平均 = 稳定水平;
  至少一次成功 = 上限水平)——应对模型输出随机性,单次成绩不可信;
- 失败分类计数:没发 / 通道偏移 / 参数不合法 / 参数错值 / 工具选错;
- 跨 run 对比:改提示词或换模型后重跑,`summary.json` 对出每题旧→新,
  和 `uv run pytest` 之于代码一样,成为提示词改动的"回归测试"。

成本估算:系统提示词 + 工具 schema 约 9KB(≈3-4k token),输出每次几百 token;
30 题 × 3 次 = 90 次调用/模型,约 35 万 token,单模型 5-15 分钟、几毛钱以内;
四家全跑一遍也就几块钱、一小时以内。

## 7. 判分器自身的测试(防成绩造假)

判分器是代码,也会有 bug,而它一错成绩就是假的。给它配一个单元测试
`tests/unit/evals/test_toolcall.py`,用手写的假回复(不走网络)测五道门:
一条全对、一条没调用、一条坏 JSON、一条缺必填参数、一条选错工具——
五条样例的判分结果逐一断言。判分器测试用 mock 是合理的(测的就是判分逻辑本身)。

## 8. 实施计划与验收

单会话可落地:

1. `evals/toolcall.py`:题目 30 题 + 五级判分 + 运行器 + 报告;
2. 判分器单元测试(5 条样例);
3. 真机跑 glm 一轮,人工核对全部失败题的原文(验证归因栏不胡说);
4. 写 devlog。

验收标准:

- 同配置重跑,成功率波动 ≤ 1 题(判分确定性);
- 报告能直接回答:哪个工具最弱?损失集中在哪一环?nudge 类"没发"占多少?
- 每道失败题都有原文存档,可人工复核。

## 9. 与项目纪律的相容性

- 不改核心循环、不改 src 任何文件:全部外围消费现有接口;
- 不产生 conversation.jsonl(不走会话,每题只存原文 + 判分 JSON),无主日志问题;
- 消息不可变 / call_id 纪律:D5 并行题的判分本身就是 call_id 配对的巡检;
- 真实成本如实入 devlog(按 AGENTS.md 忠实报告)。

## 10. 后续衔接(v2 及以后)

- 题目集从真机会话捞素材补充(离线评估方案"防过拟合"同款纪律)。
