## 2. 问题定义(为什么需要"多代理"审查)

单个主代理自己审自己的代码有三个结构性问题:

1. **上下文污染** —— 审查者应该只看改动,不该背着整场对话的立场
   (自己写的代码自己审,模型天然偏袒);
2. **关注点拥挤** —— 正确性、测试覆盖、可读性塞在一个提示词里互相挤兑,
   拆成独立代理后各自的提示词可以写得很锋利;
3. **责任与安全** —— 审查是"建议权"不是"修改权",给它独立身份才好把
   能力裁到最小(能看不能改)。

## 3. 终态架构(gptme 同构,五层)

### 3.1 总图(可默画在白板上)

```
                    ┌────────────────────────────────────────┐
                    │              /review main...HEAD        │
                    │        (或主模型完成任务后自派)          │
                    └───────────────┬────────────────────────┘
                                    │ 解析范围 + diff --stat 预校验
                                    ▼
        ┌─────────────── L3 编排层(异步,fire-and-forget)───────────────┐
        │  review() 立即返回 3 个 agent_id;注册表记录句柄(进程/日志/维度/状态) │
        │  预算闸:输出 token 预算 + 并发信号量(不超过 4)                  │
        └──────┬──────────────────┬──────────────────┬────────────────┘
               ▼                  ▼                  ▼
        ┌─ 正确性审查员 ─┐   ┌─ 测试审查员 ─┐    ┌─ 可读性审查员 ─┐
        │ 独立子进程      │   │ 独立子进程    │    │ 独立子进程      │   ← L1 执行单元
        │ 独立会话日志    │   │ 独立会话日志  │    │ 独立会话日志    │
        │ 工具=read,grep, │  │ 同左          │    │ 同左            │  ← L2 安全层
        │ shell(只读强制) │  │               │    │                │
        └───────┬─────────┘   └──────┬───────┘    └───────┬────────┘
                │ 完成时写日志,监控线程读到        │                │
                ▼                                ▼                ▼
        ┌─ LOOP_CONTINUE 钩子:"✅ 审查员 correctness 完成(7 条发现)" ─────┐
        │  (父会话的下一个模型步自然看到,主循环零改动)                      │
        └───────────────────────────────┬─────────────────────────────┘
                                        ▼ 全部完成
        ┌─ L4 聚合:确定性拼接(严重度排序)→ v2:合并代理去重终审 ─┐
        └───────────────────────────────┬─────────────────────────────┘
                                        ▼
                    报告:打印 + 回注父日志(主模型可接着"修第 2 条")

  中途干预(L3 控制通道):/review steer <id> "重点看并发" ─┐
                          /review cancel <id>            ─┼→ control.jsonl
                                                        ┘   → 子进程 STEP_PRE
                                                            钩子排空 → 干净退出
```

### 3.2 L1 执行单元:审查员 = 一类有"档案"的子代理

gptme 里叫 **profile(代理档案)**:一个名字对应一套
(工具白名单 + 系统提示词 + 模型 + 环境变量)。

**审查员的上下文 = 它日志里的六条开场消息,逐条(父会话一条都不进来)**:

| # | 消息 | 内容 |
|---|---|---|
| 1 | system | 身份 + 工具文档(**白名单裁剪后只剩 read/grep/shell 三个的文档**) |
| 2 | system | 当前时间 |
| 3 | system | 长期记忆索引 MEMORY.md(现有会话开场就注入,保持不动) |
| 4 | system | "# 审查员档案" + 审查方法论 + 报告格式(对应 gptme 的 profile 消息) |
| 5 | system | 收尾指令:报告 = 最后一条回复,输出后不再说话 |
| 6 | user | 审查任务:范围(git 命令原文)+ 未跟踪文件清单 |

(gptme 的构造顺序同构:基础上下文 → profile 提示词 → 专属记忆 →
可选父上下文 → 收尾指令 → user 任务,execution.py:485-655;
父上下文我们**永远不转发** —— 审查员不带立场是结构保证,不是提示词自觉。)

**日志布局,路径写死**:

```
~/.local/share/my-agent-alpha/projects/<workspace_key>/logs/     ← 会话根
└── subagent-<uuid4>/                                            ← 审查员会话目录
    ├── conversation.jsonl   # 主日志:六条开场 + 全部回合;只追加永不改写
    ├── meta.json            # 标题(命名钩子写;审查员标题≈报告摘要)
    ├── control.jsonl        # 控制通道:父追加、子排空,读完即删(M3)
    ├── .control.lock        # flock 锁,防写一半被读走半行(M3)
    ├── progress.jsonl       # 进度流,父监控线程 tail(M3)
    ├── subagent-meta.json   # 注册表持久化,父重启后认领(M3)
    └── stderr.log           # 崩溃诊断(M3)
```

**结果契约**:子代理的最后一条 assistant 消息 = 报告。
需要程序可解析时,启动参数加 `--output-schema`,让子代理按 dataclass
输出结构化 JSON(gptme 同款机制,schema 塞进收尾指令):

```python
@dataclass
class Finding:
    severity: Literal["高", "中", "低"]
    file: str; line: int; title: str; detail: str; suggestion: str
@dataclass
class ReviewReport:
    findings: list[Finding]; verdict: Literal["通过", "整改后可合", "打回"]
```

### 3.3 L3 编排层:异步三件套(派发即返 / 通知 / 控制)

**派发即返(fire-and-forget)**:`review()` 用 `subprocess.Popen` 起进程,
登记注册表,立刻返回 agent_id 列表。父会话不阻塞,用户可以继续聊。

**完成通知**:每个审查员一个监控线程,轮询进程退出 + 排空它的日志;
发现"最后一条 assistant 消息"就调用通知函数 → 往父会话的提示队列里塞
"✅ 审查员 X 完成(7 条发现)"。父会话的 LOOP_CONTINUE 钩子在回合之间
排空队列,于是主循环**一行没改**就看到了结果。

**控制通道(steer / cancel)**:每个审查员的会话目录下有一个
`control.jsonl`(旁边一个 `.control.lock` 做 flock 文件锁),
父侧持锁追加一行一条 JSON;子代理的 STEP_PRE 钩子(每次调模型前)
持锁整读 → 逐行解析(坏行跳过)→ **删掉文件**:

```json
{"op": "cancel", "queued_at": "2026-10-29T12:00:00+00:00"}
{"op": "steer", "queued_at": "2026-10-29T12:01:00+00:00", "content": "重点看并发部分"}
```

- `cancel` → 抛 SessionCompleteException,子代理走正常收尾路径
  退出(不是杀进程,日志完整、可审计);读文件失败也按 cancel 处理
  (fail-closed,gptme 原文注释就这么写的);
- `steer` → content 成为子代理下一次模型调用看到的 user 消息 ——
  中途改指示不打断工作。

这是 gptme"日志当唯一事实来源"哲学的延伸:**连控制指令也只是日志文件里
的一行 JSON**,没有 sockets、没有消息队列。

**预算与上限**:全机群输出 token 预算(超了拒绝新派发)+ 并发信号量
(同时存活的审查员 ≤ 4)。规模封顶在个位数,所以不需要更复杂的调度。

### 3.4 故障处理矩阵(面试加分点:每一行都有真实机制)

| 故障 | 机制 | 结果 |
|---|---|---|
| 审查员超时 | 看门狗计时器 kill 进程 | **从它的日志捞部分发现** —— 日志即事实,半成品也可回收 |
| 审查员崩溃 | 退出码非 0,stderr 尾部三行回传 | 父会话收到 ✗ 消息,其他维度不受影响(进程隔离红利) |
| 审查员跑偏 | steer 注入纠正 | 不打断,下一个模型步生效 |
| 审查员死循环 | cancel → 干净退出 | 日志完整可审计 |
| 预算耗尽 | 派发闸拒绝 | 明确报错,不静默烧钱 |
| 父进程重启 | 从各日志目录的元数据重建注册表 | 在跑的子代理被重新认领(gptme persistence 同款) |

### 3.5 安全纵深(四道闸,由外到内)

```
① 派发即审批     —— 人敲 /review 或主模型过确认链,批的是"整个审查行为"
② 工具白名单     —— 注册表层裁剪:审查员的表里根本没有 save/edit/memory
③ 只读强制 shell —— ALPHA_SHELL_READONLY=1:非只读命令(ls/git diff 级别之外)
                    直接拒绝。判不准 = 当不安全(fail-closed,与现有
                    is_readonly_command 同一姿态)
④ 灾难护栏       —— 优先级 200,rm -rf / 这类连 -y 也拦(已实现)
```

为什么强调工具层而不是提示词层:**提示词是建议,工具层是物理约束**。
提示词可以说"你是只读审查员",但只要 save 工具还在注册表里,
一个被误导的模型照样能写文件。

(顺带讲发现缺口的过程:我审查自己代码时发现 `-y` 模式下确认链
"走到链尾自动放行",`git checkout .` 这类会毁掉未提交改动的命令
能溜过去 —— 这正是 ③ 的由来。**在自己项目里找安全缺口并补上**,
比背十篇安全文章有说服力。)

## 4. 与 gptme 逐机制对照(证明"一样"而非"像")

| gptme 机制 | 本方案对应 | 状态 |
|---|---|---|
| profile(白名单+提示词+模型预设) | reviewer 档案(tools+env+prompt) | 设计 |
| fire-and-forget + 钩子通知 | Popen + 监控线程 + LOOP_CONTINUE 注入 | 设计(MVP 先同步) |
| control.jsonl + STEP_PRE 检查点 | 同名同位置,一字不差 | 设计 |
| --output-schema 结构化输出 | Finding/ReviewReport dataclass | 设计 |
| SubagentBudget + BoundedSemaphore | 输出预算 + 并发 ≤ 4 | 设计 |
| persistence.py 重启重建 | 日志目录元数据重建注册表 | 设计 |
| worktree 隔离 | 不需要(审查只读) | 有意省略 |
| 线程后端(ContextVar 隔离) | 不做,子进程一种后端 | 有意省略 |

有意省略的两条是加分话术:"gptme 支持线程/子进程/ACP 三种后端,
我只保留子进程 —— 审查场景不需要低延迟共享上下文,少一种后端就少
一整类隔离 bug。"

## 5. 三分钟讲稿(口语,按这个顺序讲)

"这个项目是我仿 gptme 写的个人 AI agent,核心是一条三层循环:
外层 REPL 收用户输入,中层'回合'反复做'模型生成 + 执行工具'直到模型
不再调工具,底层每一步都落一条不可变的消息日志。所有东西都长在这根
脊柱上 —— 确认、hook、压缩、子代理,全是外挂,主循环零特殊分支。

最近我给它加多代理代码审查。**为什么多代理**:自己审自己有立场污染,
三个维度挤一个提示词互相干扰,而且审查应该只有建议权没有修改权 ——
独立身份才好把能力裁到最小。

**审查员是什么**:一个子进程,自己的会话日志,工具白名单只剩
read、grep 和一个被环境变量钉死为只读的 shell —— 它能自己跑
git diff、git blame、grep 调用点,但物理上写不了任何文件。
结果就是它日志里的最后一条模型回复;要程序解析就让它按
dataclass 输出 JSON。

**编排**:三个维度并行派发,派完就返回,父会话继续可聊;
谁完成了,监控线程往父会话提示队列塞一条完成消息,hook 在回合间
排空 —— 主循环一行没改。中途可以往它的控制文件里追加
'转向'或'取消',它每次调模型前排空这个文件,取消是走正常
收尾路径退出,日志完整可审计。

**安全是四道闸**:派发即审批、工具白名单、只读强制 shell、
灾难护栏。这里有个我自己的故事:我审查代码时发现 -y 模式下
确认链走到尾部自动放行,git checkout 点这类命令能溜过去,
于是设计了只读强制模式,判不准就当不安全 —— 和我整个安全分级的
姿态一致。

**取舍**:gptme 是全功能编排器(三种后端、预算、持久化重建),
我的 MVP 是同步等一个,先求简单正确;这份终态方案是照着它的
实现逐条研究后写的,哪些抄、哪些有意省略(线程后端、worktree),
我都能说清为什么。"

## 6. 追问预案(每题 30 秒内答完)

**Q1 为什么子进程不用线程?**
进程崩了不连坐、无共享状态所以不存在隔离 bug;gptme 的线程后端要靠
ContextVar 一整套隔离工具注册表,复杂度换来的只是低延迟,审查场景不需要。

**Q2 怎么保证审查员不改代码?**
四道闸,重点讲工具层:白名单让它注册表里没有写工具;shell 被只读
强制模式钉死,非只读命令直接拒。提示词也写"你是只读审查员",
但那是第四道软闸 —— 提示词是建议,工具层是物理约束。

**Q3 并行了,共享状态怎么办?**
子代理之间零共享:各自进程、各自日志目录。唯一共享的是父侧注册表,
一把锁保护。聚合发生在全部完成之后,读的是各自的日志文件。

**Q4 结果怎么传回来?为什么不搞消息队列?**
日志文件就是接口:最后一条 assistant 消息是报告,监控线程读同一个文件
得知完成。控制指令也只是一行 JSON 追加。不加队列/socket 是刻意的 ——
"日志是唯一事实来源",文件天然可审计、崩溃后还在。

**Q5 审查员跑偏/啰嗦怎么办?**
steer:往 control.jsonl 追加指示,它下一次调模型就看到,不打断工作;
实在不行 cancel,走正常收尾退出,拿回部分结果。

**Q6 超时怎么处理?**
每审查员一个看门狗,超时 kill;但先从它的日志里捞已产出的发现 ——
半成品也可回收,这是日志即接口的红利。

**Q7 成本怎么控?**
机群输出 token 预算 + 并发信号量封顶 4;维度就 3 个,规模可控。
真正的大头是父会话本身的上下文,所以报告回注的是聚合后的一份,
不是三份原文。

**Q8 三个审查员的发现重复/矛盾怎么办?**
v1 确定性合并:按严重度、维度排序拼接,重复是可接受的噪音;
v2 加一个合并代理做去重和终审 —— 它只读三份报告,不读代码,很便宜。

**Q9 审查员给的发现是错的呢?**
报告强制"存疑"标注 + 严重度分级;审查是建议权,合不合由人
(或主会话带着完整上下文)裁决。结构化 schema 让每条发现可被
单独验证 —— 主模型可以拿着 file:line 去复核。

**Q10 为什么不用 LangGraph / AutoGen?**
这个项目的目的就是把 agent 的循环自己写一遍,框架把最值得学的
循环藏起来了;而且我的架构原则是横切关注点全走 hook、消息不可变、
日志唯一事实 —— 这些约束自己实现反而更短。真要选型时我也会问:
框架给的图编排、checkpointer,我的日志 + hook 已经覆盖了哪些。

**Q11 和 Claude Code 的 code review 比呢?**
机制同构:只读审查员、按维度并行、严重度报告。我比它多的约束是
子进程隔离;它比我强的是模型侧的审查质量 —— 这是模型问题不是架构问题。

**Q12 下一步?**
三件:合并代理(去重终审);增量审查(只审改动函数的调用邻域,
按调用图扩散);审查缓存(同一 diff 不重审)。

**Q13 fire-and-forget 之后,父代理在干嘛?怎么等子代理?**
三层。回合内:模型显式调 wait,阻塞在工具执行里,超时返回状态再等
(gptme 主模式);回合边界:LOOP_CONTINUE 钩子排空完成队列,把
"✅ 审查员完成"作为 user 消息回灌提示队列,循环自然续跑;空闲态:
队列空但有子代理在跑,主循环阻塞在完成队列上 —— 这就是"等待状态",
事件到达变成一条 user 消息落日志、开新回合,**恢复循环 = 追加一条消息**。
关键设计:完成事件的唯一去向是队列(不许旁路 print),put 在 get 之前
还是阻塞中都能拿到,没有"检查后阻塞"的丢事件窗口。gptme 的 CLI 反而
没做第三层(坐回输入提示符傻等,server 才有唤醒),这是我们比它多的地方。

## 7. 可能被要求现场写的代码(预热)

只读强制钩子(全部新机制里最核心的 ~15 行,值得能默写):

```python
def strict_readonly_hook(tooluse: ToolUse) -> ConfirmationResult | None:
    """ALPHA_SHELL_READONLY=1 时,shell 里非只读命令一律拒绝(fail-closed)。"""
    if os.environ.get("ALPHA_SHELL_READONLY") != "1":
        return None                      # 开关没开,行为不变
    if tooluse.tool.name != "shell":
        return None
    command = tooluse.kwargs.get("command") if tooluse.kwargs else tooluse.content
    if command and not is_readonly_command(command):
        return ConfirmationResult("skip", message="审查代理只能跑只读命令")
    return None
```

注册一行:`register_confirm_hook("strict_readonly", strict_readonly_hook, priority=15)`
(只读放行 10 之后,链尾自动放行之前)。
