# llm-layer

## 目的
gptme 的 LLM 客户端层(gptme/llm/,约 1 万行)是 agent 核心(消息、工具、聊天循环)与所有 LLM 后端之间的唯一接缝(seam)。它只暴露一个入口点 `reply()`(返回一条已完成的 `Message`):对上层隐藏 provider 路由(Anthropic SDK 路径 vs 一条由约 14 个 provider 加自定义/插件 provider 共享的 OpenAI 兼容路径);在 gptme 的规范文本格式(canonical text format,即 `<think>` 块和 `@tool(call_id): {args}` 工具调用)与各 provider 的线上格式(wire format)之间做双向转换;一边流式产出 token 一边在终端实时渲染,并支持提前中断去执行工具调用;按请求跟踪用量/费用;把模型名解析为丰富的元数据(上下文窗口、价格、能力);并独立于各家 SDK 自行掌管重试/退避(retry/backoff)策略。

## 关键抽象
- **reply(messages, model, stream, tools, ...) -> Message** —— gptme/llm/__init__.py:362。代码库其余部分唯一调用的函数。触发 GENERATION_PRE 钩子,复制消息,用 mark_llm_reply_origin 给 provider 异常打标,然后委托给 _reply_after_hooks,由它挑选 _chat_complete(返回 (str, MessageMetadata))或 _reply_stream(返回 Message)。校验 max_tokens>0。
- **Provider / BuiltinProvider / CustomProvider** —— models/types.py:51-100。Provider = BuiltinProvider | CustomProvider,其中 BuiltinProvider 是 16 个名字构成的 Literal('openai'、'openai-subscription'、'anthropic'、'azure'、'openrouter'、'requesty'、'gptme'、'gemini'、'groq'、'xai'、'grok-subscription'、'deepseek'、'moonshot'、'nvidia'、'local'、'mock'),CustomProvider 是面向用户配置或 entry-point provider 的 str 子类。get_provider_from_model(llm/__init__.py:483)拆分 'provider/model',并把未知但已配置的名字包成 CustomProvider。关键的路由分叉:PROVIDERS_OPENAI(types.py:103,14 个 provider)全部共享 llm_openai;只有 'anthropic'、'openai-subscription' 拥有自己的线上格式;'mock' 是进程内的。
- **ModelMeta(frozen dataclass)** —— models/types.py:134。字段:provider、model、context、max_output、supports_streaming/vision/reasoning/responses_api/parallel_tool_calls/strict_tools/mid_system、price_input/price_output(美元/百万 token)、knowledge_cutoff、deprecated、default_tool_format、preferred_edit_format('diff'|'whole')、pricing_type('per_token'|'subscription')。属性 `.full` = 'provider/model'。整个层级中的路由决策、费用计算、工具格式选择和能力门控都由这一个对象驱动。
- **get_model(model: str) -> ModelMeta** —— models/resolution.py:176 -> _resolve_model(183)。对未知模型从不抛错;依次回退:静态 MODELS 精确命中 -> 动态 API 拉取(openrouter/gptme)-> 别名表 -> 日期后缀剥离(-20250929)-> 按 knowledge_cutoff 的同家族最近匹配 -> 推荐模型 -> 通用 128k 兜底。在 178 处应用 infer_supports_mid_system(检测 Qwen3.5)。这种"永远能解析"的设计意味着新的 provider 模型在静态字典更新之前就能工作。
- **_StreamWithMetadata** —— llm/__init__.py:648。包装 Generator[str, None, MessageMetadata|None];__iter__ 从 StopIteration.value 捕获生成器的返回值作为 .metadata,并回退到共享的 _partial 字典(Anthropic message_start 的用量)或 {'model': model}。正是这个技巧让各 provider 的 stream() 函数可以是"返回元数据的普通生成器"。
- **Provider 的 stream()/chat() 生成器契约** —— 每个 provider 模块都导出 chat(messages, model, tools, output_schema, max_tokens, temperature, top_p) -> tuple[str, MessageMetadata|None] 和 stream(...) -> Generator[str, None, MessageMetadata|None],以 gptme 的规范格式产出纯文本块。规范格式:推理内容包裹在 <think>...</think> 中,工具调用写作 '@name(call_id): {json-args}'。所有下游解析(ToolUse.iter_from_content)都只针对这一种格式工作,与 provider 无关。
- **@retry_on_openai_error / @retry_generator_on_overloaded 装饰器** —— llm_openai.py:939/971 与 llm_anthropic.py:521/553。包装 chat 和 stream。生成器变体只在尚未产出任何内容时才重试(has_yielded 标志,llm_openai.py:1003),以避免重复输出。经 retry_delay_for_error 做退避并尊重 Retry-After;可经 retry_abort.backoff_wait 中止。

- **ProviderPlugin** —— models/types.py:193。经 entry-point 声明的第三方 provider:name、api_key_env(可选)、base_url、models 列表、可选的 init(config)。经 importlib.metadata 的 'gptme.providers' 组发现(provider_plugins.py:69);在 llm_openai.init 中自动初始化为 OpenAI 兼容客户端(llm_openai.py:673-698)。

## 设计亮点
- 唯一的规范内部格式:provider 产出纯文本,其中推理是 <think>...</think>,工具调用是 '@name(call_id): {json}'。每个 provider 的 stream() 产出的都是它,终端/执行器/解析器消费的也只有它,而 _handle_tools 在下一轮把它转换回各 API 的原生形态。这一个决定就避免了 N 个 provider x M 个消费者演变成 N*M 个转换器。
- 生成器返回值元数据协议:provider 的 stream() 生成器把 MessageMetadata 字典作为 `return` 值;_StreamWithMetadata 从 StopIteration.value 捕获它;_drain_toolbreak_stream 在提前工具中断后专门重新消费生成器以收割最终的用量事件,并以共享的 _partial 字典(Anthropic message_start)作兜底 —— 即使流被中断,用量/费用也得以保全。
- break_on_tooluse:借助格式感知的断点字符做字符级扫描(_tooluse_break_check_char),agent 一旦有一个可运行的工具调用完整就能停止生成并立即执行它,而不必等待完整响应;支持并行工具调用的模型经 ModelMeta.supports_parallel_tool_calls 退出该行为。
- "永远能解析"的模型查找:get_model 从不失败 —— 别名表、日期后缀剥离、按 knowledge_cutoff 的家族前缀最近匹配、动态 API 拉取,最后是通用 128k 兜底。新的 provider 模型第一天就能带着近似元数据工作。
- 重试所有权:每个客户端都设 SDK_MAX_RETRIES=0,让 gptme 的装饰器独占退避策略(防止重试相乘),累计预算约 5 分钟,尊重 Retry-After 头,生成器只在首次产出前重试,且退避睡眠可按线程中止以便测试清理(retry_abort.py 的 generation 计数器 + Event)。
- 一切皆惰性:provider 函数走 PEP 562 模块 __getattr__,_LazyClient 推迟 openai SDK 导入,只对活跃 provider 做按 provider 的 init —— CLI 启动保持快速。
- 构造时盖戳的静态元数据字典:MODELS 经 _stamp_provider 一次性构建,给 OpenAI 兼容 provider 盖 default_tool_format='tool'、给有文档记载的 provider 盖 supports_parallel_tool_calls,因此这些标志不会偏离原始的逐模型表。
- Anthropic 思考签名往返:签名以 <!-- think-sig: ... --> 注释的形式嵌在存储消息文本的 <think> 块内,下一次请求时再提取成带签名的 thinking 块 —— 在不改动 Message 模式的前提下满足 Anthropic "缺签名即 400" 的规则。
- 在单个函数里归一化 4 种线上形态(Chat Completions、Responses API、OpenRouter 记账、裸 Codex SSE 字典)的用量,经鸭子类型的 _obj_get 实现,未缓存输入按 prompt - cache_read - cache_create 计算,费用计算对各 provider 保持一致。
- 费用即元数据 + 遥测副作用:_record_usage 既写 MessageMetadata(持久化到 conversation.jsonl),又喂给 record_llm_request -> CostTracker + 缓存命中率启发式;订阅制模型保留 token 计数,但经 pricing_type 记费用 0。
- 提示词缓存是显式的:apply_cache_control 在 system prompt、临时消息之前的稳定边界、以及最后两条 user 消息上放置 ephemeral 断点 —— 对经 OpenRouter 服务的 Anthropic 模型同样适用。
- OpenAI 路径是万能适配器:14 个内置 + 自定义配置 provider + entry-point 插件全部复用一个以 Provider 为键的客户端注册表,差异仅在 init() 时解析的 api_key/base_url。

## MVP 指引
- 首先复刻:双函数 provider 契约(chat -> (str, metadata)、stream -> Generator[str, None, metadata])加一个路由器(get_provider_from_model + if provider == 'anthropic' elif openai-compatible)。这就是承重的 20%。
- 立即照搬规范文本格式:<think> 块和 '@tool(call_id): {args}'。从第一天起就围绕它设计你的 Message 和工具解析器;事后到处补装原生 tool-call 对象的代价很高。
- 照搬 _StreamWithMetadata + 把元数据作为生成器的返回值返回。它只有约 40 行,却让流式用量追踪变得轻而易举。
- 从恰好两个 provider 起步:anthropic(原生 SDK)和一个 OpenAI 兼容的(openai 或 openrouter)。尽早加上按 base_url 的自定义 provider 支持,因为它几乎免费(clients 字典里再加一个条目而已)。
- 模型元数据:先从一个小的静态字典 {name: {context, price_in, price_out, supports_reasoning, max_output}} 和带宽松回退链的 get_model() 开始;只在支持 openrouter/local 之后再加动态 /models 拉取。
- 实现成对的重试装饰器(函数版 + 带 has_yielded 守卫的生成器版),并关闭 SDK 重试;Retry-After 解析和可中止退避可以推迟。
- 流式工具调用提取:对原生工具增量,在 func.name 上发出头部并增量流出参数 —— 不要缓冲整个调用。用于提前中断的 ToolUse.iter_from_content 流式解析是 v2 特性;v1 可以等流结束再处理。
- 初期跳过:面向严格 provider 的消息变换(_fold_mid_system、deepseek reasoning_content 恢复)、三个订阅/OAuth provider(openai-subscription、grok-subscription、gptme cloud)、经 entry points 的 provider 插件、validate.py、local_discovery.py、思考签名保存(只在 Anthropic 扩展思考多轮时需要)、快速模式、think-sig 显示抑制。
- 尽早但小规模地加上:面向 Anthropic 的 apply_cache_control(4 个缓存断点是值得做对的硬 API 约束)、按元数据表逐 token 计费的 _record_usage,以及用于门控 break_on_tooluse 的 ModelMeta.supports_parallel_tool_calls。
- 尽早加 mock provider(约 30 行)—— 它让 LLM 层之上所有环节的测试既确定又无需网络。

## 开放问题
- gptme/llm/ 中任何地方都没有 embeddings 支持 —— 检索/嵌入类功能(如果有的话)位于本层之外(例如 gptme/knowledge/),因此需要 embeddings 的重实现应新增一条独立的客户端路径,而非扩展这些 provider 模块。
- `reply()` 签名接受 workspace/output_schema/on_token/on_thinking,而 output_schema(结构化输出)有三种不同实现:OpenAI 的 json_schema response_format、Responses API 的 text.format、以及 Anthropic 的伪工具技巧(_make_schema_tool + _inject_schema_instruction)—— 刻意没有尝试统一抽象。
- 限流只做被动处理(429 时带 Retry-After 重试);本层没有客户端限流器或请求队列。
- gptme-cloud 路由(_gptme_backend)检查解析后的 ModelMeta.model 前缀,来为网关模型决定走 anthropic-SDK 还是 OpenAI-SDK;这是 llm_gptme.py 模型列表与路由器之间基于字符串约定的耦合,若网关增加后端就需要重新设计。
- 工具格式是双轨的:模型可以用原生 'tool' 格式(tool_calls),也可以用纯文本中的 markdown/xml 工具块;ModelMeta.default_tool_format 和 get_tool_format() 按模型选择,流式断点检查和 _handle_tools 必须两者都处理 —— 重实现可以只选原生格式来简化。
- llm_openai.py 保留了并行的两套流式循环(Chat Completions 在 1679-1754,Responses 在 1482-1558 + 共享的 openai_responses._stream_responses_events);文件自己的注释(1493-1501)提到未来可能合并 —— 若为新构建做合并,选 Responses 循环。
