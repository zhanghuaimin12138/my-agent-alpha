# tools-system

## Purpose
The gptme tool system is the agent's capability layer: a declarative ToolSpec registry that (a) renders tool documentation into system prompts in three formats (markdown code blocks, XML tags, and native function-calling), (b) parses assistant output back into ToolUse calls in any of those formats, (c) executes them through a uniform `execute(code, args, kwargs) -> Generator[Message]` interface wrapped in hooks (confirmation, telemetry, pre/post execution), and (d) ships ~40 concrete tools — a stateful persistent-bash shell with allowlist/denylist/shellcheck/flag-table safety, an in-process IPython REPL, file read/save/edit tools, a functions-only subagent orchestrator that spawns nested agents in threads, subprocesses, or via ACP, a browser tool, and an MCP adapter that converts external MCP servers into native ToolSpecs. The same ToolSpec abstraction serves model-facing docs, execution dispatch, user-facing slash commands, and lifecycle hooks.

## Key Abstractions
- **ToolSpec** — frozen dataclass, gptme/tools/base.py:467. Fields: name, desc, instructions, instructions_format: dict[ToolFormat,str] (per-format override replacing the auto function listing), examples: str | (tool_format)->str, functions: list[ToolFunction]|None (registered into IPython, not directly executable), init: ()->ToolSpec (called at load, may return a modified copy — python.py rewrites its instructions this way), execute: ExecuteFunc, block_types: list[str] (markdown langtags + API names), available: bool|callable + available_hint, parameters: list[Parameter], load_priority (sorting), disabled_by_default, requires_tools (companion closure), is_mcp, hints: frozenset (e.g. 'read-only','destructive','code-exec' — used by hint: allowlists), read_only, hooks: dict[name,(HookType.str, fn, priority)], commands: dict[str,Callable] (slash-commands). __eq__ by name; __lt__ by (load_priority, name).
- **Parameter / ToolFunction** — Parameter(name, type: str, description, enum, required) — a flat, hand-written mini-schema; there is NO automatic inference for ToolSpec.parameters, but ToolFunction.from_callable (base.py:235) infers Parameter lists from inspect.signature annotations (derive_type renders Literal/Union/generics concisely) + first docstring paragraph. ToolFunction(name, fn, description, group, parameters, hints) normalizes bare callables passed via the plugin API.
- **ExecuteFunc** — The universal tool entry: execute(code: str|None, args: list[str]|None, kwargs: dict[str,str]|None) -> Generator[Message] | Message. Three channels arrive here: markdown codeblock → (content=code, args from langtag suffix); XML → (content=inner text, args from attributes); native tool call → (kwargs JSON dict, code/args None). Tools yield system-role Messages as results; generator form enables streaming/multi-message output.
- **ToolUse** — frozen dataclass (base.py:838): tool, args, content, kwargs, call_id, start (char offset for ordering), _format. iter_from_content() is the single parser for all three formats; execute() is the runtime wrapper (hooks TOOL_EXECUTE_PRE/POST, telemetry trace + record_tool_call with duration/success, _current_tool_use ContextVar, call_id stamped ONLY on the last yielded message so Responses-API function_call_output pairing stays 1:1); _to_params() maps positional args onto Parameter slots for display/serialization; to_output() renders the call back into a prompt example in any format.
- **ToolFormat** — Literal['markdown','xml','tool'] (base.py:58) with a module-global default 'markdown' and set_tool_format(). Same ToolSpec renders docs and accepts calls in all three; the LLM layer picks per model. Native 'tool' parsing coexists with markdown parsing (impersonate/user blocks) and skips matches inside fenced codeblocks.
- **Registry (ContextVar tool state)** — gptme/tools/__init__.py keeps loaded tools, the availability cache, init flag, and session allowlist in ContextVars so every thread/asyncio context (server conversations, subagent threads) gets an independent toolset; init_tools() is the thread-safe loader (allowlist expansion incl. presets/globs/hint: patterns, file-path tools, requires_tools fixpoint); load_tool/unload_tool mutate mid-conversation with hook registration/unregistration.
- **Confirmation hook chain** — TOOL_CONFIRM hooks return ConfirmationResult|None in priority order (highest first, None falls through). Tool-owned auto-approvers (shell allowlist, prio 10) run before CLI/server prompt hooks; ConfirmAction.EDIT returns edited_content which replaces the command before execution. read_only tools bypass the chain but consult guardrail hooks directly.
- **ShellSession** — Persistent bash process with a sentinel-delimited protocol (unique per-command START/END markers + ReturnCode/PWDHEX trailer), cwd tracked out-of-band via hex-encoded `pwd -P`, env/cwd snapshot file for crash recovery, stdin hardening (< /dev/null injection via tree-sitter), timeout ladder (kill children → grace → killpg → restart), 32MiB byte cap, and soft-timeout promotion of the whole session into a BackgroundJob.
- **BackgroundJob** — shell_background.py:91 — registered process (own pgid) with reader thread, locked output buffers, conversation scoping, and kill/close/output callbacks; the unified representation for both explicit `background:true` jobs and promoted foreground commands; completions are delivered into the conversation by step.pre/loop.continue hooks.
- **Subagent orchestration** — Functions-only ToolSpec; subagent(agent_id, prompt, ...) returns None immediately (fire-and-forget). Backends: thread (re-entrant chat() with isolated ContextVar toolset and profile-enforced allowlist), subprocess (`python -m gptme -n` with prompt on stdin, progress via logdir/progress.jsonl), ACP (external harness). Results cached first-writer-wins; completions queued and delivered by hooks; cancel/steer via logdir control.jsonl + STEP_PRE checkpoint; SubagentBudget + BoundedSemaphore cap fleet cost/concurrency; metadata persisted in the child's logdir for restart rehydration.
- **MCP adapter** — create_mcp_tools(config) converts each remote MCP tool into a first-class ToolSpec named 'server.tool' with Parameters lifted from inputSchema and a closure execute that marshals JSON content → client.call_tool; ToolAnnotations become hints so existing allowlist/guardrail machinery applies to remote tools unchanged.

PROMPT SIDE: for markdown/xml models, prompts/templates.prompt_tools (:418) calls tool.get_tool_prompt(examples, tool_format) → '## name / **Description** / **Instructions** / ### Examples' or the XML <tool> wrapper; instructions come from get_instructions(format) which prefers a per-format override (needed to fit OpenAI's 1024-char limit) else appends get_functions_description(). For native tool calling, llm_anthropic._spec2tool (:1328) / llm_openai / openai_responses._tool_spec_to_responses_tool (:174) convert the SAME spec into API tool params via parameters2dict (llm/utils.py:92), with name = block_types[0] when present. CALL SIDE: model output arrives as an assistant Message; chat.py:983 calls execute_msg(msg). ToolUse.iter_from_content (base.py:1082) parses: markdown → Codeblock.iter_from_markdown + langtag lookup (get_tool_for_langtag __init__.py:543, e.g. ```shell ls```); xml → lxml/etree walk of <tool-use>/<function_calls>; tool → regex `@name(call_id): {` + brace matching + json_repair.loads, skipping fenced-codeblock ranges. EXECUTION: execute_msg (:459) materializes all ToolUse, checks is_runnable, wraps each in terminal-state title and timing, and calls ToolUse.execute (:848): trigger TOOL_EXECUTE_PRE hooks → set _current_tool_use ContextVar → call tool.execute(content,args,kwargs) → stream (or buffer when call_id set, stamping call_id+tool metadata on the last message only) → record telemetry → trigger TOOL_EXECUTE_POST. CONFIRMATION happens inside each tool (not in dispatch): shell/save/append wrap their impl in execute_with_confirmation (util/ask_execute.py:69) → get_confirmation (hooks/confirm.py:186) → TOOL_CONFIRM hook chain, where shell_allowlist_hook (shell_validation.py:770) auto-approves allowlisted commands and CLI/server hooks prompt the human (y/n/c/e/auto). SHELL DETAIL: execute_shell (shell.py:3287) intercepts job-management commands, runs shellcheck and the denylist, then execute_shell_impl (:2885) races the command against the 120s foreground timeout on a worker thread; on timeout the live ShellSession is registered as a promoted BackgroundJob and a 'Promoted' message is yielded; otherwise ShellSession.run (:771) splits the script (tree-sitter + bash -n), writes the sentinel-wrapped command to the persistent bash, and _read_output_unix (:1688) polls fds under byte/timeout limits, tracks cwd from the ReturnCode/PWDHEX trailer, and streams output live; _format_shell_output (:2736) token-truncates (2000/8000 head/tail) after saving the full output to the conversation logdir. RESULT: yielded Messages (role 'system', call_id when structured) are appended to the log and converted per provider (Anthropic tool_result blocks llm_anthropic.py:1104; OpenAI role:'tool' llm_openai.py:1824 with orphan/buffering guards). SUBAGENT FLOW: model writes an ipython block calling subagent('id', 'task', use_subprocess=True); python.py executes it in the REPL; api.subagent (:163) validates, isolates (optional git worktree), and dispatches to _run_subagent_subprocess (:488) — `python -m gptme -n --no-confirm --tools +complete,+clarify,+progress`, prompt on stdin — or _create_subagent_thread (:159) — clear_tools(), profile-filtered set_tools(), fresh prompt via get_prompt(), then chat(..., output_format='quiet'). The child finishes by emitting a `complete` block; its monitor thread reads the log, caches ReturnType, and calls notify_completion (hooks.py:262) which either wakes the server session or queues for _subagent_completion_hook, so the parent's next model step sees '✅ Subagent X completed: <summary>'. MCP FLOW: config-listed servers are connected at discovery; each remote tool becomes ToolSpec 'server.tool' whose execute parses JSON content and calls the MCP client; the 'mcp' tool's slash-commands load/unload servers at runtime (load_tool path).

## Design Highlights
- One ToolSpec drives everything: model docs (markdown/xml/native), execution dispatch, confirmation policy (hints, read_only), slash-commands, hooks, and IPython functions — adding a tool never touches the chat loop.
- Triple-format call parsing with one dataclass: ToolUse.iter_from_content handles markdown langtags, XML (two dialects, lxml with stdlib fallback), and native `@name(call_id): {json}` with brace-counting + json_repair and fenced-codeblock exclusion — so the same agent core works with weak models (markdown), XML-preferring models, and OpenAI/Anthropic native tool calling.
- instructions_format['tool'] override exists specifically because OpenAI caps function descriptions at 1024 chars (#1697): tools ship a compact native-mode summary while keeping rich markdown docs.
- Confirmation as a priority-ordered hook chain returning ConfirmationResult|None (first non-None wins): tool-specific auto-approvers (shell allowlist at prio 10) run before CLI/server prompts, and ConfirmAction.EDIT lets the human rewrite the command before it runs.
- Permitted-flag whitelist instead of a forbidden-flag blacklist (shell_flags.py): each allowlisted binary declares the flags it may be auto-approved with; an unknown flag falls through to confirmation, not a block. Fails closed without being annoying.
- Persistent-shell sentinel protocol: per-command nanosecond-unique markers plus ReturnCode/PWDHEX-in-hex trailer make output spoofing and stdout-merging impossible, and let gptme track cwd/env without chdir; a snapshot file (cd + export -p) restores state after the shell dies, and the model is explicitly told what was lost.
- Foreground-to-background promotion: instead of killing a slow command, after the soft timeout gptme registers the still-running shell session as a BackgroundJob (with kill/close/output callbacks into the live session) and hands the model a new one — the result is injected by a step.pre hook when it finishes.
- call_id discipline: execute_msg and ToolUse.execute guarantee every structured tool_use gets exactly one paired result (error results for non-runnable tools, drain-on-interrupt), preventing Anthropic/OpenAI 400s; the tool's real output is stamped as the function_call_output while earlier warnings become context.
- ContextVar-everything: tool registry, loaded tools, shell session, workspace cwd, and hook registrations are context-local, which is what makes server multi-conversation isolation and in-process subagent threads safe without locks on hot paths.
- Functions-only tools (subagent, browser): no execute at all — functions are injected into the IPython namespace by python.py's init(), so the model composes them in code (loops, budgets, pipelines) instead of one-shot JSON calls; as_function_subtoolspecs/from_function provide the escape hatch to expose a single function as its own tool.
- Subagent completion via hooks (loop.continue/step.pre) rather than blocking waits: fire-and-forget with automatic '✅ completed' injection, cross-process cancel/steer through logdir control.jsonl + STEP_PRE checkpoints, and restart-safe metadata persisted in the child's logdir.
- requires_tools companion closure: a tool can declare dependencies (hashline_edit needs read) that are loaded alongside it but never bypass the operator allowlist — capability boundary preserved while keeping convenience.
- {% if tools: a,b %} templating in tool docs: instructions can conditionally mention other tools only when those are actually loaded, keeping prompts truthful per session.
- MCP tools are first-class ToolSpecs (server.tool naming, hints from ToolAnnotations), so allowlists, guardrails, prompts, and confirmation all apply to remote tools with zero special-casing.

## MVP Guidance
- Phase 1 — core: copy the ToolSpec/Parameter/ToolUse triad with only name, desc, instructions, examples, execute, block_types, parameters, read_only, hints. Implement execute(code,args,kwargs)->Generator[Message], ToolUse.iter_from_content for markdown only (fenced codeblocks + langtag→tool lookup), execute_msg with basic error handling, and a module-scan registry (or an explicit list — discovery via dir() is a nice-to-have). Skip ContextVars initially (single session), add them when you add concurrency.
- Phase 2 — native tool calling: add parameters2dict (trivial) and a _spec2tool per provider; keep markdown parsing active alongside it. Add call_id stamping rules early (exactly one result per call_id, error results for non-runnable calls) — retrofitting this is painful.
- Phase 3 — confirmation: implement get_confirmation with a hook list and ConfirmAction(confirm/skip/edit); start with a CLI prompt hook plus one auto-approve hook. Then the shell safety ladder in this order: deny regexes with quote-awareness → simple allowlist (pipeline commands + no redirects + no command substitution) → shellcheck integration → per-binary flag tables (only when the first three are stable).
- Shell MVP: persistent bash + sentinel markers + ReturnCode trailer + select/poll loop + hard timeout (kill descendants before bash) + pre/post token truncation with full output saved to the logdir. Defer: tree-sitter splitting, stdin < /dev/null AST rewrite, byte-cap accounting, state snapshot/restore, foreground promotion — each is an independent hardening layer.
- Python tool: in-process IPython with TeeIO capture is ~100 lines and gives you the functions-registration pattern for free; skip sandboxing and artifact detection at first.
- File tools: read (with line numbers + optional line ranges) and save/append via the confirmation wrapper are enough; for edits pick EITHER simple search/replace blocks or a hashline-like read-tag→edit-verify cycle — hashline is clever but the tag/snapshot/3-way-merge machinery is a project on its own. Add requires_tools only if you build the snapshot cycle.
- Subagent: implement subprocess mode first (`python -m youragent -n --no-confirm` with prompt on stdin) — process isolation, progress via a jsonl file, completion via polling or a hook, plus wait/list functions. Thread-mode re-entrancy (isolated ContextVar toolset + re-entrant chat()) is the hard part; do it only if you need shared-process speed. Profiles (tool allowlists per child) and budgets come last.
- MCP: adopt early if you want ecosystem tools — the adapter is ~150 lines once ToolSpec exists (inputSchema.properties → Parameter list, closure execute calling the client, server.tool naming).
- Keep the 'system-role Message as tool result' convention and per-tool yielded-message streaming from day one; the buffered-last-message-call_id behavior can come when you add native tool calling.
