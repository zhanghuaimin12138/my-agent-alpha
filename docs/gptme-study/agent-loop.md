# agent-loop

## Purpose
The gptme agent loop is a three-layer nested loop that turns a terminal chat into an agentic system: an outer REPL loop (get user input / drain queued prompts), an inner "turn" loop (repeat LLM-generation + tool-execution until the assistant stops emitting runnable tool calls), and a single `step()` pass (prepare context -> call LLM with streaming -> detect tool calls in the partial stream -> execute tools -> yield assistant message + tool results). Everything is message-centric: the only shared state is a persisted, append-only conversation log (`LogManager`/`Log` of `Message` objects in `<logdir>/conversation.jsonl`), and the loop decides continuation purely by inspecting the last assistant message for runnable tool uses. Cross-cutting behaviors (steering, cancellation, auto-reply, compaction, confirmation) are injected via a hook system (HookType enum) rather than hardcoded, and durable prompt-queue files allow other processes (server, orchestrator subagents) to inject prompts into a running loop.

## Key Abstractions
- **chat(prompt_msgs, initial_msgs, logdir, workspace, ...) -> None** — gptme/chat.py:149. Session orchestrator: init(), LogManager.load, chdir(workspace), builds in-memory prompt_queue from prompt_msgs, calls _run_chat_loop, writes log on exit, handles SessionCompleteException, restores output-format/token-accumulator ContextVars in finally. Callable from CLI, server, and subagent threads.
- **_run_chat_loop(manager, prompt_queue, stream, ...)** — gptme/chat.py:324. Outer REPL: (1) drain durable queue, (2) take next message from prompt_queue or interactive input, (3) run slash-commands, TURN_PRE hooks, then _process_message_conversation, (4) run LOOP_CONTINUE hooks whose messages are appended to prompt_queue (capped at MAX_PROMPT_QUEUE_SIZE=100), (5) catch KeyboardInterrupt (append INTERRUPT_CONTENT system msg, clear queue, continue) and tagged provider errors (interactive-only recovery, else re-raise).
- **_process_message_conversation(manager, stream, tool_format, model, output_schema)** — gptme/chat.py:531. The inner agentic loop for one user turn. Repeats: STEP_PRE hooks -> step() -> append response msgs -> declined check -> mid-turn autocompact -> max-steps check -> continuation check (`any(tu.is_runnable for tu in ToolUse.iter_from_content(last_assistant_content))`, chat.py:649). Ends with TURN_POST hooks + manager.write(sync=True).
- **step(log, stream, tool_format, workspace, model, ...) -> Generator[Message]** — gptme/chat.py:896. One pass: prepare_messages -> optional ToolSpec list (only when tool_format=='tool') -> _reply_with_overflow_recovery -> GENERATION_POST hooks -> execute_msg(msg_response) with tool_timings dict -> yields assistant message (quiet unless JSON mode) then tool output messages. set_interruptible/clear_interruptible in try/finally.
- **reply(messages, model, stream, tools, ...) -> Message** — gptme/llm/__init__.py:362. Fires GENERATION_PRE hooks (their output msgs are appended to the request), then provider call via _reply_after_hooks; wraps the provider call so exceptions get marked with _gptme_from_llm_reply origin tags (mark_llm_reply_origin, :301) plus output_emitted flags - this is what lets the chat loop distinguish 'LLM is down' from tool/hook crashes (is_provider_error, :327).
- **_reply_stream(...) and break_on_tooluse** — gptme/llm/__init__.py:815. Char-level consume of the provider stream into `output`; renders <think> blocks dim, suppresses think-sig comments, buffers per line/chunk for O(chunks) terminal writes; at every format-specific break char (:1056) re-parses accumulated output with ToolUse.iter_from_content(output, streaming=True) and, if a runnable tooluse exists, drains the rest of the generator for usage metadata (_drain_toolbreak_stream, :61) and breaks - the partial message is returned and executed immediately. break_on_tooluse defaults to not model_meta.supports_parallel_tool_calls (:443-447), overridable by GPTME_BREAK_ON_TOOLUSE.
- **execute_msg(msg, log, workspace, tool_timings) -> Generator[Message]** — gptme/tools/__init__.py:459. Materializes all ToolUses up front (so each structured call_id gets exactly one result), executes runnable ones sequentially via ToolUse.execute, emits paired error results for non-runnable structured calls, converts KeyboardInterrupt into INTERRUPT_CONTENT + 'was not executed' pairing messages, accumulates wall-clock ms per tool name into tool_timings.
- **ToolUse** — gptme/tools/base.py:839 frozen-ish dataclass: tool, args, content, kwargs, call_id, start, _format. `execute()` (:848) runs TOOL_EXECUTE_PRE hooks, sets _current_tool_use ContextVar (used by confirmation flows), calls tool.execute(content, args, kwargs) accepting a single Message or a Generator (buffering the generator when call_id is set so only the LAST message is stamped with call_id + tool metadata - Responses API requires exactly one function_call_output per call_id), records telemetry, fires TOOL_EXECUTE_POST hooks, converts exceptions to a system error Message (re-raised only under pytest). `iter_from_content(content, streaming=False)` (:1083) parses markdown fences, XML (<tool-use> and Haiku <function_calls>), and native JSON tool calls (regex + find_json_end + json_repair, skipping matches inside fenced code), sorted by position.
- **Message** — gptme/message.py:281 frozen dataclass: role in {system,user,assistant}, content, timestamp, files, file_hashes, call_id (pairs tool results to structured tool_use), pinned (never context-trimmed), hide (sent to LLM but not printed), quiet (not printed on append), ephemeral_ttl (pruned after N assistant turns), metadata (usage/cost/timings incl. tool_ms_by_name).
- **LogManager / Log** — gptme/logmanager/manager.py:219/73. Persistence + views. append(msg) (:542) stores attached files by hash, dual-writes to master branch and current compacted view, writes JSONL, emits event-log, prints unless quiet. prepare_messages (:1137) is the context pipeline run before every LLM call. Views (create_view/switch_view :875/:893) implement lossless-looking compaction: master keeps everything, the view is what the LLM sees.
- **Prompt queue (durable steering)** — gptme/prompt_queue.py: JSONL records {content, queued_at, steer?, skill_invocation_id?} under logdir with flock. Regular records -> drained between turns by drain_prompt_queue (called from _drain_external_prompt_queue at top of every outer-loop iteration); steer records -> drained at every STEP_PRE by the subagent control hook (tools/subagent/hooks.py:40, registered at tools/subagent/execution.py:269) so an orchestrator's guidance reaches the very next LLM call mid-turn. The `prompt-queue-closed` sentinel file (chat.py:273/312/379/402) closes the drain race when the loop exits.
- **Hooks (HookType / trigger_hook / register_hook)** — gptme/hooks/types.py:66 + registry.py:654. Generator-based hooks that yield Messages injected into the conversation. Loop-relevant types: SESSION_START/END, TURN_PRE/POST, STEP_PRE/POST, GENERATION_PRE/POST/CHUNK/INTERRUPT, TOOL_EXECUTE_PRE/POST, TOOL_CONFIRM, LOOP_CONTINUE. This is how steering, cancellation (SessionCompleteException from the control hook), auto-reply, autocompact, and TTS are layered onto the loop without touching it.
- **SessionCompleteException** — gptme/tools/complete.py. Raised by the `complete` tool, by auto-reply exit (complete.py:534 'No tools used after 2 auto-reply confirmations'), and by subagent cancellation (tools/subagent/hooks.py:102). In _run_chat_loop it is first handled at chat.py:369: write sentinel, drain queue once more - if chained prompts remain the loop continues, else it propagates to chat() which runs SESSION_END hooks and exits cleanly.
- **Interruptible flag (set_interruptible/clear_interruptible)** — gptme/util/interrupt.py:44/49 + SIGINT handler :20. ContextVar gate: Ctrl-C raises real KeyboardInterrupt only while the loop is in step() or tool execution; during user input it just prints a hint. Registered in cli/main.py:1466.

## Data Flow
FULL TRACE of one user turn (file:line for every function in the chain):

1. ENTRY: `python -m gptme` -> gptme/__main__.py:11 `main()` (gptme/cli/main.py:762) parses CLI, builds logdir/workspace/model, builds `prompt_msgs = [Message('user', p) for p in prompts]` (cli/main.py:1136), installs SIGINT handler (cli/main.py:1466), then calls `chat(prompt_msgs, initial_msgs, logdir, workspace, model, stream, no_confirm, interactive, ...)` (cli/main.py:1478).

Provider errors (:489): `if not interactive or not is_provider_error(e): raise` else log + system msg `LLM_REQUEST_FAILED_PREFIX` + clear queue + continue (issue #3668: only exceptions tagged inside reply() count).

   a. `set_interruptible()` (:555).
   b. STEP_PRE hooks (:558) - includes the subagent control hook (tools/subagent/hooks.py:40): drains `control.jsonl` for cancel ops (raises SessionCompleteException, hooks.py:102) and drains steer prompts (hooks.py:109 -> prompt_queue.py:141) which become the next user messages the LLM sees.
   c. `response_msgs = list(step(manager.log, stream, tool_format=..., workspace=..., model=..., output_schema=..., logdir=...))` (:565-575).
   d. KeyboardInterrupt (:576) -> INTERRUPT_CONTENT msg, break (back to user prompt).
   e. For each response msg: `manager.append(response_msg)` (:586); user-role commands via `execute_cmd` (:588); `print_inline_cost` for assistant msgs (:593).

   i. `step_count += 1`; if GPTME_MAX_STEPS reached -> system msg + break (:629-636).

CONTINUATION DECISION (:642-654): if mid-turn compacted use the pre-compaction answer, else recompute `has_runnable = any(tu.is_runnable for tu in ToolUse.iter_from_content(last_assistant_content))` - because tool results are role 'system', the last assistant message still holds the tool calls that were just executed, so the loop regenerates; when the newest assistant reply contains no runnable tool use, `break`.

## Design Highlights
- The loop's only continuation test is 'does the last assistant message still contain a runnable tool use?' (chat.py:649). Since tool results are role-'system' messages appended after the assistant message, this single content-based check drives the whole agentic cycle with zero extra state - crash-safe and trivially replayable from the persisted log.
- Tool calls are detected DURING streaming by re-parsing the accumulated text at cheap format-specific break characters (llm/__init__.py:1056, _tooluse_break_check_char :49), with streaming=True codeblock extraction requiring a blank line after the closing fence (codeblock.py:355) to avoid executing half-written commands. After a tool-use break the generator is drained anyway (_drain_toolbreak_stream :61) purely to capture usage/cost metadata from the final provider event.
- Provider-failure provenance tagging (mark_llm_reply_origin llm/__init__.py:301 + is_provider_error :327): only exceptions raised inside the provider call are considered 'recoverable LLM outage' by the chat loop, so an httpx failure inside a tool or hook still crashes loudly instead of being silently swallowed into an infinite retry (issue #3668).
- Everything cross-cutting is a hook that yields Messages (hooks/types.py:66): steering, cancellation, auto-reply, autocompact, cost display, TTS. The core loop has no if-branches for any of them - the same LOOP_CONTINUE/STEP_PRE/TURN_POST trigger points service all of them.
- Durable cross-process steering: prompt-queue.jsonl with flock and a steer flag for two drain cadences (between-turn vs mid-turn STEP_PRE), plus a 'prompt-queue-closed' sentinel file written BEFORE the final drain to close the race where an orchestrator's steer would be falsely acknowledged (chat.py:369-413 comments).
- Interruptibility is an explicit ContextVar gate (util/interrupt.py) rather than raw signal behavior: Ctrl-C only raises inside step()/tool execution and is deliberately inert at the user prompt, giving 'Ctrl-C interrupts the agent, Ctrl-D exits the session' semantics with careful partial-output flushing (llm/__init__.py:1094-1123).
- Context-length overflow is self-healing inside step(): _reply_with_overflow_recovery (chat.py:794) compacts into a named LogManager view, retries once, verifies the retry actually shrank provider input, records a compaction event with before/after token counts, and reverts to the master view if the retry failed.
- Structured (native JSON) tool calls keep tool_use/tool_result pairing valid in every failure mode: non-runnable calls get synthetic error results (tools/__init__.py:522-540), interrupts drain remaining calls with 'was not executed' results (:498-515), and only the LAST message of a multi-message tool generator is stamped with call_id (base.py:907-945) because the Responses API demands exactly one function_call_output per call_id.
- Retry policy is centralized and SDK retries are zeroed (llm/retry_policy.py:29) so gptme's 11-attempt capped-backoff budget is the real budget - preventing SDK-retries x own-retries multiplication during rate limits.
- Persistence model: append-only JSONL with dual-write master/view (logmanager/manager.py:542) means compaction never destroys history, and _should_prompt_for_input (chat.py:705) can resume a crashed session by inspecting marker messages (INTERRUPT/DECLINED/LLM-failed) after the last assistant turn.

## MVP Guidance
- Replicate first (the spine): Message dataclass -> append-only JSONL Log -> outer REPL loop -> inner while-last-assistant-has-runnable-tooluses loop -> step() = prepare+reply+execute_msg -> yield results into manager.append. Everything else is polish.
- Implement streaming tool detection early even in an MVP: accumulate streamed text, and on every newline re-run a markdown codeblock parser with a requires-blank-line-after-fence rule; execute the moment a complete runnable block appears. This is gptme's defining UX (you watch the agent work tool-by-tool).
- Start with markdown fence tool calls only (like gptme's default 'markdown' ToolFormat); add native JSON tool calls (call_id pairing) as a second format once the loop works. The pairing invariants (one result per call_id, synthesize error results for non-runnable/interrupted calls) are the tricky part - copy tools/__init__.py:459's materialize-first structure.
- Copy the minimal hook set: GENERATION_PRE/POST, STEP_PRE, TURN_POST, LOOP_CONTINUE as generator-functions-yielding-Messages. You can hardcode auto-reply ('No tool call detected... complete?') and max-steps inside the loop for v1 and extract to hooks later.
- Keep the interruptible-flag pattern (ContextVar + SIGINT handler) - it is small and gives correct Ctrl-C semantics for free; likewise the three marker contents INTERRUPT_CONTENT / DECLINED_CONTENT / LLM_REQUEST_FAILED_PREFIX as first-class protocol strings.
- Skip for v1: views/compaction machinery (just truncate oldest non-pinned messages), k_best.py, circuit_breaker.py (only matters with MCP), checkpoint.py, the whole gptme/agent/ service-manager dir (systemd/launchd automation), evidence replay, auto-naming threads, ACP/TUI-specific buffering, and the prompt-queue durability/sentinel logic (in-process queue is fine until you add subagents).
- Keep provider retries simple but centralized: one retry decorator with capped exponential backoff + Retry-After, and disable SDK-internal retries - the multi-layer multiplication problem is real.
- Design the LLM facade as reply(messages, model, stream, tools) returning a fully-built Message with metadata captured from the stream wrapper - the _StreamWithMetadata 'capture StopIteration.value' trick (:648) is worth copying for usage/cost accounting.
- Order of work: (1) Message+Log persistence, (2) step() with non-streaming reply + markdown tool execution, (3) inner loop continuation check, (4) outer REPL + slash commands, (5) streaming + break_on_tooluse, (6) interrupts/declines, (7) provider retries, (8) hooks, (9) compaction, (10) steering/subagents.

## Open Questions
- gptme/agent/ does NOT contain the agent loop despite its name - it manages systemd/launchd services and template workspaces for autonomous scheduled runs. The actual loop lives in chat.py. A re-implementation should not mirror this naming.
- k_best.py is exported in the public API (gptme/__init__.py) but I found no call site inside the loop itself - it appears to be a library utility for users/evals; unclear if any built-in path decorates generation with it.
- STEP_POST and MESSAGE_TRANSFORM hook types exist (hooks/types.py:92/99) but the main CLI loop never triggers STEP_POST directly - it may be server-only or vestigial; verify in gptme/server/session_step.py (out of this subsystem's scope).
- The server (gptme/server/session_step.py) runs a parallel variant of this loop with immediate persistence and _attach_tool_timings patching instead of the CLI's buffer-then-yield approach (chat.py:975-981 comment) - exact differences were not traced here.
- break_on_tooluse discards assistant text streamed after the first detected tool call (drained for metadata only); models without supports_parallel_tool_calls therefore re-generate subsequent tool calls in later steps - this trades token cost for correctness and depends on accurate ModelMeta capability flags.
- _should_prompt_for_input treats a pinned or user-less log as 'prompt for input' (chat.py:741-747); the pinned case interacts with view switching in ways not fully explored here.
