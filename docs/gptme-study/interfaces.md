# 接口(interfaces)

> 译自英文原版(见 git 历史 aaf0543),由 Claude 翻译

## 目的
gptme 面向用户的表层:一个朴素的命令行界面(CLI,click + prompt_toolkit 聊天循环)、一个 Textual 终端界面(TUI,`gptme-tui`)、一个 HTTP 服务器(Flask 蓝图(blueprint)与服务端推送事件(SSE)流式传输)并内置 React webui、一个 ACP agent/客户端(基于 stdio 的 JSON-RPC,供 Zed 等编辑器使用)、一个 A2A JSON-RPC 端点,以及一个 OpenRouter PKCE OAuth 流程。每个接口都是搭在同一组核心原语上的薄壳——`LogManager`(JSONL 持久化)、`Message`、工具注册表(`ToolUse.execute`)、钩子(hook)系统(`trigger_hook`)以及 LLM 层(`_stream`/`_chat_complete`)——区别仅在于它们如何渲染流式 token、收集工具确认,以及把事件传送给用户。

## 关键抽象
- **chat.step() —— 共享的回合引擎** —— gptme/chat.py:896 `def step(log, stream, tool_format, workspace, model, output_schema, on_token, on_thinking, logdir, max_tokens) -> Generator[Message]`。一次 pass:生成回复、执行工具、产出(yield)Message。流式经由 on_token/on_thinking 回调解耦,使任何前端都能渲染 token,而核心层无需知晓终端、SSE 或 JSON-RPC 的存在。CLI 循环、TUI worker 和 ACP agent 都直接调用它。
- **GptmeApp(Textual)** —— gptme/tui/app.py:863。持有 LogManager、prompt_queue、_interrupt_event(threading.Event),以及一份复制出来的聊天 ContextVar 上下文(_chat_ctx,:1056)。生成通过 `run_worker(self._generation_body, thread=True, exclusive=True, group="generation")`(:1497)运行;worker 迭代 chat.step(),并用 `call_from_thread` 把 UI 更新调度回主线程。用户按 Esc 时,`_on_token`(:1608)在 worker 内抛出 KeyboardInterrupt,复用核心层自己的中断路径。
- **ConversationSession + SessionManager** —— server/session_models.py:93 与 :217。Session = 内存中的 SSE 事件缓冲(list + 用于绝对索引的 _events_offset;超过 10k 且无客户端时裁剪到 1k)、pending_tools 注册表、generating 标志、step_lock、step_seq 纪元、event_flag。Manager = 进程级注册表,以 session_id 和 conversation_id 为键;`add_event(conversation_id, event)` 向该对话的每个 session 追加事件并逐个置位 event_flag——这正是 SSE 生成器等待的唤醒原语。
- **SSE 事件流(generate_events)** —— server/api_v2_sessions.py:228-304。一个 Flask 生成器响应(mimetype 为 text/event-stream,X-Accel-Buffering: no)。先发出 `connected`(session_id + generating + pending_tools——完整的重连状态)和一个 ping,然后循环:yield 自上次绝对索引以来的事件、ping、先清零再复查 event_flag、wait(15)。客户端从 `connected` 采纳新的 session_id,因此服务器重启对客户端是透明的。
- **step_seq 生成纪元(epoch)** —— server/session_models.py:141 + session_step.py:821/1152-1168。每次预留(POST /step、工具续跑、跳过)都会在 step_lock 下递增 step_seq;worker 在入队时捕获自己的纪元,只有纪元仍然匹配时才清除 `generating`/发出 step_complete。中断会递增纪元,撤销所有过期 worker。这是服务端并发控制的心脏。
- **ToolExecution / pending_tools + 确认端点** —— server/session_models.py:70、api_v2_sessions.py:624。与阻塞式模态框(CLI/TUI)不同,服务器把检测到的工具调用连同 tool_id 停放在 session.pending_tools 里,发出 tool_pending 并挂起;浏览器显示 InlineToolConfirmation 并以 action confirm|edit|skip|auto POST /tool/confirm,后者调用 start_tool_execution。auto_confirm_count 实现"接下来 N 个工具自动确认"。
- **GptmeAgent(ACP agent 角色)** —— gptme/acp/agent.py:254。实现 ACP Agent 接口(initialize/new_session/prompt/load_session/cancel/set_session_model/set_session_mode)。从 cwd 派生的确定性会话 ID 意味着编辑器重启后会恢复同一个对话(:244)。prompt() 在线程 executor 中运行完整的 chat-step 循环并流式发送 update_agent_message 分块;工具权限变成 ACP request_permission 往返,并缓存 allow/reject 选项。
- **GptmeAcpClient + _MinimalClient(ACP 客户端角色)** —— gptme/acp/client.py:209/:62。异步上下文管理器,通过 stdio 启动 ACP agent 子进程(spawn_agent_process),执行 initialize 握手,并代理 new_session/prompt。_MinimalClient 提供 agent 会调用的客户端侧回调(request_permission、session_update -> on_update 回调、read/write_text_file)。服务器把它包进 AcpSessionRuntime,实现按 session 的 cwd 隔离。
- **"工具调用即文本"的解析** —— 由于 gptme 的工具调用以三种格式存在于 assistant 消息文本内部,每个前端都要重新解析:TUI 的 `_split_all_tool_calls`(app.py:303)把针对 `@tool(id): {...}`、XML <tool-use>/<function_calls> 和 markdown 围栏的正则解析器串成链;webui 的 toolCallParser.ts:38 用正则把围栏与工具白名单比对;server/ACP 使用权威实现 `ToolUse.iter_from_content`。结果总是渲染为可折叠卡片(Collapsible 部件、RichToolCall 组件)。
- **钩子驱动的确认(HookType.TOOL_CONFIRM)** —— 工具执行调用 trigger_hook(TOOL_CONFIRM) 并阻塞等待 ConfirmationResult。CLI 注册一个终端提示钩子;TUI 注册一个优先级 100 的钩子(app.py:1129-1134),弹出 ConfirmScreen 模态框并让 worker 阻塞在一个 threading.Event 上(:1744-1777);服务器注册的钩子把工具停挂为 pending,当 /tool/confirm 调用 resolve_hook_confirmation 时解除(session_step.py:1655)。一个工具层,三套 UI。
- **把 ContextVar 快照进工作线程** —— gptme 把默认 model/config/tools 存在 ContextVars 里,而线程不会继承它们。每个接口都在边界处复制上下文:TUI 先 `contextvars.copy_context()` 再 `_chat_ctx.run(...)`(app.py:1056、:1503);服务端 `_start_step_thread` 执行 `ctx.run(step_thread)`(session_step.py:1630);ACP `loop.run_in_executor(None, ctx.run, run_chat_turn)`(agent.py:1418)。

## 数据流
CLI 路径:`gptme 'do x'` -> cli/main.py:762 的 main() 解析 config/tools/model,通过 get_prompt(:1450)构造初始系统提示词,然后 chat()(chat.py:149)-> _run_chat_loop(:324),后者弹出 prompt_queue 或经 prompt_toolkit 的 _get_user_input 读取输入,对斜杠命令运行 execute_cmd,并调用 _process_message_conversation -> chat.step()(chat.py:896),其 on_token 把 token 打印到 rich 控制台,其产出(assistant 消息、工具输出)被追加到 LogManager 并渲染。
TUI 路径:gptme-tui/main.py:104 构建 LogManager + GptmeApp;用户在 ChatInput 提交 -> on_chat_input_submitted(app.py:1322)-> _submit 追加 Message 并展示它,_start_generation(:1485)生成一个 Textual 线程 worker;_generation_body(:1505)循环执行 `step(manager.log, stream=True, tool_format=..., on_token=self._on_token, on_thinking=self._on_thinking)`;每个 token 经 call_from_thread 跨越线程边界进入 StreamingMessage.append_token(:1636-1652);每个产出的 Message 把流式部件替换为最终的 AssistantMessage/SystemMessage(_on_step_message :1679);工具确认让 worker 停在 TOOL_CONFIRM 钩子内,直到 ConfirmScreen 模态框给出结果;当没有剩余可运行的工具调用时 worker 退出,on_worker_state_changed -> _generation_done(:1707)派发下一条排队的提示词。
服务端路径:浏览器 ApiClient.subscribeToEvents 打开 EventSource GET /api/v2/conversations/<id>/events(api_v2_sessions.py:162);SSE 生成器发送带 session_id 的 `connected`,客户端将其保存。sendMessage POST 用户消息(api_v2.py:1842 经 LogManager 追加到 JSONL 并广播 message_added),然后 step() POST /step(api_v2_sessions.py:307);该路由在 conversation_lock+step_lock 之下预留生成权,并生成一个守护线程(_start_step_thread,session_step.py:1555)运行 step()(:741);该线程触发钩子,调用 LLM 的 _stream,把字符批量组成 generation_progress 事件(:1007-1011 -> SessionManager.add_event -> session.event_flag.set()),发出带完整消息的 generation_complete,解析 ToolUse.iter_from_content,注册 ToolExecution + tool_pending 事件;若非自动确认则返回等待——浏览器显示 InlineToolConfirmation 并 POST /tool/confirm(:624),后者运行 start_tool_execution -> execute_tool_thread(:1216),以发出 tool_output 事件的 stream_tool_output 回调执行工具,然后串联剩余工具,最后启动续跑 step 线程;整个过程中 SSE 生成器在 event_flag 上唤醒并推送 `data: {...}\n\n` 帧;中断 POST(:1194)清除各标志并递增 step_seq,让过期的 worker 收工。
ACP 路径:编辑器启动 `gptme-acp`(packages/gptme-acp 占位包 -> gptme.acp.__main__:main);stdio 被捕获,使 JSON-RPC 独占 stdout;initialize 运行 gptme init;new_session 把 cwd 映射到确定性的 LogManager;session/prompt 把内容转换为 Message 并在 executor 中运行 chat-step 循环,每 0.1s/50 字符把缓冲的 token 冲刷为 session/update agent_message 分块(agent.py:1259-1316);工具调用以 tool_call 更新的形式呈现,并受 request_permission 往返把关;循环返回 PromptResponse(stop_reason)。反方向上,HTTP 服务器可以让某个 session 选择启用 `use_acp`(api_v2_sessions.py:414-463),创建一个 AcpSessionRuntime,把 `gptme-acp` 作为子进程启动,并通过 _acp_step(session_step.py:453)把它的 session_update 通知翻译成同样的 SSE 事件。

## 设计亮点
- 带有 on_token/on_thinking 回调的单回合 `step()` 生成器就是全部接口契约:随心所欲渲染 token,消费产出的 Message 获取结构——这正是四个前端共享一个核心而毫无 UI 泄漏的原因。
- 通过带优先级的 TOOL_CONFIRM 钩子,在同一个工具层之上实现三种确认交互:终端提示(CLI)、阻塞工作线程的模态屏(TUI)、待确认工具注册表 + HTTP 端点(服务器)。
- 带绝对索引偏移的 SSE 环形缓冲(_events_offset + events_count)允许事件列表被裁剪到 1k 条,同时重连的客户端仍保持索引一致;`connected` 事件携带 session_id + generating + pending_tools,使客户端在服务器重启后能完整恢复 UI 状态,而服务端无需保留任何粘性(stickiness)。
- 在传输层做 token 批处理(20 字符或换行 -> 一个 generation_progress 事件)把 SSE 流量削减约 20 倍;TUI 与 ACP agent 各自有针对自身传输调优的批处理器(字符缓冲的 Static 部件;0.1s/50 字符冲刷,带防重复的发送确认)。
- 基于纪元的预留(在 step_lock 下于入队时捕获 step_seq,在 finally 中比对后清除)使中断 + 并发 /step + 工具续跑的竞态变得可控,而无需取消线程。
- 在每个线程边界做 ContextVars 快照并运行(TUI 的 _chat_ctx、服务端的 ctx.run 线程、ACP 的 run_in_executor),让单个进程服务多个对话时仍保持按 session 的 model/config 隔离。
- 事件总线唤醒模式:生产者追加事件并置位每 session 的 threading.Event;SSE 生成器"先清零-再复查-再等待(15)"以避免丢失唤醒的竞态,ping 兼作保活(keepalive)。
- TUI 内联模式利用 Textual inline 驱动的光标位置不变量(_previous_cursor_position),把 Rich 可渲染对象打印进应用上方终端的原生回滚区(app.py:1187-1222)——Claude-Code 式滚动,且无需接管整个屏幕。
- ACP 的 stdio 捕获(在任何 gptme 导入之前用 dup2 把 fd 1 -> stderr)保证了 JSON-RPC 信道的纯净,无论核心层打印什么;一个极小的 PyPI 占位包(packages/gptme-acp)的存在纯粹是为了让编辑器能 `uvx gptme-acp`。
- 工具调用以文本形式随 assistant 消息传输,因此每个消费者(服务端续跑循环、TUI 折叠部件、webui 卡片)解析的都是同一份产物——单一事实来源,三个解析器。
- 面向插件子命令的 gptme-* 可执行文件发现(cli/main.py:60-86)加上动态 --help 扩展,让 CLI 保持可扩展而不付出导入开销。

## MVP 指南
- 先把核心构建成一个库:Message 数据类、JSONL LogManager、带 execute() 的工具注册表,以及带 on_token 的 step() 生成器——然后 CLI 只是围绕它的一个 prompt_toolkit 循环。这精确镜像了 gptme 的分层。
- 接着做 TUI:一个带 VerticalScroll 聊天区的 Textual App、一个由 call_from_thread 喂料的 StreamingMessage 部件、展示工具输出的 Collapsible 区段,以及一个弹出模态框的 TOOL_CONFIRM 钩子。跳过内联模式、Tab 补全覆盖层、历史编辑和 termios 看门狗——那些属于打磨(app.py 有 40% 是打磨)。
- 服务器:一个 Flask 蓝图就够——POST /conversations/<id>/messages(追加 + 持久化)、POST .../step(生成一个线程,对着同一个 LogManager 运行你的 step(),把事件推到按对话的列表 + threading.Event 上)、GET .../events(SSE 生成器,逐字照抄 gptme 的 connected/ping/index/wait 循环)。把 token 批处理和 events_count 偏移的思路抄过来。
- 不要像 gptme 那样在服务器上重新实现 chat.step(session_step.py:741 为了事件控制把它复制了一份);如果不想承受 gptme 一直忍受的分叉(divergence),就让 step() 通过可注入的观察者(observer)发出事件。
- 前端:React + Vite;一个 ApiClient 类,持有每个对话一个 EventSource 并带事件类型 switch;一个 useConversation 钩子,做"先追加消息再 POST step";markdown 渲染配一个围栏正则的工具调用解析器 + 白名单。Radix/Tailwind 是便利,不是本质。
- 从第一天起就把 epoch/step_seq 中断协议和 confirm/skip/auto 待确认工具流程偷过来——事后补装并发控制比一开始就内置难得多。
- 完全推迟:ACP(两种角色)、A2A、OAuth PKCE、panels/artifacts/preview-proxy/computer-use/tasks 蓝图、Tauri 桌面包装、OpenAPI 文档、指标、多服务器 webui。每一个都是独立产品;gptme 仅 ACP 就约 2.5k 行。
- 顺序:core+CLI -> TUI -> server+webui。每个阶段都在演练同一个 step() 契约,并为下一个传输层加固它。

## 开放问题
- 服务器运行的是 Flask 内置开发服务器(server/cli.py:400 的 app.run)——每条 SSE 连接在其生命期内占用一个工作线程;它如何扩展(以及 chat.gptme.org 的托管部署是否使用 waitress/gunicorn)在仓库里看不出来。
- session_step.step() 是 chat.step() 的手写平行版本(约 400 行),因为它需要逐消息的事件发出和续跑控制——一个已知的重复;对其中一个循环得到的任何认知都必须对照另一个循环核查。
- webui 的 toolCallParser.ts 正则与 GPTME_TOOL_ALLOWLIST 可能与服务端的 ToolUse 解析发生漂移(例如新工具、XML/工具格式不会在浏览器中渲染成工具卡片——只有 markdown 围栏会)。
- webui 的 SSE 客户端最多同时保持 MAX_CONNECTED_CONVERSATIONS=3 条流(useConversation.ts:42),并依赖服务器的内存态 SessionManager;服务器重启会丢失所有 session,但"携带新 session_id 的 connected"握手让这一情形可以存活——断连间隙期间产生的工具输出如何到达客户端(答案:message_added/LogManager 重载)只是隐式交代。
- ACP 的 prompt() 流式发送 agent 文本,但要等整个回合在 executor 循环中完成后才转发工具结果消息——Zed 是否在回合中途显示实时工具输出,取决于 tool_call 更新路径(_report_tool_call),我没有完整追完。
- `elicit` 端点(api_v2_sessions.py:1032)与 resolve_hook_elicitation 暗示存在一个交互式结构化输入工具('elicit'),其钩子阻塞机制与 TOOL_CONFIRM 如出一辙,但位于所指派的研究范围(hooks/)之外。
