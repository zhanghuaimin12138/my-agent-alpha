# interfaces

## Purpose
The user-facing surface layer of gptme: a plain CLI (click + prompt_toolkit chat loop), a Textual TUI (`gptme-tui`), an HTTP server (Flask blueprints, SSE streaming) with a bundled React webui, an ACP agent/client (JSON-RPC over stdio for editors like Zed), an A2A JSON-RPC endpoint, and an OpenRouter PKCE OAuth flow. Every interface is a thin shell over the same core primitives — `LogManager` (JSONL persistence), `Message`, the tools registry (`ToolUse.execute`), the hook system (`trigger_hook`), and the LLM layer (`_stream`/`_chat_complete`) — differing only in how they render streaming tokens, collect tool confirmation, and transport events to the user.

## Key Abstractions
- **chat.step() — the shared turn engine** — gptme/chat.py:896 `def step(log, stream, tool_format, workspace, model, output_schema, on_token, on_thinking, logdir, max_tokens) -> Generator[Message]`. One pass: generate a response, execute tools, yield Messages. Streaming is decoupled via the on_token/on_thinking callbacks so any frontend can render tokens without the core knowing about terminals, SSE, or JSON-RPC. The CLI loop, the TUI worker, and the ACP agent all call this directly.
- **GptmeApp (Textual)** — gptme/tui/app.py:863. Holds a LogManager, prompt_queue, _interrupt_event (threading.Event), and a copied chat ContextVar context (_chat_ctx, :1056). Generation runs via `run_worker(self._generation_body, thread=True, exclusive=True, group="generation")` (:1497); the worker iterates chat.step() and marshals UI updates back with `call_from_thread`. `_on_token` (:1608) raises KeyboardInterrupt inside the worker when the user hits Esc, reusing the core's own interrupt path.
- **ConversationSession + SessionManager** — server/session_models.py:93 and :217. Session = in-memory SSE event buffer (list + _events_offset for absolute indexing, trim to 1k when >10k and no clients), pending_tools registry, generating flag, step_lock, step_seq epoch, event_flag. Manager = process-wide registries keyed by session_id and conversation_id; `add_event(conversation_id, event)` appends to every session of the conversation and sets each event_flag — the wakeup primitive the SSE generator waits on.
- **SSE event stream (generate_events)** — server/api_v2_sessions.py:228-304. A Flask generator response (mimetype text/event-stream, X-Accel-Buffering: no). Emits `connected` (session_id + generating + pending_tools — full reconnect state), a ping, then loops: yield events since last absolute index, ping, clear-then-recheck event_flag, wait(15). Client adopts the new session_id from `connected`, so server restarts are transparent.
- **step_seq generation epoch** — server/session_models.py:141 + session_step.py:821/1152-1168. Every reservation (POST /step, tool continuation, skip) increments step_seq under step_lock; workers capture their epoch at queue time and only clear `generating`/emit step_complete if the epoch still matches. Interrupts bump the epoch, revoking all stale workers. This is the concurrency-control heart of the server.
- **ToolExecution / pending_tools + confirm endpoint** — server/session_models.py:70, api_v2_sessions.py:624. Instead of a blocking modal (CLI/TUI) the server parks detected tool uses in session.pending_tools with a tool_id, emits tool_pending, and suspends; the browser shows InlineToolConfirmation and POSTs /tool/confirm with action confirm|edit|skip|auto, which calls start_tool_execution. auto_confirm_count implements 'auto for N tools'.
- **GptmeAgent (ACP agent role)** — gptme/acp/agent.py:254. Implements the ACP Agent interface (initialize/new_session/prompt/load_session/cancel/set_session_model/set_session_mode). Deterministic session id from cwd means an editor restart resumes the same conversation (:244). prompt() runs the full chat-step loop in a thread executor and streams update_agent_message chunks; tool permissions become ACP request_permission round-trips with allow/reject option caching.
- **GptmeAcpClient + _MinimalClient (ACP client role)** — gptme/acp/client.py:209/:62. Async context manager that spawns an ACP agent subprocess over stdio (spawn_agent_process), performs the initialize handshake, and proxies new_session/prompt. _MinimalClient supplies the client-side callbacks the agent invokes (request_permission, session_update -> on_update callback, read/write_text_file). The server wraps this in AcpSessionRuntime for per-session cwd isolation.
- **tool-call-as-text parsing** — Because gptme tool calls live inside assistant message text in three formats, every frontend re-parses them: TUI `_split_all_tool_calls` (app.py:303) chains regex parsers for `@tool(id): {...}`, XML <tool-use>/<function_calls>, and markdown fences; webui toolCallParser.ts:38 regexes fences against a tool allowlist; server/ACP use the canonical `ToolUse.iter_from_content`. Result is always rendered as a collapsible card (Collapsible widget, RichToolCall component).
- **hook-driven confirmation (HookType.TOOL_CONFIRM)** — Tool execution calls trigger_hook(TOOL_CONFIRM) and blocks for a ConfirmationResult. The CLI registers a terminal prompt hook; the TUI registers one at priority 100 (app.py:1129-1134) that pushes a ConfirmScreen modal and blocks the worker on a threading.Event (:1744-1777); the server registers one that parks the tool as pending and resolves when /tool/confirm calls resolve_hook_confirmation (session_step.py:1655). One tools layer, three UIs.
- **ContextVar snapshotting into worker threads** — gptme stores default model/config/tools in ContextVars which threads don't inherit. Each interface copies context at the boundary: TUI `contextvars.copy_context()` then `_chat_ctx.run(...)` (app.py:1056, :1503); server `_start_step_thread` runs `ctx.run(step_thread)` (session_step.py:1630); ACP `loop.run_in_executor(None, ctx.run, run_chat_turn)` (agent.py:1418).

## Data Flow
CLI path: `gptme 'do x'` -> cli/main.py:762 main() resolves config/tools/model, builds initial system prompt via get_prompt (:1450), then chat() (chat.py:149) -> _run_chat_loop (:324) which pops prompt_queue or reads input via prompt_toolkit _get_user_input, runs execute_cmd for /commands, and calls _process_message_conversation -> chat.step() (chat.py:896) whose on_token prints tokens to the rich console and whose yields (assistant msg, tool outputs) are appended to the LogManager and rendered.
TUI path: gptme-tui/main.py:104 builds LogManager + GptmeApp; user submits in ChatInput -> on_chat_input_submitted (app.py:1322) -> _submit appends Message, shows it, _start_generation (:1485) spawns a Textual thread worker; _generation_body (:1505) loops `step(manager.log, stream=True, tool_format=..., on_token=self._on_token, on_thinking=self._on_thinking)`; each token crosses the thread boundary via call_from_thread into StreamingMessage.append_token (:1636-1652); each yielded Message replaces the stream widget with a final AssistantMessage/SystemMessage (_on_step_message :1679); tool confirmation suspends the worker inside the TOOL_CONFIRM hook until the ConfirmScreen modal resolves; when no runnable tool uses remain the worker exits and on_worker_state_changed -> _generation_done (:1707) dispatches the next queued prompt.
Server path: browser ApiClient.subscribeToEvents opens EventSource GET /api/v2/conversations/<id>/events (api_v2_sessions.py:162); the SSE generator sends `connected` with a session_id which the client stores. sendMessage POSTs the user message (api_v2.py:1842 appends to the JSONL via LogManager and broadcasts message_added), then step() POSTs /step (api_v2_sessions.py:307); the route reserves generation under conversation_lock+step_lock and spawns a daemon thread (_start_step_thread, session_step.py:1555) running step() (:741); that thread fires hooks, calls the LLM _stream, batches chars into generation_progress events (:1007-1011 -> SessionManager.add_event -> session.event_flag.set()), emits generation_complete with the full message, parses ToolUse.iter_from_content, registers ToolExecution + tool_pending events; if not auto-confirm it returns and waits — the browser shows InlineToolConfirmation and POSTs /tool/confirm (:624) which runs start_tool_execution -> execute_tool_thread (:1216) executing the tool with a stream_tool_output callback that emits tool_output events, then chains remaining tools and finally starts the continuation step thread; the whole time the SSE generator wakes on event_flag and pushes `data: {...}\n\n` frames; interrupt POST (:1194) clears flags and bumps step_seq so stale workers stand down.
ACP path: editor spawns `gptme-acp` (packages/gptme-acp stub -> gptme.acp.__main__:main); stdio is captured so JSON-RPC owns stdout; initialize runs gptme init; new_session maps cwd to a deterministic LogManager; session/prompt converts content to a Message and runs the chat-step loop in an executor, flushing buffered tokens as session/update agent_message chunks every 0.1s/50 chars (agent.py:1259-1316); tool calls are surfaced as tool_call updates and gated by request_permission round-trips; the loop returns PromptResponse(stop_reason). In the reverse direction, the HTTP server can opt a session into `use_acp` (api_v2_sessions.py:414-463), creating an AcpSessionRuntime that spawns `gptme-acp` as a child process and translates its session_update notifications into the same SSE events via _acp_step (session_step.py:453).

## Design Highlights
- Single-turn `step()` generator with on_token/on_thinking callbacks is the entire interface contract: render tokens however you like, consume yielded Messages for structure — this is why four frontends share one core with no UI leakage.
- Three confirmation UXs over one tools layer via prioritized TOOL_CONFIRM hooks: terminal prompt (CLI), modal screen blocking a worker thread (TUI), pending-tool registry + HTTP endpoint (server).
- SSE ring buffer with absolute-index offset (_events_offset + events_count) lets the event list be trimmed to 1k entries while reconnecting clients keep consistent indices; `connected` event carries session_id + generating + pending_tools so a client can fully restore UI state after server restart without any server-side stickiness.
- Token batching at the transport (20 chars or newline -> one generation_progress event) cuts SSE volume ~20x; the TUI and ACP agent each have their own batcher tuned to their transport (char-buffered Static widget; 0.1s/50-char flush with duplicate-safe send confirmation).
- Epoch-based reservation (step_seq captured at queue time under step_lock, compare-and-clear in finally) makes interrupt + concurrent /step + tool-continuation races tractable without cancelling threads.
- ContextVars snapshot-and-run at every thread boundary (TUI _chat_ctx, server ctx.run threads, ACP run_in_executor) keeps per-session model/config isolation in one process serving many conversations.
- Event-bus wakeup pattern: producers append + set a per-session threading.Event; the SSE generator clears-then-rechecks-then-waits(15) to avoid the lost-wakeup race, and pings double as keepalive.
- TUI inline mode exploits the Textual inline driver's cursor-position invariant (_previous_cursor_position) to print Rich renderables into the terminal's native scrollback above the app (app.py:1187-1222) — Claude-Code-style scrolling without owning the screen.
- ACP stdio capture (dup2 fd 1 -> stderr before any gptme import) guarantees JSON-RPC channel purity regardless of what the core prints; a tiny PyPI stub package (packages/gptme-acp) exists purely so editors can `uvx gptme-acp`.
- Tool calls travel as text inside assistant messages, so every consumer (server continuation loop, TUI collapsibles, webui cards) parses the same artifact — one source of truth, three parsers.
- gptme-* executable discovery for plugin subcommands (cli/main.py:60-86) plus dynamic --help expansion keep the CLI extensible without import cost.

## MVP Guidance
- Build the core first as a library: Message dataclass, JSONL LogManager, tools registry with execute(), and a step() generator with on_token — then the CLI is just a prompt_toolkit loop around it. This mirrors gptme's layering exactly.
- TUI next: Textual App with a VerticalScroll chat, a StreamingMessage widget fed by call_from_thread, Collapsible sections for tool output, and a TOOL_CONFIRM hook that pushes a modal. Skip inline mode, tab-completion overlays, history editing, and the termios watchdog — they're polish (app.py is 40% polish).
- Server: one Flask blueprint is enough — POST /conversations/<id>/messages (append + persist), POST .../step (spawn a thread running your step() against the same LogManager, pushing events onto a per-conversation list + threading.Event), GET .../events (SSE generator copying gptme's connected/ping/index/wait loop verbatim). Copy the token-batching and events_count offset ideas.
- Do NOT reimplement chat.step on the server like gptme did (session_step.py:741 duplicates it for event control); instead have step() emit events via an injectable observer if you want to avoid the divergence gptme lives with.
- Frontend: React + Vite; a single ApiClient class owning one EventSource per conversation with the event-type switch, a useConversation hook doing append-message-then-POST-step, and markdown rendering with a fence-regex tool-call parser + allowlist. Radix/Tailwind is convenience, not substance.
- Steal the epoch/step_seq interrupt protocol and the confirm/skip/auto pending-tool flow from day one — retrofitting concurrency control is much harder than building it in.
- Defer entirely: ACP (both roles), A2A, OAuth PKCE, panels/artifacts/preview-proxy/computer-use/tasks blueprints, Tauri desktop wrapper, OpenAPI docs, metrics, multi-server webui. Each is a separate product; gptme's ACP alone is ~2.5k lines.
- Order: core+CLI -> TUI -> server+webui. Each stage exercises the same step() contract and hardens it for the next transport.

## Open Questions
- The server runs Flask's built-in dev server (server/cli.py:400 app.run) — each SSE connection holds a worker thread for the connection's lifetime; how this scales (and whether waitress/gunicorn is used for the hosted deployment at chat.gptme.org) isn't visible in-repo.
- session_step.step() is a hand-rolled parallel of chat.step() (~400 lines) because it needs message-at-a-time event emission and continuation control — a known duplication; anything learned about one loop must be checked against the other.
- webui's toolCallParser.ts regex and GPTME_TOOL_ALLOWLIST can drift from the server's ToolUse parsing (e.g. new tools, XML/tool formats are not rendered as tool cards in the browser — only markdown fences).
- The webui SSE client keeps at most MAX_CONNECTED_CONVERSATIONS=3 streams open (useConversation.ts:42) and relies on the server's in-memory SessionManager; a server restart loses all sessions but the `connected`-with-new-session_id handshake makes that survivable — how tool outputs produced during the disconnect gap reach the client (answer: message_added/LogManager reload) is only implicit.
- ACP prompt() streams agent text but forwards tool-result messages only after the whole turn completes in the executor loop — whether Zed shows live tool output mid-turn depends on the tool_call update path (_report_tool_call), which I did not fully trace.
- The `elicit` endpoint (api_v2_sessions.py:1032) and resolve_hook_elicitation imply an interactive structured-input tool ('elicit') whose hook blocking mechanism mirrors TOOL_CONFIRM but lives outside the assigned scope (hooks/).
