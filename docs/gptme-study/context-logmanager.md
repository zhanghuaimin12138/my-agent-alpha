# context-logmanager(消息、日志/会话持久化、上下文管理、系统提示词构建器)

> 译自英文原版(见 git 历史 aaf0543),由 Claude 翻译

## Purpose(目的)
这个子系统是 gptme 的记忆脊柱。它定义了每一轮对话(user、assistant、工具输出、系统提示词)共用的唯一 `Message` dataclass;以 append-only(只追加)JSONL 目录的形式把会话持久化到 `~/.local/share/gptme/logs/<conv-id>/` 下,支持分支(branch)、压缩后的"视图(view)"、WAL 风格的事件日志(event log),以及内容寻址(content-addressed)的文件附件;它把存储的日志转换为最终发给 provider 的提示词(文件内容嵌入 enrichment、带 TTL 的临时消息修剪、token 上限截断、孤儿工具调用对的修复);它还构建分层的启动系统提示词(身份 + 工具文档 + 用户/项目/工作区上下文 + 动态的日期/git-status 小节),并以固定(pin)的隐藏系统消息的形式种入(seed)日志。`context/` 包提供了可选开的上下文管理(预算配置、文件/教训(lesson)选择策略、基于 zlib 的新颖度分析、自适应压缩、以及用便宜模型做的"侦察(scout)"预处理),而 `session.py` 在 LogManager 之上为 server/ACP 前端提供了内存中的会话注册表。

## Key Files(关键文件)
- **gptme/message.py** — 唯一的消息类型。`Message` frozen dataclass(第 280 行),含 role: Literal['system','user','assistant']、content、timestamp、files/file_hashes、call_id、pinned/hide/quiet 标志、ephemeral_ttl、metadata。序列化:to_dict(379,供日志用的 JSON)、to_toml/from_toml(449/509,供手工编辑)、msgs2dicts(809,面向 LLM 的 dict,键为 role/content/files/call_id)。MessageMetadata TypedDict(164)携带 model/cost/usage/timings/artifacts;_migrate_metadata(218)升级旧的扁平日志。print_msg/format_msgs(683/577)为终端或 JSONL stdout 渲染(ContextVar _output_format,第 39 行)。
- **gptme/logmanager/manager.py** — 核心持久化。`Log` 是对 list[Message] 的 frozen 包装,带一个持久化游标(append cursor,追加游标)(persisted/persisted_path/persisted_size,第 72 行),通过 _can_append 的对象同一性(identity)检查(128)与原子的 write_jsonl(158:临时文件 + fsync + os.replace + 目录 fsync)实现 O(new) 的追加。`LogManager`(219):加载分支/视图,通过 .lock + fcntl/msvcrt 锁定目录并带过期 PID(stale-PID)恢复(333-435),append() 同时双写(dual-write)到视图与主日志(542),edit()/undo() 带备份分支(740-786),fork()(971),视图的创建/切换/恢复(871-969)。`prepare_messages`(1137)就是"日志 → 提示词"的流水线;prune_ephemeral_messages(1005)、_merge_consecutive_messages(1044)、ephemeral_cache_boundary(1075)、_active_prompt_generation(1094)、_gen_read_jsonl(1230,前向兼容的读取器,丢弃未知字段)。`_current_log_var` ContextVar(214)让工具能找到当前活跃的日志。

- **gptme/logmanager/conv_checkpoints.py** — 每个会话的 `/backtrack` 标记:ConvCheckpoint(index,label,timestamp) 追加到 conv-checkpoints.jsonl(39),可按 label 或原始消息索引解析(77)。与工作区快照(gptme/checkpoint.py)是两回事。

## Key Abstractions(关键抽象)
- **Message (gptme/message.py:280)** — frozen dataclass,role: Literal['system','user','assistant'] | content: str | timestamp: datetime | files: list[FilePath|URI] | file_hashes: dict[str,str] | call_id: str|None | pinned: bool | hide: bool | quiet: bool | ephemeral_ttl: int|None | metadata: MessageMetadata|None | terminal_display_content: str|None。没有单独的 tool_call/tool_output 消息类型:工具调用以围栏代码块(fenced block)的形式存在于 assistant content 中,由 ToolUse.iter_from_content 解析(gptme/tools/base.py:839,字段 tool/args/content/kwargs/call_id/start/_format),工具输出则存储为带 call_id 的 role='system' 的 Message。相等性/哈希只使用 (role, content);replace()/concat()(330)合并同 role 消息并保留标志,TTL 取最小值。
- **Log (gptme/logmanager/manager.py:72)** — 对 list[Message] 的 frozen 包装,外加持久化游标(persistence cursor)(persisted: 按对象同一性比较的 tuple[Message,...]、persisted_path、persisted_size)。read_jsonl(path, limit) 加载并标记游标;write_jsonl(path, append=True) 在 _can_append() 验证了相同路径、相同大小、结尾有换行、且已持久化前缀对象同一之后,只追加游标之后的消息——否则通过 NamedTemporaryFile+fsync+os.replace 原子地重写并返回更新后的 Log。这让常规路径的开销是 O(新消息数),同时保证编辑/截断安全。
- **LogManager (gptme/logmanager/manager.py:219)** — __init__(log, logdir, branch='main', lock=True, view=None)。持有 _branches: dict[str, Log](main → conversation.jsonl,其他 → branches/<name>.jsonl)与 _views: dict[str, Log](views/<name>.jsonl)。log 属性在设置了视图时返回当前视图,否则返回当前分支;append() 先按哈希对附件做快照,在视图激活时同时双写 main+view;write(branches=True, sync=False) 持久化一切并可选地对文件+事件日志+目录做 fsync。暴露 workspace(logdir/workspace 符号链接,带 ChatConfig 回退,451)、name、fork()、branch()、diff()、create_view/switch_view/switch_to_master(以 views/.current 标记,加载时恢复)、undo(n)、edit(new_log)。类方法 load(logdir, initial_msgs, branch, create, lock) 把相对路径解析到 get_logs_dir() 之下并重新挂上追加游标(787-836)。
- **prepare_messages(msgs, workspace, logdir) (manager.py:1137)** — "存储日志 → provider 提示词"的变换:(1) _active_prompt_generation 把最新生成的系统提示词移到最前,并让更旧的/遗留的退役;(2) enrich_messages_with_context 嵌入附件文件文本(优先按哈希寻址);(3) prune_ephemeral_messages 丢弃 TTL 过期的消息、修复孤儿工具对、合并相邻同 role 消息(带 call_id 的消息与缓存边界消息豁免);(4) limit_log 硬性限制到模型窗口(理论上不应触发——压缩会更早处理;若触发则告警);(5) 可选的 GPTME_EVIDENCE_REPLAY 从 conversation.jsonl 重新注入被压缩掉的证据(evidence)。由 chat.step(gptme/chat.py:924)和溢出恢复重试(chat.py:861)调用。
- **get_prompt(...) -> list[Message] (gptme/prompts/__init__.py:573)** — 签名:(tools, tool_format='markdown', prompt='full'|'short'|'full-noexamples'|str, interactive, model, workspace, agent_path, context_mode, context_include, include_user_context, include_examples, initial_prompt, prompt_generation, profile)。按三层构建具名小节——core(通过 _join_messages 合并为一条系统消息)、cacheable(工作区/agent 配置,保留为独立消息)、dynamic(systeminfo/timeinfo/runtime/context_cmd/chat-history)——在 cacheable 与 dynamic 之间插入 SYSTEM_PROMPT_CACHE_BOUNDARY 文本,然后把每条消息标记为 hide=True pinned=True(+ 可选 metadata.prompt_generation)。调用方在会话开始时一次性追加这些消息(gptme/cli/main.py:1450、gptme/acp/agent.py:793)。
- **SYSTEM_PROMPT_CACHE_BOUNDARY (prompts/__init__.py:63)** — 一条插入日志的字面量系统消息('# System Prompt Cache Boundary — Static bootstrap content ends above...')。Anthropic 适配器的 _transform_system_messages 会把直到(不含)该边界的所有开头系统消息折叠进唯一的顶层 system 参数(llm_anthropic.py:1263-1275),而 _merge_consecutive_messages 拒绝跨过它合并——它就是显式的提示词缓存断点(prompt-cache breakpoint)。
- **ConversationMeta (logmanager/conversations.py:69)** — 概括一个会话目录的 frozen dataclass:id、name、path、created/modified、messages、branches、workspace、agent_*、model、total_cost/tokens、models_usage、last_message_preview。由 _meta_from_file 构建,要么全量扫描(费用/token 聚合),要么 8KB 尾部扫描配合 (path,mtime) LRU 缓存的行数——这条快速路径支撑 list/search 端点。
- **eventlog recover_messages(logdir) (logmanager/eventlog.py:273)** — WAL 恢复:找到最新的 checkpoint 事件,加载其 payload['messages'],重放其后的 message_append/undo/message_edit 事件,返回消息 dict(不存在 events.jsonl 时返回 None)。每 50 个事件做一次 checkpoint;write_checkpoint 还会在追加所用的同一 flock 侧车下压缩掉被取代的事件。
- **ContextConfig / ContextSelector (gptme/context/)** — ContextConfig(config.py:11):enabled、budget(0<x≤1 的比例,或 int>1 的绝对 token 数,否则动态取 min(0.9*window, window-max_output-headroom))、scout_model、嵌套 selector 配置。ContextSelector.select(query, candidates: Sequence[ContextItem], max_results) 支持 rule/llm/hybrid 策略;file_selector 送入按提及度/新近度/git-status 加权的工作区文件(git ls-files)。可选开——默认路径完全不使用这些。
- **BaseSession / SessionRegistry (gptme/session.py:21/56)** — BaseSession(id, log: LogManager|None, conversation_id, cwd, active, created_at, last_activity),带 touch()/deactivate();SessionRegistry 是一个 dict 包装:create/get/remove/list_sessions/cleanup_inactive(max_age_minutes=60)。纯进程内的句柄跟踪,服务于 ACP(直接传递 log)与 server(conversation_id,惰性加载)——持久化状态完全存在于 LogManager 的文件里。

## Data Flow(数据流)
STARTUP:cli/main.py 通过 get_logdir 选出 logdir(1598)→ generate_conversation_id 生成 'YYYY-MMDD-<slug>'(util/auto_naming.py:69)→ get_prompt(tools, workspace, ...)(prompts/__init__.py:573,在 cli/main.py:1450 被调用)组装出 [core_system_msg, workspace_msgs..., CACHE_BOUNDARY, dynamic_msgs...],每条都 pinned+hidden → chat() 种入一个全新的 LogManager 并把这些追加到 conversation.jsonl。
TURN:用户 Message 经 LogManager.append 追加(manager.py:542)——附件快照到 files/<hash>(manager.py:569,util/file_storage.py:45),日志增量写入(Log.write_jsonl 追加路径,manager.py:158),一条 message_append 事件追加到 events.jsonl(manager.py:494→eventlog.py:129)。随后 chat.step(chat.py:895)调用 prepare_messages(log.messages, workspace, logdir)(manager.py:1137):活跃提示词代(generation)选择 → 文件内容嵌入(util/context.py:262)→ ephemeral-TTL 修剪 + 孤儿修复 + 同 role 合并(manager.py:1005-1072,util/reduce.py:553)→ limit_log 硬上限(util/reduce.py:624)。得到的 list[Message] 交给 provider 适配器:msgs2dicts(message.py:809)→ _handle_tools 把 assistant content 中的工具块转换为 API 的 tool_calls,把 system+call_id 消息转换为 role='tool'/tool_result(llm_openai.py:1790,llm_anthropic.py:1432),_transform_system_messages 把开头的 system 块折叠进 Anthropic 的 system 参数并放置 cache_control 断点(llm_anthropic.py:1232,1394-1440)。流式产出的 assistant Message(工具调用内嵌于 content)被追加到日志;execute_msg 解析 ToolUse 块(tools/base.py:839)并执行,把每个工具输出作为带 call_id 的 system Message 追加。发生上下文长度错误时,_reply_with_overflow_recovery 通过 compact_for_overflow 压缩,把结果存为新视图(views/compacted-NNN.jsonl),切换过去,重试 prepare_messages,并记录一个压缩事件(chat.py:823-892)。
SHUTDOWN/RESUME:write(sync=True) 对转录文件、事件日志和父目录做 fsync(manager.py:610-687,durability.py:75)。恢复 = LogManager.load(logdir) 重新读取 conversation.jsonl(并从 views/.current 恢复活跃视图,manager.py:940);若 JSONL 受损,eventlog.recover_messages 从 checkpoint+events 重建状态(eventlog.py:273)。列出/搜索会话使用 conversations.py 的尾部扫描快速路径。

## Design Highlights(设计亮点)
- 三 role 的 Message + call_id 约定:把工具调用存进 assistant content(markdown/XML 块),把工具输出存为以 call_id 为键的 system role 消息,使磁盘上的日志与 provider 无关且人类可读;provider 适配器只在请求时重建原生的 tool_calls/tool_result(llm_openai.py:1790,llm_anthropic.py:1432)。一种格式挺过 provider API 的更迭。
- 不可变 Log 上的追加游标(append cursor):按对象同一性(而非计数)比较已持久化消息,加上文件大小 + 结尾换行检查,使追加开销为 O(新消息数),同时仍能捕获原地编辑、截断和重排;完整重写走临时文件 + fsync + os.replace,崩溃绝不会毁掉上一份转录(manager.py:128-205)。
- 双写视图代替破坏性压缩:压缩把压缩副本写到 views/compacted-NNN.jsonl 并切换活跃指针(views/.current);conversation.jsonl 永远保留完整历史,所以压缩可逆且可审计(manager.py:871-969)。
- 显式的 SYSTEM_PROMPT_CACHE_BOUNDARY 消息:日志里的字面量标记把静态引导内容与会话易变上下文分开,同时兼任 Anthropic 缓存断点与合并屏障(prompts/__init__.py:63,llm_anthropic.py:1269)。
- 带轮次计数 TTL(ephemeral_ttl)的临时(ephemeral)消息在不触碰磁盘的情况下从上下文中丢弃 thinking 块,并在第一条 ephemeral 消息之前算出一个稳定的缓存边界(manager.py:1075),配合孤儿工具对修复,使修剪绝不会产生 API-400 序列(util/reduce.py:553)。
- 内容寻址附件(files/<sha256><suffix>)加 Message.file_hashes,让 prepare_messages 即使在工作副本已变的情况下也能重新嵌入消息时刻的文件内容——免费获得快照语义(manager.py:569,util/context.py:262)。

## MVP Guidance(MVP 指引)
- 先复刻承重的 20%:(1)单一的 frozen Message dataclass,含 role/content/timestamp/files/call_id/pinned/hide,以及 to_dict/from-JSON 往返;(2)每个会话一个 JSONL 文件(append-only,每行一个 dict),放在 logs 目录下,用日期前缀的 id;(3)一个带 append/write/load 和简单文件锁的 LogManager;(4)作为显式流水线的 prepare_messages(嵌入文件附件 → 裁剪到窗口);(5)一个返回少量 pinned 隐藏系统消息(身份、工具、用户、项目、日期)的 get_prompt(),在会话开始时一次性追加。
- 尽早采用工具调用约定:assistant content 以围栏块内嵌工具调用;工具输出是带 call_id 的 system role 消息;在请求时写一个到你 provider 原生格式的转换器。这一个决定就能让你的日志可移植、可调试。
- 廉价地照搬缓存边界思想:静态提示词内容放前,易变内容(日期、git status)放后,中间放一行标记——不需要在日志层写任何 provider 特定代码就获得 provider 的提示词缓存。
- 按这个顺序依次添加:经 temp+replace 的原子写入;等日志变大再做追加游标优化;分支/undo 用副本实现(编辑前做备份分支,简单得微不足道且有效);内容哈希的附件存储。
- MVP 阶段完全跳过:events.jsonl WAL + checkpoint(只有当你承诺崩溃持久性时才需要)、views/压缩机制(先只用"在提示词内截断",绝不重写磁盘)、整个 context/ 包(选择器策略、zlib 新颖度分析、自适应压缩器、scout 预处理——全是可选项)、conv-checkpoints 侧车、model_selection_trace、证据重放(evidence replay)、TOML 往返编辑支持,以及快速尾部扫描的会话列表(小规模下全量扫描足够)。
- 只有在你构建 server 时才保留 session.py 的形状(id → LogManager 句柄的注册表,带最后活跃时间清理);CLI 只需要一个模块级的"当前日志"引用(他们的 ContextVar 模式值得照抄,用于线程安全)。
