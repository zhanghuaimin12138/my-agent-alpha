# Extensibility & Configuration (commands, hooks, plugins, config, MCP, sandbox, credentials, profiles)

## Purpose
This subsystem is gptme's entire extension surface and runtime configuration spine. It provides four user-facing extension mechanisms — slash-commands, lifecycle hooks, folder/entry-point plugins (which bundle tools+hooks+commands+LLM providers), and MCP servers (both as a client consuming external tools and as a server exposing gptme's tools) — all sitting on a layered TOML configuration model (per-chat config.toml > project gptme.toml > user config.local.toml > config.toml > operator config.runtime.toml > built-in defaults) resolved through a ContextVar-scoped `Config` object. It also owns the security envelope around all this extensibility: a TOFU trust gate for project-declared shell hooks, a hook-based tool-confirmation/permission system (CLI prompt / server SSE / auto-confirm / deterministic guardrails), opt-in OS-level sandboxing of the persistent bash shell (firejail/bwrap/docker/wasmtime), an env-var allowlist that strips provider API keys from subprocesses, and a 0600-mode credentials.toml store. Startup orchestration lives in gptme/init.py, which orders plugin discovery, model init, tool loading, hook registration, trust checks, script-hook registration, and command registration.

## Key Abstractions
- **command(name, aliases=None, completer=None, auto_undo=True) decorator + register_command(name, handler, aliases, completer, owner_tool=None)** — Two ways to add a slash-command. The decorator (commands/base.py:54) is for built-ins: it wraps the handler so `ctx.manager.undo(1, quiet=True)` removes the command message from the transcript before execution, registers name+aliases in the process-global `_command_registry`, and optionally a tab-completer `Callable[[partial_arg, previous_args], list[(completion, desc)]]` in `_command_completers`. `register_command` (line 102) is the dynamic path used by ToolSpec.register_commands() and plugins; setting `owner_tool` records ownership in `_command_owners` and dispatch/listing then require `has_tool(owner)` in the current session — process-global registry, session-local enforcement.
- **CommandContext(args: list[str], full_args: str, manager: LogManager)** — Single context object passed to every command handler; handlers are generators yielding Messages (or return None). The single-dataclass shape means new fields never break existing handlers.
- **HookType (str Enum) + HookFunc protocols** — ~24 lifecycle points in dot notation (hooks/types.py:66). Standard hooks are generators `(*event_args, **kwargs) -> Generator[Message | StopPropagation]`; signatures are Protocol classes (SessionStartHook, ToolExecutePreHook(data: ToolExecutePreData), GenerationChunkHook, FilePreSaveHook, etc.), and `register_hook` uses typing.overloads so a Literal HookType binds the correct Protocol statically.
- **Hook dataclass (name, hook_type, func, priority=0, enabled=True, async_mode=False)** — Registry unit (hooks/types.py:382). Higher priority runs first; same-name re-registration replaces; async_mode=True runs the hook in a daemon thread with a copied context (fire-and-forget telemetry/notifications). `__lt__` sorts by (priority, name) descending.
- **StopPropagation** — Empty sentinel class a hook yields to halt all lower-priority hooks for that event (hooks/types.py:54). In async mode it is logged and ignored.
- **ToolConfirmHook -> ConfirmationResult** — The permission-model exception within the hook system (hooks/confirm.py:135): confirmation hooks RETURN `ConfirmationResult(action=confirm|skip|edit, edited_content, message)` rather than yielding; tried in priority order, first non-None wins, None = fall through. `get_confirmation()` is the single entry point every tool calls; with zero registered hooks it auto-confirms (autonomous mode). Implementations: cli_confirm (0), server_confirm (100), auto_confirm (0), guardrails (200).
- **GptmePlugin (unified plugin manifest)** — Dataclass (plugins/plugin.py:22) normalizing every discovery mechanism: provider (ProviderPlugin for custom LLM providers), tool_modules (module names to scan for ToolSpecs), tools (direct ToolSpec instances), register_hooks / register_commands (callables invoked by init_hooks/init_commands), init(Config) (once-at-discovery lifecycle hook reading `[plugin.<name>]` config). Folder plugins are adapted via `_folder_plugin_to_gptme_plugin` which wraps their hook/command module lists in import-and-call-register() closures.
- **ToolSpec.hooks / ToolSpec.commands** — Declarative per-tool extension: a ToolSpec may carry `hooks={name: (hook_type_str, func, priority)}` and `commands={name: handler}` (tools/base.py:518-519); `_init_single_tool` calls `tool.register_hooks()` (namespaced `<tool>.<hookname>`) and `tool.register_commands()` (owner_tool=self.name) when the tool loads, and unload_tool unregisters the hooks — so loading a tool atomically wires its whole extension surface.
- **Config (user: UserConfig, project: ProjectConfig|None, chat: ChatConfig|None, _model_source)** — Aggregate resolved object (config/core.py:44) stored in a ContextVar. Key methods: `get_env` (env>chat>project>user fallback chain used for MODEL, TOOL_MODULES, HOOK_ALLOWLIST, API keys), `mcp` property (server union with chat-first precedence), `get_script_hooks()` (user+project sorted by priority desc), `get_plugin_config()` (paths + union allowlist). Explicitly documented as a resolve-object, not a pass-around god object.
- **MCPServerConfig(name, enabled, command, args, env, url, headers) + MCPConfig(enabled, auto_start, servers)** — TOML schema for MCP: `[[mcp.servers]]` entries; `is_http` property picks streamable-HTTP vs stdio transport; stdio servers inherit the full parent environment with their env merged on top (mcp/client.py:297-298). Merging across config layers is by server name with env-dict merging (config/user.py:906-967).
- **MCPClient** — Sync facade over the async MCP SDK (mcp/client.py:60): owns a private asyncio event loop, an AsyncExitStack holding transport+ClientSession, per-server CircuitBreaker, roots list, elicitation callback. `connect(name)` -> (ListToolsResult, ClientSession); `call_tool(name, args)` -> str; `close()` with cancellation and 5s bound.
- **create_mcp_tools(config) -> list[ToolSpec]** — Bridge that makes each remote MCP tool a first-class gptme ToolSpec named `<server>.<tool>` (tools/mcp_adapter.py:200), including JSON-Schema->Parameter conversion, annotation->hint mapping, confirmation integration, and connection-error retry with client restart. Called from get_available_tools so MCP tools flow through the same allowlist machinery as native tools.
- **SandboxConfig + wrap_shell_cmd/build_env** — Env-var-driven sandbox policy (sandbox.py:91): backend in {firejail, bwrap, docker, wasmtime, none}; the shell tool composes `apply_memory_limit` (inner) then `wrap_shell_cmd` (outer) then `build_env` at Popen time; secrets never enter the subprocess env because the allowlist excludes provider keys by design.
- **Profile / ProfileBehavior** — Agent capability bundles (profiles.py:56): system_prompt + tools allowlist + soft behavior flags (read_only, no_network, confirm_writes). Hard enforcement comes from only loading the listed tools; built-ins cover explorer/researcher/verifier/isolated etc.; user profiles in ~/.config/gptme/profiles/ as TOML or markdown+YAML-frontmatter.
- **TOFU trust: compute_shell_hash / check_project_shell_trust** — Security gate (config/trust.py): sha256 over the canonical {context_cmd, sorted hook commands]} scoped per resolved workspace, persisted in project-trust.toml, deny-by-default when non-interactive, bypass via GPTME_TRUST_PROJECT_SHELL=1. Guards against cloned repos shipping a malicious gptme.toml.
- **credentials.toml store** — `[providers.<name>] = key` file at ~/.config/gptme/credentials.toml written with 0600 (credentials.py:52-69); the last-resort API-key source after process env and the config [env] tables; read by doctor, /account, and the openai/anthropic provider clients.

## Design Highlights
- Everything-is-a-hook symmetry: even the permission prompt is a hook (TOOL_CONFIRM) with three interchangeable implementations (CLI tty prompt, server SSE round-trip, auto-confirm) selected purely by init mode — one registry, two contracts (generator-yields-Messages vs returns-ConfirmationResult-with-None-fallthrough).
- Generator-based hooks that yield Messages directly into the conversation log: an extension can inject context (time_awareness), rewrite messages (message.transform), or veto execution (StopPropagation sentinel) without any callback plumbing in core code.
- Tool-owned commands with split scope: the command registry is process-global (shared by sibling server sessions) but dispatch checks the session-local loaded-tool set (_command_owners + has_tool), avoiding the classic multi-session bleed when one conversation unloads a tool.
- ContextVar-everything: config, hook registry, loaded tools, auto-confirm state, and the current ToolUse are all context-local, which is what makes the single-process multi-conversation server and subagent threads safe without locks on read paths.
- GptmePlugin as a normalization boundary: folder plugins, pip entry-point plugins, legacy provider entry points, and even bare ToolSpec exports all reduce to one manifest dataclass, with an editable-install dedup (folder shadows entry point) and an allowlist checked BEFORE ep.load() so a disabled heavy plugin costs zero import time.
- Layered TOML with name-aware merging: config.runtime.toml (operator defaults, read-only, strict-fail) -> config.toml -> config.local.toml (secrets) at user level; gptme.toml -> gptme.local.toml at project level; per-conversation config.toml at chat level — with MCP servers and [[providers]] merged by name (env dicts merged) instead of replaced, and mtime-keyed lru_cache for project configs.
- Provenance-tracked model resolution: resolve_model_source returns not just the model but which of 7 layers it came from (cli/chat_config/environment/project/models.default/MODEL), recorded in a ModelSelectionTrace — great UX for 'why am I on this model?' debugging.
- TOFU trust gate for project shell hooks: sha256 of the canonical command set scoped per workspace, deny-by-default in non-interactive contexts, byte-level .orig backups before any guessed-encoding rewrite — cloned-repo supply-chain defense done cheaply.
- Sandbox env allowlist that deliberately excludes provider API keys (LLM calls happen in the parent process), turning 'sandbox bypassed' from 'credentials leaked' into 'workspace escaped only'; BASH_ENV is unset before ulimit so startup scripts can't pre-allocate outside the memory ceiling.
- MCP client as a sync facade over a private asyncio loop with per-server circuit breakers, connection-error retry that transparently restarts the server process, a 60s init timeout to accommodate interactive OAuth, and MCP elicitation bridged into the same elicit hook the native UI uses — so server-side user-input requests get the CLI/WebUI for free.
- MCP works in both directions from one tool abstraction: gptme consumes external MCP servers as `<server>.<tool>` ToolSpecs AND exposes its own tools as an MCP server (GptmeMCPServer) with persistent shell state injected into executor threads via ContextVar pre-seeding.
- Graceful degradation discipline everywhere: malformed user-config MCP/provider entries are skipped with a warning instead of crashing --help; unknown top-level config keys are auto-stripped from disk after a single warning; plugin init/register failures are logged and isolated per plugin.

## MVP Guidance
- Build in this order: (1) ToolSpec + module-scan discovery (import module, collect ToolSpec instances — ~30 lines); (2) the hook registry: Hook dataclass with priority, one dict[HookType, list[Hook]], generator trigger with StopPropagation, ContextVar storage; (3) the command registry: @command decorator + handle_cmd with tool fallback; (4) layered config: user config.toml + project gptme.toml + per-chat config.toml with a single get_env() precedence chain — this quartet is 80% of gptme's extensibility value.
- Start with a small HookType set: session.start/end, step.pre/post, tool.execute.pre/post, tool.confirm, turn.post. gptme's file.patch.*, generation.chunk, cache.invalidated, cwd.changed are refinements you add when the corresponding features exist.
- Make the permission prompt a TOOL_CONFIRM-style hook from day one (return-result-with-None-fallthrough, priority order) rather than a hardcoded input() — it's what later gives you --no-confirm, server mode, and deterministic guardrails for free.
- Copy the ToolSpec.hooks/ToolSpec.commands pattern: loading a tool auto-registers its hooks and slash-commands, unloading unregisters them. This makes tools self-contained extension bundles and dodges lifecycle wiring bugs.
- Copy the two-secret-file convention early: config.toml committable, config.local.toml for API keys (or a separate 0600 credentials.toml), plus the env > chat > project > user lookup order in ONE function.
- MCP: use the official Python `mcp` SDK with the private-event-loop-per-client + run_until_complete pattern (gptme/mcp/client.py:63-111) so your sync agent loop can call async MCP; one ToolSpec per remote tool named server.tool; wrap calls in the confirmation flow. Skip roots/resources/prompts/elicitation and the MCP-server direction for v1.
- Plugins: support folder-based discovery (dir with tools/ hooks/ commands/ subdirs) first; add entry-point (`gptme.plugins` group) discovery only when you have external users; always gate entry-point loads on the allowlist before import.
- Sandboxing is phase 2+: begin with just the env allowlist (strip everything not explicitly allowed — it's ~10 lines and blocks credential exfiltration even without a sandbox), then bwrap or firejail for stdio shell, docker for python. Keep it env-var driven like GPTME_SANDBOX so it's opt-in.
- Trust gate: if you support project-level config files that can define shell commands (hooks.scripts / context_cmd), implement the TOFU hash store — it's ~100 lines and closes the biggest supply-chain hole.
- Skip entirely for an MVP: encoding-fallback byte backups, Claude Code memory-dir interop, the official MCP registry search, model-selection attestation traces, per-plugin init timing logs, and the markdown-with-frontmatter profile format (TOML profiles suffice).

## Open Questions
- MCPConfig.auto_start is defined, merged across layers (config/core.py:116-122), and documented in gptme.toml, but no code outside gptme/config/ reads it — appears to be a vestigial or not-yet-wired flag.
- The hook allowlist is only readable from the HOOK_ALLOWLIST env var; the init_hooks comment (hooks/__init__.py:150-152) notes chat-config hooks 'could be added later' — config-file hook selection is currently absent.
- HookType.TOOL_TRANSFORM and MESSAGE_TRANSFORM are declared in the enum; message.transform is used by hooks but tool.transform has no visible trigger site in this subsystem — may be dispatched from tools/base.py internals or simply unimplemented.
- SettingsConfig is an empty dataclass on both user and project sides (config/models.py:226) — a placeholder for future CLI/runtime defaults; the loader tolerates and discards a removed 'gear' key.
- Config.mcp merge semantics: server lists union with chat-first name precedence, but enabled/auto_start are taken wholly from the outermost layer that defines [mcp] — a user-level enabled=true with project servers can be silently switched off by a chat config that defines [mcp] enabled=false with no servers.
- The MCP stdio transport passes the FULL parent environment to server subprocesses (env.update(os.environ), mcp/client.py:297-298) — deliberate for compatibility, but it means MCP servers (e.g. npx-launched ones) see all provider API keys, which contrasts sharply with the sandbox env-allowlist posture; worth deciding intentionally in a re-implementation.
