## 一、长期记忆(memory_store.py + tools/memory.py)

gptme 设计的落地(memory 模块,见研究报告 context-engine 节):
- 一条记忆 = 一个 markdown 文件,两层目录"近的盖住远的":
  工作区/memory/(项目层)> 数据目录/memory/(用户层);
- MEMORY.md 自动索引,会话开始注入系统提示词(64KB 预算,gptme 同款);
- 写入走 memory 工具(非只读 → 确认链把关):模型提议、用户点头;
- /memory(别名 /mem)命令查看,/memory show <名> 看全文;
- 需要细节时模型自己用 read 工具看原文 —— 索引只给指针,这正是
  "把日志/文件当唯一事实来源"哲学的延续。

## 二、subagent(tools/subagent.py)

gptme 的 MVP 路线(研究报告:"subprocess mode first"):
- 子代理 = 独立进程(python -m my_agent_alpha -n -y),自己的会话日志
  (subagent-<id> 目录),跑完即退,崩了不连坐父会话;
- 提示词从 stdin 传入("-" 约定,防超长命令行);模型默认继承父会话
  (新增 context 模型 ContextVar);结果 = 子日志的最后一条模型回复
  —— "日志是唯一事实来源"的又一次红利;
- 与 gptme 的差异(记录):gptme 是 fire-and-forget + 钩子通知、可并行;
  我们同步等待 —— 简单正确,异步版等真实需求。

## 三、MCP 客户端(mcp_client.py)

gptme 的核心做法照搬:**远端工具 → 本地一等 ToolSpec**,命名
`服务器.工具`,参数从 JSON Schema 换算 —— 确认链、系统提示词、
双调用通道全部自动适用,零特殊分支。

- 配置:alpha.toml 的 [[mcp.servers]](name/command/stdio);
- 同步桥接异步 SDK(和 gptme 一样的坑):每客户端一个专属事件循环
  线程 + 常驻会话协程(连接/列举/调用/关闭全在同一任务,规避
  anyio 取消作用域的"跨任务退出"限制),同步侧经队列投递;
- 单个服务器连不上告警跳过(gptme 容错姿态);会话结束统一 close;
- **mcp SDK 2.x 适配**:FastMCP 已改名 MCPServer、工具对象字段
  input_schema(旧 inputSchema 兜底)—— 测试服务用 v2 API 写。
