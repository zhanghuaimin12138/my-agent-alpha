# 041 —— token 估算改造:len_tokens(中文单价修正 + 缓存)

## 目标

按 [docs/token-counting-dev.md](../token-counting-dev.md)(gptme/util/tokens.py 的移植方案)
重写 token 估算:修正中文系统性低估的旧规则,加内容哈希缓存。
方案评审记录见对话:采纳 D1/D2/D4/D5/D6/D7,三处按本项目情况调整。

## 决策及理由

- **核心改动(D5)**:单价从"英文÷4 + 中文÷1.5字符/token"改为
  "中日韩每字 1 token + 其余字符÷4 向上取整"。
  理由:错误方向比错误大小更重要 —— 高估只是提前压缩(浪费窗口),
  低估是"以为装得下实际装不下",请求直接被接口拒。
  旧规则对纯中文低估 4 倍(cl100k 实测 1.0 字符/token vs 估算的 0.67)。
  纯英文/代码数字完全不变((n+3)//4 与 -(-n//4) 同一个式子)。
- **照抄 gptme 的部分**:`_is_cjk` 五个码位区间;缓存用内容 SHA-256 做 key
  (不存原文)、上限 1000(用户确认,不放大到 5000)、满了删最早插入的、
  不加锁(dict 单操作原子,最坏是并发重复算一次);只数消息的 content 字段。
- **与方案文档的三处不同**:
  1. 鸭子类型(hasattr)→ 显式联合类型 `str | Message | Sequence[Message]`,
     因为本项目 mypy strict 且有正式 Message 类;
  2. 删掉 `estimate_tokens`/`messages_tokens` 不留别名,统一为 `len_tokens`
     (与 gptme 同名,方便对照源码);引用点一次改完;
  3. §5 的三档位比例和 `context_usage()` 不做 —— 项目已有 `get_context_budget`
     (绝对数版"宁低勿高"),且没有第二个调用方需要比例。
- **压缩阈值不重标定**(`_TOOL_RESULT_THRESHOLD=2000` 等):新规则只让中文内容
  估算变大(→ 更早压缩,安全方向),英文不变;等日志里攒够真实 usage 再调。
- **文档挪位置**:token-counting-dev.md 从 src/my_agent_alpha/utils/(源码包)
  挪到 docs/。注意它内部引用的 token-counting.md、autocompact-dev.md
  不在本仓库,链接是悬空的,留着没动。

## 改动结构

- `src/my_agent_alpha/utils/tokens.py`:重写 —— `_is_cjk`/`_estimate`/
  `_token_cache`/`len_tokens`(带缓存);`get_context_budget` 原样保留。
- `src/my_agent_alpha/utils/__init__.py`:导出改为 `len_tokens` + `get_context_budget`。
- `src/my_agent_alpha/compaction.py`:导入与 8 处调用点换名,压缩逻辑零改动。
- `chat.py` 不动(只用 get_context_budget)。
- `tests/test_tokens.py`(新建):方案 §6 的 8 个用例 + 实测样本方向性断言
  + 预算测试(从 test_compaction 搬来);autouse fixture 清缓存保证隔离。
- `tests/test_compaction.py`:估算/预算测试移出,`messages_tokens` → `len_tokens`;
  其余断言**一个没改** —— 核算过:测试数据以 ASCII 为主,中文部分估算变大
  只会让压缩更早触发,`<= budget+余量` 类断言全部照旧通过。
- 开发中修过一处自己的错:混合样本"看一下 gptme 的文件"手数成 7 汉字,
  实为 6 汉字 + 7 非汉字(= 8),测试第一跑挂掉后修正。
