# 016 · 空回复/漏写代码块:自动提醒模型补发工具调用

## 目标

解决踩坑记录条目 3 遗留的问题(当时记为"模型自己抽风,与解析无关"):
真实会话(dashscope/kimi-k3)里,模型**明确需要调用工具**,回复里却
一个围栏代码块都不写,回合静默结束 —— 不报错、不提示,用户只看到空气,
只能自己再敲一遍"结果呢"。实录样本存档在 `docs/tmp.jsonl`。

逐条核对实录,失败的 assistant 回复分三种形态:

| 样本(行号) | 形态 | 当时结局 |
|---|---|---|
| 3、18 | 正文为空:整条回复只有 `<think>`(思考里写着"Let me use the websearch tool")甚至全空 | 静默结束 |
| 6、12 | 正文以冒号结尾戛然而止(如"现在为您查询:") | 静默结束 |
| 9、15 | 围栏写了但格式/键名错 | 已有报错回传,模型可自纠(015 已修) |

## 决策及理由

**两层修:事前把规则说死,事后检测兜底。**

1. 事前(提示词):`prompts` 的两条身份说明(markdown/原生)各加一条
   规则 —— "打算调用"必须落实为正文里真的写出代码块/真的发起函数调用,
   只在思考里想或只用文字描述都不会执行;不要空回复、不要停在冒号结尾的
   半句话上。
2. 事后(检测 + 补发):新增 `missed_tooluse_reason()`,在回合**即将
   因"无可执行调用"结束**时检查最后一条 assistant 回复,命中三种形态
   之一就注入一条**可见的** system 提醒消息(`[工具调用提醒]` 开头),
   再生成一轮(上限 `MAX_TOOL_NUDGES`,默认 1,环境变量
   `ALPHA_MAX_TOOL_NUDGES` 可调);超限则如实报告"本回合结束"。

关键取舍:

- **不碰循环继续判定**。继续条件仍只有"最后一条 assistant 是否有可运行
  ToolUse",提醒只是把"静默 return"变成"提醒 → 再跑一轮";
  `nudges` 计数与 `steps` 同性质的保险丝,不是新的循环状态。
- **检测必须保守**(宁可漏报不误报):冒号只认**结尾**(正文中间的冒号
  是正常行文);围栏标记写岔只在"和某个已知工具名按点号拆段后重合"时才
  提醒(```websearch → websearch.search 算,```python → 谁也不算,
  那是给用户看的示例代码);空正文无歧义,直接提醒。
- **绝不静默**:提醒消息进日志、发给模型、也打印到终端;超限也要写明
  原因再结束 —— 这是踩坑记录"静默失败最危险"教训的直接落实。
- 不做成 hook:hook 只能产出消息,无法表达"别结束、再跑一轮"的循环
  语义;这本质是中层循环的兜底,不是横切关注点。

## 复测迭代(2026-10-05 下午,真机两连测)

上午的修复真机验证:**提醒机制生效**(冒号结尾 → 提醒 → 模型补发了
格式完全正确的调用),但暴露三个残留问题,同日修复:

1. **无冒号的行动宣告漏检**(会话 2026-1005-700ec7 行 9):回复
   "我来帮你查一下上海今天的天气。"—— 宣布要干活但不以冒号结尾,
   检测器放行 → 回合静默结束。修法:检测器加"行动宣告"分支,标记表
   `_ANNOUNCE_MARKERS = ("我来", "让我", "我去", "这就", "马上", "稍等",
   "let me", "i'll ")`,要求正文一个围栏都没有。**只收"我+动作"的词**:
   初版收了"帮你/帮您",真机复测立刻误伤两条正常回答("我可以帮你做
   这些事:"能力介绍、"需要我帮你找找吗?"主动提议),已移除并用
   真机误报原文加了回归用例;
2. **提醒额度不随真实执行重置**(同会话 行 12→20):行 12 漏写 → 提醒
   → 模型补发、工具执行 → MCP 超时报错 → 行 18 模型说"我换个方式
   试试:"想重试 → 额度已用完 → 被迫"本回合结束"。修法:循环尾部改
   显式分支,`has_runnable_tooluse` 为真(真的执行过调用)时 `nudges=0`
   重新计数 —— 额度语义从"整回合 1 次"变为"每段漏写序列 1 次",
   总量仍被 MAX_STEPS 兜底;
3. **原生通道调用编号带点号导致解析整行失败**(会话 2026-1005-332a08,
   独立 bug,详见踩坑记录条目 5):dashscope/kimi 的编号格式
   `websearch.search_0_a475cfc6` 含点号,`_NATIVE_CALL_RE` 的编号字符集
   `[A-Za-z0-9_\-]*` 不认 → 生成端写下的调用行解析回读时零匹配 →
   不执行、不报错、检测器也放行(正文非空无围栏结尾是 `}`)→ 双重
   静默。修法:字符集放宽为 `[A-Za-z0-9_.\-]*`(`tools/base.py`);
   另加检测器兜底分支 `_LOOSE_NATIVE_CALL_RE`:宽松探测命中调用行
   但严格解析出 0 个 → 提醒,防未来服务商再出怪编号格式。

复测回放(两份真机日志原文过修复后的代码):


MCP 超时本身是环境问题(websearch 直连 duckduckgo 不通,踩坑记录条目 2),
不在代码修复范围;修复后模型至少能收到可读的超时报错并有机会换路子重试
(额度重置保证了"报错后再试"不会被掐死)。

## 已知限制

- 冒号结尾、空正文、行动宣告都是**启发式**:"我要先问用户:"这类正常
  反问会被提醒一次,代价是多一轮生成(提醒措辞已写明"无需工具就直接给
  最终回答",模型可体面收场);
- 只检查**最后一条** assistant 回复,回合中途的空回复若后面还有调用则
  不受影响(也无需处理);
- 每段漏写序列默认只提醒 1 次(可用 `ALPHA_MAX_TOOL_NUDGES` 调),
  连续抽风的模型只能靠用户重试(不无限拉锯;总量另有 MAX_STEPS 兜底)。
