# 022 — 长期记忆改进方案(文档)

## 目标

用户研究了《Claude Code 长期记忆架构报告》(docs/长期记忆架构报告.md,基于 2026.3.31 源码快照泄露事件的研究材料,仅作学习参考),要求对照报告给出本项目长期记忆模块的改进方案(明确不做团队记忆),产出 md 文档。本会话**只写方案,不改代码**。

## 决策及理由

1. **按 KISS 分期而非照单全收**:报告覆盖存储格式、三通道注入、后台提取、自动整理、团队同步等一整套;我们按"小改动大收益"排序成 M1-M4 四期 + M5 远期可选。理由:学习项目,记忆规模小,重型机制(轮末提取代理、按需召回)没有触发场景。
2. **M1 优先做 frontmatter description**:报告最有力的结论是"没有向量库,description 就是向量的替代品"——先把地基(格式+提示词纪律)打好,再谈召回。
3. **兼容策略选"读时兼容、写时升级"**:旧记忆文件不主动重写,解析时按默认值回填;只有再次保存才升级格式。理由:不搞迁移脚本,不打扰用户手写的文件。
4. **保留确认链,不学 CC 的权限豁免**:CC 写记忆免确认靠提示词纪律;我们的"模型提议、用户点头"本身就是最好的排除清单,方向不同但更适合本项目。
5. **整理("做梦")做成手动 `/memory consolidate` 命令**:CC 的三重门控(时间/会话/锁)为无人值守设计;手动触发=用户审批,天然安全,复杂度砍半。
6. **明确列出"不采纳"清单**:团队记忆(用户要求)、向量库(报告证明不需要)、提示词缓存微优化(单 provider 无收益)、自动定时 dream、agent 专属记忆目录、注入位置挪移——每条给理由,防止未来会话反复纠结。

## 改动结构

- 新增 `docs/长期记忆改进方案.md`:现状盘点(带 file:line)→ 五条设计标尺 → M1-M5 改进项(每项:报告依据→现状→改法→验收)→ 不采纳清单 → 实施顺序 → 风险注意;
- 新增本 devlog,更新 README 索引;
- **零代码改动**(git status 可验证)。

## 已知限制

- M2 的双上限数值(100 行/16KB)与 M2.2 的过时阈值(30 天)是估计值,待真实使用量校准;
- M4 依赖 subagent 工具支持"按调用定制工具白名单",当前可能不支持——已在方案风险节列为前置小任务;
- 方案未估算 token 成本影响(索引行变长),影响方向:每次会话常驻注入略增,换取模型少 read 若干次,预期净收益为正但未实测。
