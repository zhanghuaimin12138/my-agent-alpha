# 034 · 流式原生工具调用全量用例集(286 条)

## 目标

把 `tmp/agent_tool_parser_test_cases_stream_v2.md`(286 条,9 类工具 + 协议边界 + 围栏通道 + 回归)
全部转成真实可跑的 pytest 用例,测的链路固定为:

```
假流式分片(mock SDK 事件)→ _stream_once() 拼装吐出文本 → ToolUse.iter_from_content() 解析出调用
```

不含:真实网络请求、reply() 断点检测、chat 循环、工具执行。

## 决策及理由

1. **每条用例显式写死三样东西,互不推导**:输入事件、期望文本、期望解析结果。
   最初版本的期望值由输入自动推导(拼接片段 + partition 拆行),被用户否掉——
   "自己出题自己答",期望没有独立性。改后三处手抄互相交叉验证:
   kwargs 抄错 → 断言二炸;片段拼装结果和期望文本不符 → 断言一炸。
2. **沿用假客户端手法**:monkeypatch `_make_client`,SimpleNamespace 伪造 SDK 事件,
   与文件里既有的 reasoning/重试测试同一套路,不发真请求,286 条秒级跑完。
3. **278 条走数据表 + 8 条手写**:7 条非标准 SDK 结构(arguments 是对象、tool_calls 是
   dict/str/含 None、缺 index)用 `pytest.raises` 锁住"当前直接抛 Python 异常"的现状;
   ADV-037(双 choices)单独手写。
4. **第二层期望按"当前代码实际行为"断言,不按文档的建议目标**。写之前先读
   codeblock.py/tools 注册表确认解析行为:围栏只认反引号(`~~~` 不识别)、围栏 content
   末尾换行被 split/join 吃掉、`<think>` 区里的 @调用行会被剥掉、正文中间的
   `@read(...)` 会被当真调用(缺陷清单第 7 条)。实测全部吻合。
5. **逐用例一行注释**:用脚本从 md 提取每条的标题(`### ID · 标题`)自动插入,
   和文档逐条对应,人工概括不抄错。

只动一个文件:`tests/unit/llm/test_openai_compat.py`(480 行 → 约 2650 行)。

- `_frag_case`:§1-§9 九类工具共用的"单调用分片"构造器(174 条);
- `_case`:§10-§13 通用构造器,事件表整体显式(104 条);
- `_use` / `_fence`:两种通道的期望调用五元组 (工具名, 编号, kwargs, 块头参数, 块内容);
- `_mock_chunk`:dict 用例 → 假 SDK 事件(content/reasoning/tc/usage 键);
- `_run_stream_case`:装假客户端跑 `_stream_once`,返回 (完整文本, 用量);
- `test_stream_native_cases`:278 条参数化;`test_stream_native_protocol_errors`:7 条异常;
  `test_adv037_only_first_choice_processed`:双 choices。

## 已知限制 / 发现的问题清单(未修,留档)
