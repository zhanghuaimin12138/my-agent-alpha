# 047 —— LLM 语义压缩 步骤 1:纯函数层

## 目标

按《LLM 语义压缩开发报告》L2(方案步骤 1)落地 compaction_llm.py:
五个纯计算零件 —— 指纹、切分、指令、验货、组装。不调模型、不写磁盘、
不改任何现有行为;规则压缩与 View 存储层零改动(仅 tool_groups 改公开名)。

## 决策及理由

- **`_tool_groups` 改名为公开 `tool_groups`**(compaction.py):规则压缩的
  hard_cap 与本次的 prefix/tail 切分必须共用同一套"完整交互组"规则,
  各写一份迟早漂移(一处修了组边界、另一处没修,就是拆调用链的 bug)。
- **指纹 = 各消息 to_dict 后整体 JSON(键排序)的 SHA-256**:同语义同指纹;
  条数、内容、顺序、metadata 任一变化指纹必变。用途是压缩前后比对,
  防"模型写笔记的几十秒里又来了新消息"。
- **历史拍平成证据文本再给摘要模型**(`[001][USER] …` /
  `[003][TOOL_RESULT call_id=x] …`),不按原样重放消息:旧历史里的原生
  调用/结果对在严格服务商处重放可能报配对错误;拍平后历史只是"材料",
  同时天然防御历史文本里的提示注入(指令明确声明历史是数据不是命令)。
- **七节标题用英文**(Objective/Key Decisions/Current State/Open Items/
  Critical Facts/Context Files/Next Action,说明用中文):模型对英文标题
  的遵循更稳,验货按标题逐个验收,少一节拒收。
- **伪造工具调用检测复用 ToolUse 解析器**:摘要里混入 `@工具(call_x): …`
  行(解析出 call_id)就拒收 —— 这种行存进视图可能被 msgs2dicts 误当
  真调用。检测标准与生产解析器同源,不会"检测器认得、解析器不认"。
- **组装的保留规则一句话**:前缀里的 pinned 消息原样保留(含非系统
  pinned,如用户钉住的关键约束),旧 Checkpoint 除外(它就是要被替换的);
  新 Checkpoint 替换旧的、pinned+hide(防请求级裁剪/终端不刷屏);
  尾部原样。metadata 记 source_view/source_count/source_digest 可追溯。
- **切分"至少保一组,宁可超预算"**:预算连一组都装不下时保留最后一组
  并如实超 —— 总预算校验是组装/服务层的事,这里不产出残缺调用链。

## 改动结构

- `src/my_agent_alpha/compaction.py`:仅 `_tool_groups` → `tool_groups`
  改名(公开),逻辑一字未动。
- `src/my_agent_alpha/compaction_llm.py`(新增):`LLMCompactionConfig`、
  `digest_messages`、`split_for_semantic_compaction`、`find_checkpoint`、
  `build_summary_request`、`validate_summary`、`assemble_semantic_view`、
  七节摘要指令模板。
- `tests/test_compaction_llm.py`(新增,20 个用例):对应报告 UT01~UT10、
  UT13、UT20;含关键集成点 —— **组装结果能通过现有
  validate_compacted_messages 安检**(pinned 在/最后 user 在/配对完整)。
