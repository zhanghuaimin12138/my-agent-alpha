## 一、目标

按路线图搭建 agent 的脊柱:让"消息 → 生成 → 工具 → 追加"这条主线跑起来。

## 二、改动结构

```

├── chat.py            # ★ 三层循环(外层 REPL / 中层 turn / 内层 step)
```

## 三、关键设计决策

1. **继续判定零状态**(chat.py `has_runnable_tooluse`):最后一条 assistant 消息里
   还有可运行 ToolUse 就继续 step —— gptme 循环的心脏,一行不改地移植;
2. **增量消费 step() 产出**:每 yield 一条立刻落盘,中断/异常时已产生的消息不丢;
3. **中断语义**(仿 gptme execute_msg):Ctrl-C 落在工具执行期间 → 已完成结果保留、
   被中断调用给 `[interrupted]` 标记、剩余调用标"未执行"、turn 停止;
   落在 LLM 生成期间 → 外层捕获、追加标记、回提示符;
4. **provider 异常不杀 REPL**:交互模式记 `[LLM 请求失败]` system 消息回到提示符,
   非交互模式重抛(退出码带出去)—— 对应 gptme 的 is_provider_error 分支(阶段 2 引入来源标记);
5. **协议字符串一等公民**:`[interrupted]`、`[LLM 请求失败]` 定义在 message.py,
   将来崩溃恢复靠扫它们;
6. **未闭合围栏一律丢弃**:本阶段就确立"只执行写完整的块",阶段 2 流式检测直接复用;
7. **mock provider 三形态**:echo(手工体验)/ static / **脚本序列**(测试驱动多步循环的主力);
8. **msgs2dicts 跳过空内容消息**(部分端点对空 content 400);
9. read 路径双通道:fence 头参数 + 代码块每行一个(后者是 gptme 正统)。

## 六、已知限制(按计划推迟)

- 无流式输出(阶段 2);无原生工具调用与 call_id 配对(阶段 3);
- 无确认链 —— shell/save 相当于 gptme 的 `-y` 模式,危险命令不设防(阶段 4);
- reply() 每次构造 OpenAI 客户端(性能可接受,缓存属优化);
- 交互层的中断未做 ContextVar 门(提示符处已用 try 处理,语义等价);
- 系统提示词在恢复会话时不重新生成(gptme 的 prompt_generation 机制属后续)。
