# 013 · 修复 kimi 思考区粘连导致工具调用静默丢失

## 目标

真实会话(2026-1004-efe787,模型 dashscope/kimi-k3)里连续三次工具调用
(`websearch.fetchWebContent` ×2、`websearch.search` ×1)全部没有任何结果:
日志里 assistant 消息后面直接是下一条用户输入,不报错、不中断、不执行。
定位根因并修复。

## 根因(诊断过程)

1. **现象**:每次工具调用后日志无结果消息;模型下一轮 `<think>` 里自己都在说
   "no system tool output shown";input token 数还能反证上下文里确实没有结果。
2. **锁定**:唯一"什么都不写就结束回合"的路径是 `chat.py` 的
   `has_runnable_tooluse() → False` 静默返回 → 说明解析出的 ToolUse 是 0 个。
3. **复现**:kimi 的输出把围栏开栏紧跟在 `</think>` 后面写在**同一行**:

   ```text
   <think>…Let's fetch.</think>```websearch.fetchWebContent
   https://…
   ```

   而 `codeblock.py` 的开栏识别要求反引号在**行首**(`_FENCE_RE.match(line)`)→
   开栏没被认出 → 后面单独成行的 ``` 反被当成新开栏且永不闭合 → 整块丢弃。
   实验确认:粘连写法解析结果 `[]`,换行隔开则正常解析。

## 决策及理由

**采用 gptme 的原做法:解析工具调用前先剥掉 `<think>...</think>` 思考区。**
(查证了 gptme master 分支 `gptme/codeblock.py` 的 `_extract_codeblocks`:
开头就有 "dont extract codeblocks from thinking blocks",把闭合标签及其之前
的内容整体删掉。)

理由:
- think 是草稿,里面写的围栏本来就不该执行(无论粘不粘连);
- 剥掉后粘在 `</think>` 后面的围栏自然落到行首,kimi 格式直接兼容;
- 连带修掉一个隐患:修复前思考区里写的示例性 `@save(call_x): {...}`
  会被原生通道当成真调用执行;
- 额外收益:流式早停检测不会再被思考区里"恰好完整"的围栏骗到而提前截断生成。

实现语义(与 gptme 一致的三个要点):
1. 完整思考区:兼容 `<think>` 与 `<thinking>`(Gemini),开闭标签名允许混搭;
2. 没闭合的思考区(行首开标签、无闭合):**整体不解析**(流式中间态,宁可不执行);
3. 只认**行首**的开标签为"思考开始",粘在行中间的 `<think>`(如 ```<think>)
   不算 —— 避免"围栏语言标记里带 think 字样"的误伤。

保留不动:日志(conversation.jsonl)继续保留 think 原文;压缩视图剥旧 think
(compaction)也不变 —— 与 gptme 的三层处理完全对齐,只补了缺失的第三处。

## 已知限制

- 正文里(思考区外)粘在前文后面的围栏依旧不解析(行首规则不变,gptme 同款);
- 消息里同时存在完整思考区和**行首**未闭合开标签时,按 gptme 语义整体放弃
  解析(极端情形,流式安全优先)。
