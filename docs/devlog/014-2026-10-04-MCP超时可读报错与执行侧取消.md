# 014 · MCP 超时:可读报错、执行侧取消、超时可配置

## 目标

修复踩坑记录条目 2(docs/踩坑记录.md):真实会话里 websearch MCP 工具两次
超时,错误消息却是空白(`执行失败: `),模型不知道死因;且一次挂起的调用
可能堵死同服务器的后续调用。

## 决策及理由

按"原因 → 方案"一一对应实施:

| 原因 | 方案 |
|---|---|
| `TimeoutError.str()` 是空串,错误拼出来是空白 | `ToolUse.execute` 错误格式带 `{type(e).__name__}`;MCP 客户端把超时翻译成带服务器名、工具名、秒数、建议的可读 RuntimeError |
| 超时只在等待侧(`fut.result`),协程里的 `await call_tool` 继续挂着,串行队列被堵死 | 超时挪进协程内:`asyncio.wait_for(session.call_tool(...), timeout)`,到点**取消**单次调用,协程立刻回队列;主线程只留 +10 秒兜底 |
| 60 秒一刀切,搜索/渲染类工具天然偏慢 | `McpServer.timeout` 配置字段(alpha.toml 的 `[[mcp.servers]]` 下 `timeout = 180`),默认提到 120 秒 |

关键取舍:超时**必须在执行侧**生效。等待侧超时只是"我不等了",资源还挂着;
`asyncio.wait_for` 到点发取消,协程回到 `await ops.get()` 继续服务——这是
"单协程串行"架构能自愈的前提。回归测试专门验证了这点。

## 已知限制

- 取消依赖 `asyncio.wait_for` 能打断 SDK 的 await;若某 SDK 内部屏蔽取消,
  只能靠主线程 +10 秒兜底超时,此时会话可能仍需重建;
- websearch 服务器本身连不上 duckduckgo 的网络问题没有(也无法在客户端)解决,
  需在 alpha.toml 里给服务器注入代理环境变量或换引擎。
