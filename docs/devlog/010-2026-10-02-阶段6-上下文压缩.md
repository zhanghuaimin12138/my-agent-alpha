# 010 · 阶段 6:上下文压缩

- **日期**:2026-10-02
- **阶段**:6 / 上下文压缩(gptme 的护城河,长对话寿命的关键)
- **验收标准**:超预算的历史被压缩进"发给模型的视图",磁盘日志一字节不动;
接口报上下文超长能自愈重试 —— ✅ 达成

## 一、设计(仿 gptme 压缩引擎,一处重要简化)

**与 gptme 的差异**:gptme 把压缩结果存成"视图文件"切换使用;
我们**每次请求现算视图**(compaction 在 prepare_messages 管线里),
磁盘日志永不改写 —— 更符合我们的架构纪律(AGENTS.md:主日志永不销毁),
代价是每次请求重算一遍(纯 Python 遍历,毫秒级,可接受)。

### token 估算(不装分词库)

英文 ≈ 4 字符/token、中文 ≈ 1.5 字符/token 的两项启发式。
对"要不要压缩"的决策足够准;真实用量仍以接口 usage 为准。

### 预算

`get_context_budget = max(min(0.9×窗口, 窗口-预留回复-余量), 1000)`

### 三阶段规则压缩(快、确定性、不调模型)

1. **剥思考**:距结尾 ≥5 条的旧回复删 `<think>` 块(结论在正文里);
2. **截工具结果**:超 2000 token 的 system 工具输出,**最大优先**截断;
   截断前先存档到会话目录 tool-outputs/compacted/(文件名按内容哈希,
   重复压缩不重复存),占位注明存档路径 —— 模型需要时可自己去读;
3. **压长回复**:距结尾 ≥3、超 1000 token、不含工具调用的旧回复,
   抽取式压缩到 70%(切句打分:开头 +2/结尾 +1.5/文件路径 +1/错误关键词 +1.5;
   代码块无条件完整保留,按原顺序拼回)。
4. **兜底硬截断**:仍超预算 → 保留 pinned + 尽量多的尾部。

### 溢出自愈

llm 层识别接口的"context length"类 400 错误 → 抛专用 ContextLengthError
(独立 errors.py,避免循环导入);step() 捕获后**预算砍半再压、重试一次**,
再失败才抛出(不无限循环)。

## 四、过程中的坑

- **中文切句**:最初正则要求标点后跟空白 —— 中文句号后没有空白,
  整段被当成一句,抽取式压缩完全失效(测试抓住)。改为零宽断言直接切,
  英文句点额外要求后随空白(防切 3.14/e.g.);
- 测试自身两处算错:下标指向 user 消息、截断门槛用 >= 而非 >(恰好 2000 不截)。

## 五、已知限制(按计划推迟)

- 无 LLM 摘要式压缩(gptme 的 summarize 路径,RESUME.md)—— 规则压缩救不回
  的极端长对话目前走硬截断;
- 无 token 感知的动态预算(usage 回填校准估算)、无 prompt-cache 经济学
  (视图每次重算对缓存不友好,gptme 的 10% 节省率门控在视图模型下才有意义);
- 阶段 3 的句子打分是简化版(无语义/承诺/决策类词汇表)。
