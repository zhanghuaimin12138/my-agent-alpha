# 020 · R3:grep 工具

日期:2026-10-06 · 阶段:第二轮 R3 · 状态:代码完成,待用户审查后 commit

## 目标

round2-plan R3:治"agent 找得到代码"。给模型一个内容搜索工具,
输出固定格式 `相对路径:行号:命中行`,和 read 的行号输出、edit 的
精确替换配套,构成"找代码 → 看代码 → 改代码"的工作流。

## 决策及理由

| 决策 | 理由 |
|---|---|
| **纯 Python 实现**(偏离路线图"包装系统 rg/grep") | 本机没有 rg(`which rg` 为空);包装系统工具引入版本/locale 差异、双路径测试矩阵;本项目规模的仓库(os.walk + re)毫秒级完成,零外部依赖、测试 100% 稳定 |
| 工具名 grep、read_only=True | 模型对 grep 零学习成本;纯读免确认(shell 里跑 grep 要过确认分诊) |
| 参数文法与 todo 一致 | 围栏体第一行裸写 pattern,或 `pattern=/glob=/path=` 每行一个 key=value;原生通道三个具名参数(glob/path 可选)。两工具同一文法,模型的迁移成本为零 |
| 默认忽略 .git/__pycache__/node_modules/.venv/缓存目录/隐藏文件/读不了的文件 | 搜垃圾目录只有噪音;对照 gptme 的 allowlist 哲学(grep/rg 在它的只读白名单里)但我们在工具内做卫生,不依赖 shell 分诊 |
| 上限:200 行命中、单行 200 字符 | 宽泛 pattern 刷屏会淹没上下文;超限提示"收窄 pattern 或加 glob" |
| 无命中时明确说"没有匹配"并报扫描文件数 | round2-plan 的要求;模型拿它做否定判断,不能是空消息 |

对照:gptme 没有独立 grep 工具(研究报告 tools-system.md 无此条目),
它靠 shell 生态跑 rg/grep —— 我们做独立工具是因为确认链体验和输出
格式的确定性。

## 已知限制

- 默认区分大小写(模型可写 `(?i)`,instructions 里教了),没有单独的
  ignore-case 参数 —— 少一个参数就少一分文法歧义;
- 没有 context 行(前后 N 行)参数 —— read 工具已经是"带行号看上下文"
  的配套件,grep 只管定位;
- 超大仓库(百万行级)会慢于 rg —— 不是本项目的使用场景。
