# 052 —— 默认原生工具调用 + coding agent 定位提示词 + shell 无状态说明

## 目标

用户提的三件事:

1. 工具调用方式默认改成**原生工具调用**(function calling,不再默认走围栏代码块);
2. 系统提示词重写:定位从"通用个人助手"改成 **coding agent**(写代码为主,也能执行普通终端命令),并加入两条工作要求:
   - 写完代码要当场跑测试/检查,修到通过才算完成;
   - 一次做不完的大任务,先用 todo 工具拆成任务清单再推进;
3. shell 工具是"无状态"的(每次调用都是独立的 bash 进程)——要不要在说明里写明,由我判断。

## 决策及理由

### 1. 默认通道:markdown → tool

- 真正的默认值定在 `config.py` 的 `effective_tool_format` 兜底那一行,改它才有效;
  顺带把 `chat.py` 里三个内层函数的参数默认值也从 `"markdown"` 统一成 `"tool"`
  ——之前 `chat()` 默认 `tool`、内层默认 `markdown`,两处不一致,
  虽然实参一路显式传递没出过事,但留着就是给未来埋坑。
- 优先级链(命令行 > 环境变量 > 项目配置 > 用户配置 > 默认)不动,
  想切回围栏代码块:`--tool-format markdown` 或 alpha.toml 里 `tool_format = "markdown"`。
- mock 假模型不吃 tools 参数(见 llm/\_\_init\_\_.py 的分支),默认改原生不影响任何测试;
  压缩摘要调用(compaction_llm.py)显式写死 markdown,摘要不需要工具,不动。

### 2. 提示词重写(两通道同款要求)

- 身份段:"个人 AI 助手" → "个人 coding agent:主业写代码/改代码/排查代码问题,
  同时也能替用户执行普通终端命令(文件操作、git、系统查询等日常事务)"。
- 新增独立的"# 编码任务纪律"段,三条:
  - 动手前先读相关代码,不凭猜写作,改动小而准;
  - 写完当场用项目自带的检查手段验证(pytest / ruff / mypy 这类),
    修到通过才算完成,不许"写完即收工",也不许把验证推给用户;
  - 大任务先用 todo 工具拆待办,清单没清空就不算完成
    (这条和已有的"完成门控"钩子正好配套:提示词劝在先,门控拦在后)。
- "行动纪律"段(防"光说不做")原样保留,测试锁的关键话术一个没动。
- 放哪个通道都一样的纪律,就两份都写(_IDENTITY 和 _IDENTITY_NATIVE 各一份),
  不搞"只在某一版提"的偏门 —— 两通道提示词本来就要内容对齐。

### 3. shell 无状态:要说明(我的判断)

- 行为事实:每次调用都是 `bash -c` 起的全新进程,cwd 固定在工作区,
  上一次的 `cd`、环境变量、后台任务对下一次**完全不可见**。
- 为什么值得写:大模型普遍把"终端"默认理解成"一个持续的会话",
  很自然写出"先 cd 进目录,下一条再 ls"这种两段式命令 —— 第二条就悄悄跑错地方了。
  说明写在工具自己的 instructions 里,原生通道(函数描述)和
  markdown 通道(工具文档)自动都会带上,不用改两处。
- 给的对策也写明了:目录切换和操作写在同一条命令里(`cd src && ls`),或用绝对路径。

## 已知限制

- 旧会话 /resume 恢复时不重写系统提示词,老会话仍是旧身份表述 ——
  符合"日志不可变"的纪律,新会话自然用新提示词。
- 编码纪律里点名了 todo 工具;若用 --tools 白名单把 todo 裁掉,
  提示词仍会提到它(模型会自行适应,没做"按白名单动态裁剪提示词")。
- "写完跑测试"只是提示词层的约束,没有硬门控(不像 todo 有完成门控钩子)。
