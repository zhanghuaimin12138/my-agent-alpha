# 048 —— LLM 语义压缩 步骤 2:服务层与 /compact summarize

## 目标

按报告 L3(方案步骤 2)把步骤 1 的纯函数零件串成服务层:调一次模型写
笔记、验货、比对指纹、复用视图存储层激活;提供 /compact summarize
手动命令与笔记存档。/compact(机械压缩)行为不变。

## 决策及理由

- **摘要调用走 llm.reply() 通用门面**,但四个参数钉死:tools=()(记录员
  没有工具,笔记里的命令只是文字)、break_on_tooluse=False(笔记含代码块
  不许打断)、max_output_tokens=配置上限、markdown 通道。摘要请求本身
  **一个字不进对话日志** —— 它是内部操作,不是用户交互。
- **reply()/openai 兼容层加可选 max_output_tokens**:不传(None)不向接口
  声明,所有旧调用行为零变化;openai_compat 的 create_kwargs 条件加入。
- **结果分四种状态**:success/skipped(不值得:无前缀或收益不足)/
  stale(摘要期间历史变了,作废防漏消息)/failed(模型层故障)。
  笔记不合格/安检不过走 ValueError 单独一类 —— 那不是故障,是货不行,
  重试未必有用,由命令层如实转述。
- **提交前二次比对指纹**:模型写笔记花了时间,期间历史若变,这次结果
  基于旧快照,激活会漏新消息 —— stale 作废,不激活(测试用"reply 返回后
  立刻 append"模拟了这个竞态)。
- **收益门槛 15%**(min_savings_ratio,比规则压缩的 10% 高):这次要花
  一次模型调用,省得更少不值得。
- **笔记存档 views/summaries/<视图名>.md**:每个视图配独立文件而不是
  一份反复覆盖的总笔记,审计能对上号;写失败只告警(它只是人看的副本,
  真历史在主日志和视图 JSONL 里)。
- **测试抓到一个真冲突并修复**:V4 安检规定"pinned system 一条不能丢",
  而旧笔记恰是 pinned system、又必须被新笔记替换 —— 二次压缩必被误拒。
  修法:安检对 metadata 里 compaction.kind="llm_checkpoint" 的消息开
  精确例外(笔记是压缩产物,替换是设计行为);判断内联在 compaction.py,
  避免 compaction ↔ compaction_llm 循环导入。
- 尾部预算 = min(配置 8k, 模型窗口÷4):小窗口模型不死守 8k。

## 改动结构

- `src/my_agent_alpha/compaction_llm.py`:追加服务层(LLMSummaryResult、
  _save_summary_markdown、compact_current_with_llm)。
- `src/my_agent_alpha/llm/__init__.py` + `llm/openai_compat.py`:
  可选 max_output_tokens 透传(stream/_stream_once/reply 三级)。
- `src/my_agent_alpha/compaction.py`:validate_compacted_messages 的
  checkpoint 例外(+_is_llm_checkpoint 内联判断)。
- `src/my_agent_alpha/commands/builtin.py`:/compact summarize 子命令
  (成功/无前缀/笔记不合格各有一句人话),/help 更新。
- `tests/test_compaction_llm.py` +9:成功路径(FS01/FS02:Master 字节
  不变、双写继续、存档落盘)、无前缀 skip、坏笔记 ValueError、模型故障
  failed、竞态 stale、二次压缩替换旧笔记(FS07)、收益不足 skip、
  命令 e2e、max_output_tokens 透传(patching _stream_once 捕获参数)。
