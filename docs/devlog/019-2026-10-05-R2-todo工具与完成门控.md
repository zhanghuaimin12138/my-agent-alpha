# 019 · R2:todo 工具与完成门控

日期:2026-10-05 · 阶段:第二轮 R2 · 状态:代码完成,待用户审查后 commit

## 目标

治"多步任务半途而废":模型一句"我完成了"就收工,说过要做的事没人推。
对照 gptme(tools/todo.py + complete.py 的 auto-reply 门控),给 agent 加:

1. **todo 工具**:模型自己维护的内存任务清单(增删改查);
2. **完成门控**:回合结束而无工具调用、清单还有未完成项时,自动注入
   user 消息把模型拉回来;连续 2 轮仍不动手 → 熔断(如实报告,不再催);
3. **会话恢复**:todo 状态不写文件,恢复时重放日志里的 todo 调用重建。

## 决策及理由

| 决策 | 理由 |
|---|---|
| 状态机 3 态(pending/in_progress/completed) | gptme 有第 4 态 paused,但研究报告连它的语义都没讲清,砍掉(KISS) |
| 状态存进程内存,靠日志重放恢复 | todo 调用是普通消息已落 JSONL,重放即重建(gptme 同款);不引入新文件 |
| 门控注入 user 消息(round2-plan 定) | system 消息模型不一定当新输入;gptme 同款 |
| 熔断产出 system 报告、不回灌,队列空自然结束 | 不引入 gptme 的 SessionCompleteException,queue 空即退语义等价且更简单 |
| 熔断后计数归零 | 用户下次输入是新的意图,应给重新计数的机会 |
| 中断/拒绝/LLM 失败收尾不催 | 用户已表态或刚失败,再催很烦;_tail_is_terminal_marker 放行 |
| TodoItem 不存 created/updated 时间戳 | 计划里本有,实现时砍:渲染不显示、门控不用,纯冗余 |
| todo 工具 read_only=True | 只动进程内存不碰文件系统 → 免确认链,重放和门控体验顺畅 |
| 重放前先 _reset_todos | 同进程第二次 chat()(测试常见)不清会叠加出重复条目 |

**顺带补了一个欠账**:devlog/009 记录过 LOOP_CONTINUE 钩子"只落日志、
不回灌队列"的语义缺口 —— 门控消息无法触发新一轮对话。本次在
`_run_chat_loop` 补全:钩子产出的 **user 消息回灌 prompt_queue**(由消费端
统一落日志,不重复落盘),**system 只落日志不回灌**。这是对齐 gptme 的
prompt_queue 接力语义,对所有人 LOOP_CONTINUE 钩子生效 —— 核心循环里
没有任何 todo 特判。这也是本轮唯一的核心循环改动(+8/-1 行)。

门控判定链(每次 LOOP_CONTINUE,按序短路):
`本回合执行过工具 → 计数归零` → `清单干净 → 放行` → `尾部是中断/拒绝/失败
标记 → 放行` → `计数达上限 → 熔断报告` → `否则注入 user 消息(计数 +1)`。

"本回合执行过工具"(_turn_ran_tools)从日志尾部回扫推导:遇带可运行调用的
assistant 为真,遇 user(回合边界)为止 —— 零额外状态,恢复会话天然正确。

## 已知限制

- 模型反复 `todo read` 可无限重置催促计数永不熔断(read 也是工具调用);
  gptme 同款缺陷,真实模型的成本约束下不会发生,不修;
- 用户插话、模型纯文字回答、清单有残留 → 门控也会催(这是"自主推进"
  的一部分;注入措辞含"优先响应用户新指示",2 轮熔断兜底);
- 压缩视图截掉早先 todo 调用时,模型自己"忘记"清单(重放看主日志,
  状态仍准;模型可 `todo read` 找回)。
