## 一、目标

给现有 subagent 一个专门角色:**代码审查员**。只看代码改动、产出审查报告,
**物理上没有写能力**。触发方式是斜杠命令 `/review [范围]`(和 `/memory consolidate`
同构:命令侧调 `run_subagent`,共享同一套子进程编排)。

验收标准:敲 `/review`,得到一份 markdown 报告,每条发现带
**严重度 / 文件:行号 / 理由 / 建议修法**;整个审查过程不修改任何文件。

## 二、总体流程

```
用户敲 /review [范围]
        │
        ▼
/review 命令(父进程)
        │  1. 解析范围(缺省 = 工作区未提交改动;参数 = HEAD~1 / main...HEAD / a..b)
        │  2. 跑一次 git diff --stat 校验范围合法(快速失败,别让子代理白跑 300 秒)
        │  3. run_subagent(审查提示词, tools=read,grep,shell, env=只读强制开)
        ▼
审查员子进程(python -m my_agent_alpha -n -y --name subagent-<uuid> …)
        │  自己跑 git diff / log / blame / show(全是只读级命令)
        │  read / grep 看源码上下文
        │  最后一条 assistant 消息 = 审查报告
        ▼
父进程从子会话 conversation.jsonl 取报告 → 打印(M2:再回注父日志)
```

## 三、数据流规格(上下文在哪儿、日志在哪儿 —— 照 gptme 抄)

### 3.1 审查员子进程的上下文:开场消息逐条列出

子代理与父会话**零共享内存** —— 它的全部世界观就是自己日志里的开场消息
加任务提示词。gptme 的构造顺序(execution.py:485-655):
基础上下文(按 context_mode 选身份/工具/工作区文件)
→ profile 系统提示词 → profile 专属记忆 → 父上下文(可选转发)
→ 收尾指令 → 最后才是 user 任务消息。

**我们的审查员(M1 定稿,六条)**:

| # | 消息 | 内容 | 来源 |
|---|---|---|---|
| 1 | system | 身份 + 工具文档(**白名单裁剪后只剩 read/grep/shell 三个的文档**) | 现有 `get_prompt()` 静态条 |
| 2 | system | 当前时间 | 现有 `get_prompt()` 动态条 |
| 3 | system | 长期记忆索引 MEMORY.md | 现状 chat.py:682 会话开始就注入;**保持不动**(项目层记忆对审查员有参考价值,不加特殊分支) |
| 4 | system | "# 审查员档案\n\n" + 审查方法论 + 报告格式约定 | **新增**,对应 gptme 的 profile 消息(execution.py:618-623 原文格式 `# Agent Profile: <名>`) |
| 5 | system | 收尾指令:报告 = 最后一条回复,输出后不再说话 | **新增**,gptme 的 complete 指令(hooks.py:188)的简化版 |
| 6 | user | 审查任务:范围(git 命令原文)+ 未跟踪文件清单 + "自己跑 diff、别猜" | stdin 传入 |

**明示不共享的东西**:父会话的任何消息一条都不进审查员的上下文。
gptme 里父上下文(parent_messages)本来就是可选项(execution.py:634,
带密钥脱敏);审查需要独立性,我们**永远不转发** —— 这是"审查员不带立场"
的结构保证,不是提示词层面的自觉。

M1 的落地方式:#4/#5 两段直接拼进 #6 的任务提示词(一条 user 消息,
零新 CLI);终态加 `--agent-profile reviewer` 旗标,由子进程自己把档案
写成独立的 system 消息(与 gptme 逐字同构)。

## 四、关键决策及理由

### D1 审查员自己跑 git,不是父进程喂 diff

备选方案是父进程先跑 `git diff`、把 diff 塞进提示词,审查员只拿 read/grep。
不选:审查需要自主决定看什么 —— 这行是谁改的(blame)、这个函数还有谁在调
(grep)、上一版长什么样(git show)。喂静态 diff 会把它降级成
"只会对着补丁挑格式问题的检查器"。自主的前提是安全,见 D2。

### D2 新机制:shell 只读强制模式(fail-closed)

**现状缺口**:`-y` 模式下终端询问钩子不注册,确认链"走到链尾自动放行"
(chat.py 确认链注释)。灾难命令有 200 优先级护栏拦着,但
`git checkout .`、`pip install` 这类"不灾难但会改东西"的命令会被放行。

**解法**:shell_safety.py 新增一个确认钩子,环境变量
`ALPHA_SHELL_READONLY=1` 打开:开着时,非只读命令直接 skip
(附一句"审查代理只能跑只读命令"),只读命令照常放行。
注册优先级 15(只读放行 10 之后、链尾自动放行之前)。

**安全方向**:判不准就当不安全处理(fail-closed,和现有 `is_readonly_command`
同一姿态)。命令不在白名单 → 拦;确实需要 → 显式加进 `_READONLY_COMMANDS`。

**复用面**:不只服务审查员 —— 未来任何"能看不能改"的受限代理
(整理、审计、做梦)都靠这一个开关。

### D3 工具白名单 = read, grep, shell(只读强制)

不给 edit/save/memory:审查员的天职是"看和说"。建议修法写在报告里,
动不动手由人在主会话决定。物理无写能力 → "派发即审批"依然成立:
用户敲 `/review` 这个动作,就等于批准了审查员的全部行为(和
`/memory consolidate` 派发即审批同一逻辑)。

### D4 生命周期:沿用同步等待

一次派一个、阻塞到完成或超时(`ALPHA_SUBAGENT_TIMEOUT`,默认 300 秒)。
理由同 012:简单正确。审查范围大时 300 秒可能不够 —— M1 先靠环境变量调,
不够再给 `run_subagent` 加 timeout 参数。

### D5 报告 = 子日志最后一条 assistant 消息

复用 `_last_assistant_text`,零新机制。收尾指令(§3.1 第 5 条)保证
"最后一条"就是报告。gptme 用独立的 `complete` 代码块做收尾信号,我们
用"最后一条回复即报告"的约定 —— 少一个工具,契约弱一点,M1 够用;
终态若要结构化输出再升级成 complete 块 + schema(§3.4)。

### D6 会话目录名保持 subagent- 前缀

`is_subagent` 靠前缀把工作记录从 `/resume` 列表滤掉;审查会话同样是
工作记录,不该被续聊。不新增前缀 = 不动过滤逻辑。
(gptme 的 `subagent-{id}-{rand4}` 多一段随机后缀是因为它的 agent_id
是人起的名字会撞;我们的 uuid4 本身就唯一,不需要。)

范围解析规则:

- `/review` → 工作区未提交改动(`git diff HEAD`);另有未跟踪文件时,
  `git ls-files --others --exclude-standard` 列出来写进提示词,让审查员
  自己 read(新文件往往是最该审的);
- `/review HEAD~1`、`/review main...HEAD`、`/review a..b` → 原样传给
  `git diff <范围>`;
- 非 git 仓库或范围不合法 → 命令侧直接报错,不派子代理。

提示词模板要点(review.py 内维护,即 §3.1 的 #4/#5/#6):

- 身份:你是只读的代码审查员,没有任何修改能力,别尝试;
- 方法:先看 diff,再对可疑处用 read/grep 查上下文、git blame 查来历,
  **不要凭 diff 猜**;
- 输出格式(固定,便于人读也便于将来程序解析):

  ```
  ## 发现
  ### [高] src/my_agent_alpha/xxx.py:123 一句话问题描述
  什么输入/场景下会错,为什么
  建议:……
  ## 总评
  一段话:这批改动整体如何、敢不敢合
  ```

- 纪律:只报有把握的,猜测标注"存疑";没有发现就写"未发现问题"。

### M2 报告回注父会话

命令把报告作为一条消息追加进父会话日志(LogManager 现成 API,命令侧已有
ctx.manager)。主模型下一回合看得到,用户可以说"修掉第 2 条"接着干。
角色用 user(内容是"这是审查报告,供参考"),不伪装成 assistant。

### M3 异步编排 + 按维度并行(= 终态版 §3,照 gptme)

三件事一起做(gptme 对照件全部就位后一步到位):

1. **控制通道**:§3.2/§3.3 的 control.jsonl 三件套 + 子侧 STEP_PRE 排空钩子;
2. **进度与监控**:progress.jsonl + 父侧监控线程 + 完成通知
   (LOOP_CONTINUE 钩子注入"✅ 审查员 correctness 完成(7 条发现)");
3. **并行三维度 + 聚合**:正确性 / 测试 / 可读性各派一个
   (ThreadPoolExecutor 等子进程,各自独立进程独立日志,零共享);
   确定性合并(严重度 > 维度排序);"合并代理去重终审"以后再说。
   注册表持久化 subagent-meta.json(父重启认领)。

并发上限 = 维度数(3),不需要 gptme 的信号量/预算机制。

## 六、等待与唤醒:主循环的等待态(M3 的父侧半块,W1–W3)

问题:派发即返之后,父代理这回合说完了(没有可运行工具调用),但子代理
还在跑 —— 主循环此刻应该**等**,子代理完成后再自动续跑。

### 6.0 gptme 的真实答案(三层,先抄后改)

读 /tmp/gptme 源码核实(chat.py / tools/subagent/):

| 层 | gptme 做法 | 出处 |
|---|---|---|
| 回合内等 | 模型自己调 `subagent_wait(id, timeout=60)`:`process.wait(timeout)` 阻塞在**工具执行**里,超时就"still running"返回,模型再等 | api.py:1883-1931 |
| 回合边界注入 | 回合结束时 LOOP_CONTINUE 钩子排空完成队列,产出 "✅ Subagent X completed" → prompt_queue → 外层续跑 | hooks.py:403 |
| 空闲唤醒 | **只有 server 有**:完成事件经 SSE + request_watch_wake 唤醒阻塞中的 server 会话;**CLI 不做** —— 坐回输入提示符傻等,完成事件等下一次循环迭代才投递 | hooks.py:313-353 |
| 退出清理 | SESSION_END 钩子取消属于本会话的孤儿子代理(SIGTERM→5 秒→SIGKILL) | hooks.py:356-406 |

关键认知:gptme CLI 的"等"主要是**模型的决策**(wait 工具),不是循环的
状态;循环只认"队列里有没有消息"。我们的架构纪律(继续判定不看额外状态)
与它天然一致 —— **等待只影响"空队列时阻塞在哪个等待点",不碰继续判定**。

### 6.1 我们的设计:完成事件的唯一去向是队列

新增两个部件(都在 036 M3 的注册表/监控线程之上):

```
注册表(活着的子代理)          完成队列(queue.Queue)
  subagent-aaa ──监控线程──proc.wait()──┐
  subagent-bbb ──监控线程──proc.wait()──┼──► put(("done"/"failed"/"timeout", id, 结果))
  subagent-ccc ──监控线程──proc.wait()──┘         │
                                                   ▼
   _run_chat_loop 的等待点(queue.get 阻塞,即"等待状态")
                                                   │
                          "✅ 子代理 aaa 完成:<结论>" 作为 user 消息
                                                   ▼
                             走正常路径:落日志 → 新回合 → 恢复 Agent Loop
```

**恢复循环 = 往日志追加一条 user 消息**,零特殊机制 —— "日志即接口"的
又一次红利。铁律:**完成事件只进队列,不许旁路直接 print**(见 6.3 竞态)。

### 6.2 等待点改造(_run_chat_loop,现状 chat.py:564-573)

```
while True:
    if prompt_queue:            content = prompt_queue.pop(0)
    elif _has_running_subagents():                      # ← 新分支:等待状态
        content = _wait_subagent_event()                # 阻塞在完成队列
        if content is None: continue                    # 全部结束且无事件 → 回到循环顶
    elif non_interactive:       return manager          # (-n 也要先过等待分支再退)
    else:                       content = _get_user_input()…
```

- `_wait_subagent_event()`:循环 `队列.get()` 直到拼出一条通知消息;注册表
  空了且队列空 → None。等待前打印一行
  "(2 个子代理在跑:正确性/测试,等待完成… Ctrl-C 可回提示符)";
- Ctrl-C 在等待态 = 回到普通输入提示符(子代理继续跑,结果由下一次
  回合结束时的 LOOP_CONTINUE 钩子投递)—— 等待永远有出口,不会死锁;
- 失败/超时同样入队,格式 "✗ 子代理 xxx 超时(>300s)",模型看到后自决
  重派或放弃。

### 6.3 竞态分析(为什么不会丢事件卡死)

丢事件的经典窗口是"检查完'没有事件'→ 进入阻塞"之间恰好来了事件。
我们的方案没有这个窗口:**事件先入队,get 的语义是"队列非空立即返回"** ——
put 发生在 get 之前或阻塞中,都能拿到。前提就是 6.1 的铁律(事件只走队列)。
gptme 需要用 prompt-queue-closed 哨兵文件封窗口(chat.py:468-486 大段注释),
是因为它的外部提示走文件系统;我们的事件在进程内(监控线程 proc.wait 在
父进程里),天然免疫。control.jsonl(父→子)是跨进程的,那边照抄哨兵思路。

### 6.4 与 LOOP_CONTINUE 的分工(两条路汇于同一点)

- 完成发生在**回合进行中**:事件已入队;回合结束处现有的 LOOP_CONTINUE
  钩子(chat.py:604-607,已实现)排空完成队列 → user 消息回灌 prompt_queue
  → 外层立即续跑。**这条路径主循环今天就支持**,只差一个排空钩子;
- 完成发生在**等待态**:6.2 的新等待点直接拿到。
- 汇合点都是"事件 → user 消息 → prompt_queue",一个机制、两种触发时机。

### 6.5 分阶段:W1 → W2 → W3

- **W1(一个钩子,零循环改动)**:LOOP_CONTINUE 排空完成队列的钩子。
  效果:回合结束时恰有已完成的子代理 → 无缝续跑。今天就能写;
- **W2(等待态,~10 行循环改动)**:6.2 的等待分支。这是"主 Agent 暂时
  没工作但有未完成子任务 → 等待 → 事件唤醒恢复循环"的完整实现,
  覆盖 CLI 单人场景(gptme CLI 反而没做这个);
- **W3(终态,统一事件源)**:stdin 读线程 + 完成事件合流成**一个输入
  队列**,等待点唯一化。收益:子代理在跑时用户仍能打字聊天,完成通知
  与用户输入自然交错(gptme 只有 server 模式有这体验)。代价:input()
  挪进线程、提示符渲染要小心,放最后做。

退出清理(随 W2 一起):SESSION_END 钩子照抄 gptme hooks.py:356 ——
对注册表中活着的、归属本会话的子代理 SIGTERM→5 秒→SIGKILL;
归属检查用 parent_logdir 匹配,防多会话误杀。
